# 提示词日志

**这份日志是为了回答一个问题：那一次调用，模型到底收到了什么字、吐回来什么。**

用户 2026-09-18：「将所有的提交提示词给大模型的地方和获取结果的地方都以日志保存
下来放到程序统计目录里，我要研究。」

判据只有一条：**看着日志能还原一次调用**——哪一步、用的哪个模型、什么温度、
模型真正收到的是哪段字、它吐回来什么、想了什么、花了多久、对面回了什么状态码。
**成功和失败一样记**，失败那一半正是最想研究的：什么提示词换来一个 400、
什么提示词让 schema 本地校验没过。

## 落在哪儿

程序数据目录底下的 `llm_log/`，再按**项目名**分子目录：

| 平台 | 路径 |
|---|---|
| macOS | `~/Library/Application Support/changji/llm_log/<项目名>/` |
| Windows | `%LOCALAPPDATA%\changji\llm_log\<项目名>\` |
| Linux | `$XDG_DATA_HOME/changji/llm_log/<项目名>/`，没设就 `~/.local/share/changji/llm_log/<项目名>/` |

**为什么不放在项目目录里**：跨项目的都收在一处才好做横向对比（「同一步在两部戏
上分别花了多久」），而拷项目目录给别人时也不会把日志一并带走。

`<项目名>` 取的是项目目录路径的最后一段，有中文和空格就照原样建目录。那一刻
没有项目（对拍、`--doctor`、后台批处理）时是 `_无项目`。

想把一批日志单独收到别处跑对比，设环境变量 `CHANGJI_LLM_LOG_DIR` 指向一个目录
即可，不必去动配置文件。

## 一次调用留下哪几个文件

```
index.jsonl               每项目一份，一行一次调用，追加写，**永不删**
<id>.prompt.txt           模型真正收到的那段字（贴完 schema 之后的）
<id>.reply.txt            模型吐回来的原始正文
<id>.thinking.txt         有思考才写
<id>.tools.json           带工具的那条对话且真发了工具表才写
<id>.error.txt            失败才写
```

`<id>` 长这样，排序就是时间序：

```
20260918-174233-518-0007
└ 年月日 ┘└ 时分秒┘└毫秒┘└ 序号 ┘
```

末尾那个是进程内自增的序号，同一毫秒里也不会撞。

**为什么是「索引 JSONL + 每次一对纯文本」**：统计只读 `index.jsonl`，一行几百
字节，`jq` 和 pandas 直接吃；而提示词和回复**原样**存成 `.txt`，想比两次提示词
差在哪儿就 `diff`，想找哪次提到过某个词就 `grep`。塞进 JSON 的话，几千字正文会
被转义成一行没法看的东西。

`prompt.txt` 存的是**模型真正收到的那段字**，不是那条原始提示词——schema 是当
文字贴在提示词后面发出去的（见 CLAUDE.md「没有语法层」），这个文件里含那一整段。

`error.txt` 两段：第一段是**翻给用户的那句**（当时界面上显示的原话），第二段是
对面的原始回包，**不截断**。

抬头写「对面原始回包（无）」的判据是**这一次根本没收到回包**：连不上、请求发出去
之前就被取消。**schema 本地校验没过不算**——那一次 HTTP 是 200、回包早就收下了，
抬头写的是「对面原始回包（HTTP 200）」，后面跟着整份回包。而那正是这一类最该看的
东西：模型到底吐了什么才没通过校验。（下面第二条样例就是这一种，`http_status` 是
200 而 `ok` 是 false。）

## `index.jsonl` 的字段

一行一个紧凑 JSON 对象。**下面这些永远都有**，取不到就是空串 / 0 / false，
让列永远在（统计时不用处处判缺键）：

| 键 | 类型 | 说明 |
|---|---|---|
| `id` | string | 见上，同时是那几个 `.txt` 的文件名前缀 |
| `at` | string | 本地时间，带时区偏移：`2026-09-18T17:42:33.518+08:00` |
| `backend` | string | `remote`（打 API）/ `command`（跑本机命令行） |
| `kind` | string | `complete`（整段）/ `complete_stream`（流式）/ `chat`（带工具的多轮） |
| `schema_name` | string | 是哪一步：`chapter` / `storyboard` / `script` … |
| `model` | string | **分流之后**真正用的那个，不是配置里的兜底 |
| `temperature` | number | 真正发出去的那个（按 schema 偏移过的） |
| `reasoning_effort` | string | **真发出去**才有值；空着不等于调用方没要，见下面「几条读数的时候别搞错」 |
| `endpoint` | string | 远端记 `base_url`；命令行记 `命令名 参数 参数…` |
| `project` | string | 项目目录的**绝对路径**（目录名只够分文件夹，研究时要认得出是哪一部） |
| `episode_id` | string | 哪一章 |
| `task` | string | 那件活的名字，「写正文 · 第 3 章」这种 |
| `stream_id` | string | 这一轮的推送 id，和任务页面上那条对得上 |
| `prompt_chars` | number | **UTF-8 的「字」，不是字节**，见下 |
| `reply_chars` | number | 同上 |
| `thinking_chars` | number | 同上 |
| `ms` | number | 这一次调用的墙上时间，毫秒，一位小数 |
| `finish_reason` | string | 对面给的 |
| `ok` | bool | 没抛异常就是 true |
| `http_status` | number | 对面回的状态码；不是 HTTP 那条路、或压根没连上就是 0 |
| `error` | string | 失败时**翻给用户的那句**，成功时空串 |

**有才有**（没有就整个键不出现）：

| 键 | 类型 | 什么时候有 |
|---|---|---|
| `ms_to_first` | number | 只有流式那条，且真收到过第一段正文 |
| `usage` | object | 对面回包里有 `usage`，只收 `prompt_tokens` / `completion_tokens` / `total_tokens` |
| `tools_count` | number | 只有带工具那条，且真发了工具表 |

### 三个 `_chars` 数的是**字符**，不是字节

「这条提示词五千八百字」和「这条提示词一万七千字节」里，只有前一个能跟 token 数、
跟 CLAUDE.md 里那张 schema 字数表（5573 / 7438 / 9300，量的就是字符）对得上。
**全仓只有一处按字节算**，就是下面那个磁盘上限，它名字里明写着 `mb`。

### 三条真实样例

分别是「流式写正文，成了」「整段拆分镜，schema 本地校验没过」「命令行后端，
没有项目」：

```jsonl
{"at":"2026-09-18T17:42:33.518+08:00","backend":"remote","endpoint":"https://open.bigmodel.cn/api/paas/v4","episode_id":"ep03","error":"","finish_reason":"stop","http_status":200,"id":"20260918-174233-518-0007","kind":"complete_stream","model":"glm-5.3","ms":98431.2,"ms_to_first":4120.5,"ok":true,"project":"/Users/s2/电影/山里的信号","prompt_chars":6412,"reasoning_effort":"","reply_chars":4180,"schema_name":"chapter","stream_id":"job_7f21","task":"写正文 · 第 3 章","temperature":0.5,"thinking_chars":23140}
{"at":"2026-09-18T17:44:11.902+08:00","backend":"remote","endpoint":"https://open.bigmodel.cn/api/paas/v4","episode_id":"ep03","error":"大模型输出不符合 storyboard Schema：shots[4].camera_move 不在枚举里","finish_reason":"stop","http_status":200,"id":"20260918-174411-902-0008","kind":"complete","model":"glm-5.3-flash","ms":301884.0,"ok":false,"project":"/Users/s2/电影/山里的信号","prompt_chars":7104,"reasoning_effort":"low","reply_chars":9233,"schema_name":"storyboard","stream_id":"","task":"拆分镜 · 第 3 章","temperature":0.35,"thinking_chars":0,"usage":{"completion_tokens":11402,"prompt_tokens":9130,"total_tokens":20532}}

```

三处要看清楚：

- 第一行**没有 `usage`**——流式那条拿不到，见下面「几条读数的时候别搞错」。
  它有 `ms_to_first`。
- 第二行 `ok=false` 而 `http_status=200`：对面好好地回了 200，是**我们这头**按

- 第三行 `project` / `task` / `stream_id` 全是**空串，不是缺键**：那一次跑在
  没有活、没有项目的线程上。

键的顺序是字典序（`nlohmann::json` 排的）。统计那头按键取，顺序无意义，
而字典序稳定——**别为了好看改成有序 JSON**。

## 怎么拿它做研究

下面几条直接能跑，`cd` 到那个项目的日志目录里。

**按阶段看平均耗时和次数**（哪一步最费时间）：

```bash
jq -s 'group_by(.schema_name)[]
       | {步骤: .[0].schema_name, 次数: length,
          平均秒: (map(.ms) | add / length / 1000 | .*10|round|./10),
          最慢秒: (map(.ms) | max / 1000 | .*10|round|./10)}' index.jsonl
```

**按模型看 token 用量**（只有非流式那些有 `usage`，所以先滤掉没有的）：

```bash
jq -s '[.[] | select(.usage)] | group_by(.model)[]
       | {模型: .[0].model, 次数: length,
          输入: (map(.usage.prompt_tokens) | add),
          输出: (map(.usage.completion_tokens) | add)}' index.jsonl
```

**找最长的那几条提示词**（提示词是所有开销的源头，先量再砍，见 CLAUDE.md
「量比例再动手」）：

```bash
jq -r '[.prompt_chars, .schema_name, .id] | @tsv' index.jsonl \
  | sort -rn | head -10
```

**挑出所有砸了的**，连同那句翻给用户的话：

```bash
jq -r 'select(.ok | not) | [.at, .schema_name, .http_status, .error] | @tsv' index.jsonl
```

**把某一步的所有提示词捞出来 diff**（「这两次写正文，提示词差在哪儿」）：

```bash
jq -r 'select(.schema_name == "chapter") | .id' index.jsonl > /tmp/ids
diff $(head -1 /tmp/ids).prompt.txt $(sed -n 2p /tmp/ids).prompt.txt
```

**一次调用完整地摊开来看**：

```bash
id=20260918-174411-902-0008
jq "select(.id == \"$id\")" index.jsonl
wc -m $id.*.txt
less $id.prompt.txt
```

**跨项目横着比同一步**（日志按项目分目录，就是为了既能分开看又能合起来看）：

```bash
cd ..   # 到 llm_log/
jq -s 'group_by(.schema_name)[] | {步骤: .[0].schema_name,
        崩的比例: ((map(select(.ok | not)) | length) / length)}' */index.jsonl
```

## 上限和剪旧的规矩

- 正文文件（`prompt` / `reply` / `thinking` / `error` / `tools`）有一个**总磁盘
  上限**，就是 `[llm].call_log_max_mb`，默认 1024 MB，收 1 到 102400（100 GB）
  之间的数，超出去起服务时就会说。**这个数管的是整个 `llm_log/`，不是一个项目
  一份**——同一台机器上跑得最凶的那部戏，会把别部的旧正文一起挤掉。

  ⚠️ **管得住的只有这个进程认得的那些。** 一趟进程只扫一次盘（见下），之后只认
  自己写的。同时开着两个 changji 的话，两边各按自己那本账剪到 1 GB，磁盘实占可以
  到两倍——所以这个数是「一个进程的上限」，不是「这个目录的硬上限」。
- **剪的顺序是「落盘顺序」，不是 `id` 上那个时间戳。** `id` 的时间戳是这一次
  **开工**那一刻的，而正文是这一次**结束**才落盘的：一次流式拆分镜跑掉 166 秒
  （`"ms":166842.4`），这 166 秒里批量那几条几秒钟的短记录早写完了。按 `id` 排
  的话，超上限的那一下 `begin()` 正是这次长的自己——**最贵、最想看的那一次第一
  个被扔**，留下一堆短的。所以账上排队用的是入账那一下发的自增号。
  上一趟进程留下的那些排在这一趟前面；它们彼此之间只能按 `id` 排，落盘顺序早就
  不在了。（**认回来的时机不是起服务那一下**，是这一趟进程**第一次真写下正文**
  的时候顺手扫一遍——起服务时不碰盘，日志关着的时候连目录都不去算。）
- **一次删掉那一次的全部文件**，不删一半：有提示词没回复的半份记录比没有更
  误导人。
- **`index.jsonl` 永不删，也不算在那个上限里。** 一行几百字节，一百万次调用也
  才几百 MB，而它是统计的依据。所以剪旧只淘汰正文：那几行统计照旧在，只是
  点不开原文了（`id` 还在，`<id>.prompt.txt` 已经没了）。做成「统计数据也跟着
  没了」的话，这个功能就只剩最近那几天能用——而「这半年里哪个模型的分镜最容易
  崩」正是要跨过那几天才答得出来的。
- 想关掉：`[llm].call_log = false`，改完重启。默认是**开**的。
  ⚠️ **设置页上还没有这个开关**：`/api/connections` 已经收
  `llm_call_log` / `llm_call_log_max_mb` 这两个键，界面上的控件还没做。
  **别填 `call_log_max_mb = 0` 当关掉用**，那个值起服务时就被拒了。

## 不记什么

- **`Authorization` 一个字节都不落盘。** 密钥在请求头里，而**整个请求头都不记**，
  只记 `base_url`。
- **命令行那条 `endpoint` 记的是命令名加参数**，而参数是人在
  `[llm].command_args` 里自己填的自由文本（设置页和配置接口都不过滤）。填成
  `["-p", "--api-key", "d3b4f0a1e2.9Kx2mQ7v"]` 跑一次，那把密钥就会进
  `index.jsonl`——而这份日志是拿来发给别人一起看的。所以落盘之前抹两道：

  1. **按 argv 的位置抹**（`llm/client_command.cpp` 的 `endpoint_of`）：
     上一个参数里带 `key` / `token` / `secret` / `password` 字样（不分大小写）
     的，**下一个整个换成 `***`**；`--api-key=VALUE` 这种值写在同一个 argv 里
     的，等号后面换掉。**开关名一个字不动**——研究时要认的「这次带的哪几个
     开关」照样看得见。
  2. **再按形状抹一道**（`llm/call_log.cpp` 的 `redact_secrets`，和 `error`
     那一栏同一套）：`Bearer xxx`、词首那种长的 `sk-` 串、JSON 里几个键的值。

  ⚠️ **认的就是这两种形状，别读成「密钥一定进不去」。** 开关名不带那四个词的
  （`-k VALUE`）、或者把密钥当位置参数直接跟在命令后面的，两道都认不出来。
  自己拼命令行时把密钥留在环境变量里，别写进 `command_args`。
- **回放客户端不记。** 它只给测试和回放用，接上去的话跑一次单元测试就往数据
  目录里写一千多份文件。

反过来，**提示词本身是原样落盘的**，而提示词里是整章正文。拷这个目录给别人之前
先想一下。

## 几条读数的时候别搞错

1. **命令行后端那三个数不是真值。** `backend` 是 `command` 的那些行里，
   那条路**一个参数都不发**——用哪个模型、什么温度由那个命令行自己定。
   （不记成空串，是因为空着的话按 `model` 分组会把命令行这条全归进一个空桶，
   而它其实是按 `schema_name` 分流过的。）

   **三栏的来路还不一样**，按它们分桶之前要知道分的到底是什么：

   | 栏 | 记的是 |
   |---|---|
   | `model` | 配置分流出来的（`[llm.models]` 里这一步配的那个） |
   | `temperature` | **调用方填了就是调用方的**，没填才落到配置 |
   | `reasoning_effort` | **压根不是配置项**（`LLMConfig` 里没这个字段），纯粹是这一次调用方要的 |

   所以命令行那些行按 `reasoning_effort` 分桶，分的是「这一步的调用方要它多想」，
   不是「机器怎么配的」——和远端那些行（记的是真写进请求体的值）**不是一回事**，
   别并在一起算。
2. **流式那条没有 `usage`。** 发出去的请求里没要 token 统计，最后一帧里也就
   没有。想要 token 数就先按 `_chars` 看，或者把那一步临时切回非流式跑一遍。
   **别为了补上它去改真正发出去的请求体**——各家对那个字段的支持七零八落，
   拿一次生成全挂换一个统计字段不值当。
3. **「已取消」也是一次失败。** 人按了停的那次会记成 `ok=false`、
   `error` 是那句「已取消」。这是对的：取消是一次调用真实的结束方式，账上不该
   凭空少一次。统计时按那句原话过滤就行。
4. **带工具那条的 `reply_chars` 常常是 0。** 模型这一轮只发了工具调用、没说话，
   它说的内容在 `tools_count` 和下一轮的提示词里。
5. **一次调用只有一行。** 流式那条在自己那儿记，外层转手的那一下不重复记——
   看到同一件活上两行时间套着，那是两次真调用（重试）。
6. **`reasoning_effort` 这一栏空着，不代表调用方没要求。** 它记的是**真写进
   请求体**的那个值——远端那三条路（整段 / 流式 / 带工具）都是从拼好的 payload
   里取的，不是照着配置再读一遍。
   而这个参数**只对智谱那一族发得出去**：`llm/client.cpp` 按模型名认，模型名以
   `glm-5` 打头才连同 `thinking` 一起发，理由那儿写着「认错的代价是别家收到不
   认识的字段直接 400——那会让所有生成一起挂」。
   所以上游无条件要一个 `high`、这一次却落到兜底的 `glm-4.7-flash` 时，请求体
   里一个 `reasoning_effort` 都没有，**这一栏也就是空的**。
   **拿这一栏分桶做对比之前先看 `model`**：不然「high 桶」和「空桶」里会混着
   一批发的其实是同一份请求的调用，两边的差异全是噪声。
   （`backend` 是 `command` 的那些行另说，见上面「命令行后端那三个数不是真值」
   那条：那条路一个参数都不发，这一栏记的是配置里写着什么。）
