# C++ 后端重构方案

制定时间 2026-09-07，同日按十六项决策修订。

修订集中在三处：单一二进制的边界、推理接入的顺序、契约兼容的标准。
阶段表和风险表整个重排，并新增了一个必须在阶段 1 之前做完的前置验证工程。

## 目标

把现在的三层（Python 引擎 + ComfyUI + Node 界面）收敛成两层：

- **C++ 单一二进制**：编排 + 推理 + HTTP 服务
- **Node**：界面，以及平台投递这类天然属于 Node 生态的对接

产出物是一个 exe，零运行时依赖，Windows 和树莓派都能直接跑。

约束顺序：**能跑 > 画质 > 速度**。低配硬件上时间不是问题，显存才是。

### 单一二进制的边界

严格执行：**不允许随包分发任何 Python 侧车**。配音、口型、超分这些现在
只有 Python 实现的环节，要么自己 C++ 化，要么不做。

ComfyUI 不算侧车。它是用户机器上本来就装着的独立程序，作为**可选后端**
保留——有它就能用它那一整套生态，没有它二进制自己也要能跑。

但这个目标是**终局的，不是任何一个阶段的验收标准**。配音的 C++ 化
（见风险一）工期不可估，在它完成之前，纯二进制出不了声，配音要走
ComfyUI 后端过渡。阶段表里没有任何一格的完成标志包含"单一二进制已达成"。

## 为什么是 C++

不是为了快。编排层是纯 IO 胶水，语言对性能没有影响。

真正的理由只有两个：

1. **跨模型的显存调度**，以及推理上下文的复用。见下面那节。
2. **单一二进制**。低配设备上装 Python 环境和 Node 运行时本身就是负担

### 修正：逐层换入换出不是链接进来的理由

原文这里写的是"链接进来才能拿到逐层权重换入换出的控制权，让 16GB 的模型
在 6GB 卡上跑起来"。**这句话不准确**，2026-09-08 查 sd.cpp 源码时发现的。

sd.cpp 上游已经把这套做完了，而且默认开启：

| 机制 | 参数 | 效果 |
|---|---|---|
| 权重放 RAM | `--params-backend cpu` | 权重留内存，用到才搬进显存 |
| 权重留磁盘 | `--params-backend disk` | 按需从模型文件重读，常驻最低 |
| 自动分段执行 | 默认开 | 图切成段，当前段权重钉住，下一段异步预取，压力大时从最后一段倒着驱逐 |
| 显存预算 | `--max-vram <GiB>` | 明确上限，扣除已驻留的托管权重 |
| 按模块指定 | `--params-backend diffusion=disk,te=cpu,vae=cpu` | 只对最大的那几块生效 |

`docs/performance.md` 的原话是这套流式执行 "No opt-in streaming flag is
required"。实现在 `src/device_residency_manager.h`（`ensure_compute_backend_capacity`
收"需要的张量、可驱逐顺序、受保护的张量"三组参数）和 `model_manager_prefetch.cpp`。
而且这些全在 `sd_ctx_params_t` 里，不是 CLI 专有——起个子进程调 sd-cli 一样拿得到。

把这条留着当立项理由，会让人以为不重构就跑不了大模型，那是错的。

### 真正只有单一二进制能做的两件事

**一、跨模型的显存调度。**

sd.cpp 只看得见自己那个 context。changji 一集要用四类模型，它们在时间上
是错开的：

    LLM（写剧本、分镜）→ 图像模型（首帧）→ Wan（视频）→ TTS（配音）
      一集一次              每镜一次          每镜一次       每句一次

LLM 跑完之后它那几个 GB 就再也不需要了，但 sd.cpp 不知道，llama.cpp 也不知道。
只有编排层知道"这一集的分镜已经定稿，语言模型可以整个还回去"。
ComfyUI 那边这件事由它自己的缓存策略决定，你控制不了。

**二、推理上下文的复用。**

建一个 `sd_ctx` 要解析模型文件、建张量图、分配运行时缓冲，很贵。
一集四十个镜头：进程内建一次用四十次；走子进程是建四十次。
在 6GB 卡上后者慢到不可用——每次都要重新把权重从磁盘搬一遍。

这两件事加起来就是 `src/infer/scheduler`（见架构一节）要解决的问题。

代价要认：编排层用 C++ 大约要 2.5 倍行数，且没有 pydantic 的等价物。
这是为上面两条付的学费，不是 C++ 在这一层更优。

## 二、技术选型

| 用途 | 选型 | 理由 |
|---|---|---|
| HTTP + WebSocket 服务端 | **Crow** | 路由写法接近 Flask/FastAPI，接口能近乎一一对译；WebSocket 内置；header-only，交叉编译到 ARM 省事 |
| HTTP 客户端 | **cpp-httplib** | 只用来连可选的 ComfyUI 后端。LLM 和 TTS 都进程内，不再需要客户端 |
| JSON | **nlohmann/json** | 用普通 `json` 即可，不需要 `ordered_json`——契约标准是结构兼容而不是逐字节，见第三节 |
| 视频/图像推理 | **stable-diffusion.cpp** | 已支持 Wan 2.2 TI2V-5B，含 `--offload-to-cpu` 逐层卸载、`--vae-tiling`、`--diffusion-fa` |
| 文本推理 | **llama.cpp（进程内链接）** | 剧本/圣经/分镜三个阶段用。见下 |
| ggml | **统一 vendor 一份** | 两个库都关掉自带的，指向同一个 commit。见风险二 |
| 音视频 | **ffmpeg 子进程** | 保持现状。链接 libav 收益不足以抵消复杂度 |
| 配音 | **Qwen3-TTS 自行 C++ 化** | 见风险一 |
| 单元测试 | **doctest** | 单头文件、编译快、FetchContent 友好。Pi 上本机编译时 Catch2 的编译开销受不了 |
| 构建 | **CMake + FetchContent** | Windows 用 MSVC（CUDA 要过 nvcc，nvcc 不支持 MinGW）；ARM 用 Vulkan 后端 |

### 文本推理为什么走进程内

llama.cpp 起 server 也是 OpenAI 兼容的，保留现有的 HTTP 客户端本来是
零改动的省事做法。选进程内链接是为了守住单一二进制：一个要求用户
另外起一个服务进程的二进制，不叫单一二进制。

代价要认：`LLMConfig` 的 `base_url` / `api_key` 作废，`/api/llm/providers`
和 `/api/llm/models` 语义重定义为"列本地 gguf"，连远端云端大模型的能力
一并放弃——写剧本这一环云端大模型质量明显更好，这是真的损失。
这三项进第三节的破契约白名单。

### 不需要的东西

- **业务逻辑的异步化**。Crow 自带 asio 事件循环处理连接，但六个阶段的
  代码保持同步写法，跑在工作线程池上。Python 那边满屏的 `async` 是
  FastAPI 的框架要求，不是业务需求，不要照搬
- **ORM / 数据库**。项目数据是文件系统上的 JSON，保持原样

### pydantic 的替代

C++ 没有等价物，这是移植中最枯燥的一块。采用的模式：

```cpp
struct Shot {
    std::string shot_id;
    int duration_ms = 3000;
    // ... 字段
    NLOHMANN_DEFINE_TYPE_INTRUSIVE_WITH_DEFAULT(Shot, shot_id, duration_ms, ...)

    // 校验单独一个方法，返回错误列表而不是抛异常。
    // Python 那边 pydantic 的 field_validator 逐条翻译到这里。
    std::vector<std::string> validate() const;
};
```

约束：**校验逻辑必须和 Python 的 validator 一一对应**，对拍时才能发现漏移植。

```
│   Vue 客户端 + Express          │   /bff/publish  平台投递
│                                 │   /bff/flow     八步进度判定
│                                 │   /bff/settings 引擎地址
└──────────────┬──────────────────┘
               │ HTTP，/api/* 原样转发
┌──────────────▼──────────────────┐
│ changji (单一 C++ 二进制)        │
│  ┌───────────────────────────┐  │
│  │ http/     接口层            │  │
│  │ pipeline/ 编排 + 线程池     │  │
│  │ stages/   六个阶段          │  │
│  │ models/   数据结构 + 校验   │  │
│  └───────────────────────────┘  │
│  ┌───────────────────────────┐  │
│  │ 链接: sd.cpp / llama.cpp   │  │
│  │       （统一的 ggml）       │  │
│  │ 子进程: ffmpeg             │  │
│  └───────────────────────────┘  │
└──────────────┬──────────────────┘
               │ HTTP（可选，装了才用）
        ┌──────▼──────┐
        │  ComfyUI    │  可选后端
        └─────────────┘
```

### 核心策略：接口契约兼容

标准：**字段名、嵌套结构、取值、状态码一致；key 顺序不管**。

"逐字节兼容"这个说法在早先版本里出现过，收回。nlohmann::json 默认底层是
`std::map`，key 会被排序，而 Python 的 dict 是插入序，逐字节本来就做不到；
换 `ordered_json` 能做到，但为此把每个结构体的字段声明顺序对着 pydantic
模型排一遍，收益不值。

在这个标准下：

- Node 前端零改动（破契约白名单里那几项除外）
- 改地址加换配置文件就能在两个后端之间切（配置为什么要换，见第六节）
- 任何时刻两个后端都能同时跑，同样的请求打过去比对响应
- 出问题随时切回去

不允许借重构之机顺手改接口。要改接口，等 Python 删掉之后再说。

### 破契约白名单

原本列了四项。**做完之后只剩一项。** 2026-09-08 逐项重新审过——
决策 4 把"用远端大模型"从过渡状态变成了长期形态之一，
另外三项的破契约理由随之不成立。

| 项 | 原计划 | 实际 |
|---|---|---|
| `GET /` | 返回一句纯文本 | ✅ **仍是破契约**，见下 |
| `/api/llm/providers` | 语义重定义 | ❌ 原样保留，不破 |
| `/api/llm/models` | 改成列本地 gguf | ❌ 改成**扩展**，不破 |
| `[llm]` 配置段 | 就地改造成模型路径 | ❌ 改成另开 `[models]` 段 |

#### 唯一真正的破契约：`GET /`

Python 那边返回 `page.py` 生成的一整页 HTML——那是删 Python 之前的
内置界面。两层架构下界面由 Node 提供，浏览器根本不会访问到 C++ 的根路径，
**会撞上它的只有直接开了后端端口的人**。给他们一句指路的话，
比返回 404 或者一个空页面有用：

```
场记 C++ 后端在跑。
这里只有接口，界面在 Node 那一层——默认 http://127.0.0.1:5174

体检： http://127.0.0.1:8080/api/doctor
```

**前端不用改**。这一项不影响任何前端代码。

#### 为什么另外三项不破了

三项是同一个原因：决策 4 定了"Pi 保留、模型文件走配置"，
而它的直接后果是——Pi 没有跑 14B 的内存，它只能打到局域网的 Windows
机器或者云端。**用远端大模型不是过渡状态，是长期形态之一。**

`/api/llm/providers`：那份"省得查文档"的地址清单照样有用，原样保留。
清单本身从 Python 的 `LLM_PROVIDERS` 生成（`llm_providers.inc.hpp`），
不是手抄的——十几家平台每家四个字段，手抄必然错，而且各家地址会变，
手抄的那份只会越来越旧且没有任何迹象提示它旧了。

`/api/llm/models`：**扩展不是替换**。远端有哪些模型照旧列，
另加一个 `local` 字段列本机的 gguf。加字段是向后兼容的——前端现在只读
`.models` 和 `.error`，多出来的它不看。原计划那样"改成列本地 gguf"
才是真的破契约：设置页那个下拉框会突然从"远端服务上的模型"变成
"本机文件"，而用户配的是远端服务。

`[llm]` 配置段：**保留 `[llm]` 不动，另开 `[models]` 段**。
就地改造会把"用远端"这条路堵死。现在两者语义分工清楚：

- `[llm]`——**远端**兼容 OpenAI 接口的服务（Ollama、云端）
- `[models].llm`——**进程内** llama.cpp 要加载的 GGUF 文件

这一项对 Python 的破契约程度不变：那边 `Settings` 是 `extra="forbid"`，
多一个段照样加载失败。但那只影响"拿 C++ 的配置文件去喂 Python"，
不影响前端。

#### 结论

**阶段 4 不需要任何前端改动。** 原来的完成判据里"设置页的模型选择改成
本地 gguf"这一条作废——设置页原样能用，本机模型列表是它可以选择性
利用的新信息，不是它必须适配的破坏性变更。

### 校验错误的消息文字不算契约

状态码和 body 的**形状**要一致，但 `detail` 里那句话的**文字**不比。

Python 那边 pydantic 的报错长这样：

```
改动不合法：1 validation error for Shot
duration_s
  Input should be less than or equal to 30 [type=less_than_equal, input_value=99.0, ...]
    For further information visit https://errors.pydantic.dev/2.13/v/less_than_equal
```

里面嵌着 pydantic 的版本号和文档 URL。在 C++ 里复刻既荒唐又会随上游版本
腐烂，而前端只是把这个字符串显示出来、不解析它。C++ 侧给的是
`改动不合法：duration_s 要在 0 到 30 秒之间，当前 99`——更短也更能照着做。

对拍语料里这类用例标了 `"compare": "shape"`，只比状态码加"detail 是个非空
字符串"。**这是有意的偏离，不是没对齐。**

另有一条相反方向的发现：`extra="forbid"` 的违规，FastAPI 回的是 **422 而不是
400**，而且 detail 是结构化数组 `[{type, loc, msg, input}]` 不是一句话。
那个**要照做**——状态码和嵌套结构都在契约里。第一版我写成 400，对拍抓到了。

`/api/doctor` 的 `checks` 数组内容**不算**契约。前端是泛化渲染的，只认
`can_run` 和 `name/level/detail/fix` 四个键；检查项本身按各自后端的实际
情况写（Python 那边叫 "Python"、"ComfyUI"、"hardware"，C++ 叫"运行时"、
"推理服务"、GPU，这是对的，不要为了对拍改回去）。

`/api/voices` 在阶段 6 之前返回空列表加一条说明——它依赖 ComfyUI 的
节点清单，而 comfy/ 的移植排在阶段 6。这是暂时状态，不进白名单。

### 一处有意不复刻的 Python bug：首帧种子每次重启都变

阶段 5 移植首帧时发现的。

`frames.py` 的 `_seed_for`：

```python
base = abs(hash("frame:" + shot.shot_id)) % (2**31)
return (base + shot.attempts * 6271) % (2**31)
```

**Python 的 str `hash()` 按进程随机化**（PYTHONHASHSEED 默认随机）。
实测同一个 shot_id 三次不同进程给出 1371092974 / 2100102585 / 1640920543。

后果是：**同一个镜头每次重启得到的是另一张图**。而用派生种子而不是随机
种子，全部的意义就是可复现——重跑一个不满意的镜头，结果要么是修好了
要么是没修好，不该是"换了一张"。用户改了提示词重跑，看到的变化里
混着种子变化，判断不了改动有没有起作用。

`attempts * 6271` 那个偏移是对的（每次重试换种子，否则重试等于把同一张图
再算一遍），只是基数不该是随机的。

C++ 侧用 SHA-1 前 4 字节，跨进程、跨机器、跨版本都一样。
**也不能用 `std::hash`**——那个的实现由标准库决定，换个编译器甚至换个
版本就变，和 Python 随机化的效果一样糟，只是变得慢一点。

### 一处有意不复刻的 Python bug：画质档位改了不生效

阶段 1 补 `POST /api/settings` 时发现的。

`web/server.py` 里有个 `_TIER_OVERRIDES` 字典，用户改草稿或成片档的
分辨率、步数时写进去。**但它只写不读**——全文件搜一遍，只有两处：
定义那一行，和写入那一行。

后果是：用户在设置页把草稿分辨率从 448 改成 512，接口回
`{"changed": ["draft_width"], "labels": ["草稿档宽"]}`，界面显示"已应用"，
而 `/api/hardware` 和后续渲染拿到的还是 448。**这个开关是在骗用户。**

C++ 侧让它真的生效（`config::Runtime::set_tier_override`）。仍然只在
进程内有效不写回配置——档位是按显存推出来的，写死在配置里等于把这台
机器的显存刻进项目，换台机器就不对了。

有意的偏离。复刻一个"点了没反应"的开关没有任何价值。

#### 顺带记一个我自己踩的坑

单元测试直接调 `runtime().profile()`，过了；实机验证时 `/api/hardware`
返回的还是老值。原因是那个路由走 `get_hardware(settings)`，
而那个函数**自己 detect() 了一遍**，把覆盖绕过去了。

教训是：改一个"全局状态"的时候，光测状态变没变不够，
要测**所有读它的路径**都读到了新值。这里加了带 profile 参数的重载，
由路由层显式传 `runtime().profile()`。

### 一处有意不复刻的 Python bug：`probe()` 撞上 "N/A" 会崩（阶段 7 发现）

移植 `assembly/ffmpeg.py` 时，给 ffprobe 的输出做对拍语料，
拿一个 `nb_frames` 是 `"N/A"` 的样本喂进去，**Python 直接抛
`ValueError: invalid literal for int() with base 10: 'N/A'`。**

```python
frames=int(video.get("nb_frames") or 0),
```

`or 0` 只挡得住 `None` 和空串，挡不住 `"N/A"`——而 **ffprobe 对 mkv 和
没有索引的流就是这么给的**，那不是异常情况。也就是说 `probe()` 探测一个
正常的 mkv 会直接崩，而它在闸门和装配两条路上都被调用。

`duration` 那几个字段走的是 `_to_float`，有 try/except，所以没事；
唯一漏网的是 `nb_frames` 这个 `int()`。

C++ 侧统一走 `to_double`（解析不了返回 0），所以这条路不复刻。
语料里那个样本记的是 `python_raises` 而不是期望值，用例钉的是
"C++ 不抛，而且别的字段照常解出来"。

### 一处有意不复刻的 Python bug：`/api/bible` 的 500

阶段 4 移植角色圣经时对拍抓到的。

`bible.py` 的 `_parse` 里调 `_extract_json`，而那个函数是从
`storyboard.py` import 的，抛的是 **`StoryboardError`** 不是 `BibleError`。
`/api/bible` 只 `except BibleError`，于是这个异常一路穿到最外面变成
**500 Internal Server Error**。

触发条件是"模型返回的东西里找不到合法 JSON"——这恰恰是弱模型最常见的
失败方式。用户本该看到那句「大模型输出里找不到合法 JSON：……」，
实际看到的是一个没有任何信息的 500。

C++ 侧统一抛 `BibleError`，也就是 **400 带上原始输出的前 400 字**。

这是**有意的偏离**。严格按契约应该复刻 500，但那等于专门写代码去重现一个
bug，而且重现的是"出错时不告诉用户哪里错了"这种最不该保留的行为。

对拍语料 `stage_bible.json` 的 `parse_failures` 里记着每条的
`python_error` 和 `python_http_status`，测试里有一条断言专门检查
"语料里还有 500 这条"——哪天 Python 侧修好了，那条断言会失败，
提醒把这一节从方案里删掉。

顺带一提，这个 bug 在 Python 侧是一行的事：`_parse` 里把
`_extract_json` 包进 `try/except StoryboardError` 再转成 `BibleError`。
要不要在删 Python 之前先修，取决于现在这套还要跑多久。

### WebSocket：增量，不是替换

**REST 接口原样保留，WebSocket 是加在旁边的第二条通道。**

这样契约兼容的策略才不会破：Node 前端可以先不动（继续轮询），等 C++
后端稳定后再改成订阅 WebSocket。两种方式并存，互为退路。

推送的理由是现有代码里已经论证过的——[comfy/client.py](../src/changji/comfy/client.py)
开头写着：*"用 WebSocket 监听进度而不是轮询历史接口，因为成片档一个镜头
要跑好几分钟，轮询既慢又容易漏掉中间状态。"* sd.cpp 的采样循环有逐步回调，
能推「第 12/30 步」这种真实时进度，轮询拿不到。

#### 消息格式

服务端下行，一律 JSON，带 `type` 和 `job_id`：

```json
{"type": "progress", "job_id": "...", "stage": "render",
 "shot_id": "S03", "step": 12, "total": 30}
{"type": "stage",    "job_id": "...", "stage": "audio", "status": "started"}
{"type": "log",      "job_id": "...", "level": "warn", "text": "..."}
{"type": "done",     "job_id": "...", "outputs": [...]}
{"type": "error",    "job_id": "...", "message": "..."}
```

客户端上行只有订阅控制：`{"type":"subscribe","job_id":"..."}` 和 `unsubscribe`。
**不通过 WebSocket 发业务指令**，那些走 REST。上行通道越窄越好。

#### 两条从 ComfyUI 那边学到的教训，必须带过来

1. **订阅按 job_id 记，不按连接记。** ComfyUI 按 clientId 记订阅，
   同一个 id 上并发跑两个任务，后连的会把先连的挤下线，先连的永远
   等不到完成消息。新设计里一个连接可订阅多个 job，一个 job 可被多个连接订阅，
   两者是多对多，不是一对一

2. **WebSocket 断线不是致命错误。** 服务端必须把每个 job 的最新状态
   留在内存里，REST 的 `GET /api/run` 仍然能查到完整状态。前端 WS 掉线
   就退回轮询，重连后先拉一次全量状态再续订阅。任务本身不受连接影响

#### 线程模型

```
Crow 事件循环线程   ──  HTTP 请求 + WebSocket 收发
工作线程池          ──  跑 job，同步写法
共享状态            ──  互斥量保护的 job 表 + 连接注册表
```

**不是一条工作线程。** [server.py](../src/changji/web/server.py) 现在有两个
独立的任务槽——`RunState` 跑流水线、`WriteState` 写整季，`WriteState` 的
注释明写着"跟跑流水线分开，两件事可以同时进行"。串行化会被对拍测出来。

用池加队列而不是两条固定线程：按 job 类型限流（流水线最多 1 个、写作
最多 1 个），以后想并发跑多集不用改架构。

**取消令牌按 job 挂，不按线程挂。** `/api/stop` 和 `/api/script/series/stop`
各自取消对应的 job。取消要能打断三个地方：sd.cpp 的采样回调、llama.cpp
的生成、ffmpeg 子进程。前两个的中止接口在前置验证工程里一并确认——
如果 sd.cpp 的逐步回调没有中止返回值，采样中途就停不下来，这会影响
`/api/stop` 的对拍结果。

工作线程产生进度 → 写进 job 表 → 通知广播器 → 广播器在事件循环线程上
向订阅了该 job 的连接发送。

需要小心的两处：

- **连接生命周期**。广播时连接可能已经关闭。连接注册表的增删和遍历
  必须在同一把锁下，或者用 Crow 提供的连接句柄有效性检查
- **推送频率**。逐步回调每秒可能触发几十次，直接透传会把前端淹掉。
  加节流，最多每 200ms 推一次，并且**完成消息不受节流影响**

### 跨模型调度：显存的分配与回收

这一节是上面"真正只有单一二进制能做的两件事"的落地设计。

#### 问题

一集片子的四类模型，工作集大致是（Q4 量化、5B 视频模型这一档）：

| 阶段 | 模型 | 工作集 | 调用频次 |
|---|---|---|---|
| 剧本、分镜 | LLM 14B | ~9 GB | 一集一次 |
| 首帧 | 图像模型 | ~7 GB | 每镜一次 |
| 视频 | Wan 文本编码器 | ~6.7 GB | 每镜一次 |
| 视频 | Wan DiT | ~3 GB | 每镜一次，采样循环 |
| 视频 | Wan VAE | ~0.5 GB | 每镜一次 |
| 配音 | TTS | ~1 GB | 每句一次 |

全加起来 27 GB，开发机是 RTX 2060 **6 GB**。

sd.cpp 的分段执行解决的是**单个模型内部**装不下的问题。它解决不了
"LLM 和 Wan 同时驻留"——那是两个互不知情的库。

#### 设计

一个 `ModelScheduler`，管**槽位**而不是管张量。张量级的事交给 sd.cpp。

```
槽位          底层            驻留策略
LLM           llama.cpp       Ephemeral —— 一集用一次，用完整个放掉
Image         sd_ctx          Cached    —— 每镜都要，显存紧张才放
Video         sd_ctx          Cached    —— 同上，且优先级最高
TTS           待定            Ephemeral
```

对外只有一个 RAII 句柄：

```cpp
{
    auto lease = scheduler.acquire(Slot::Video);   // 需要时才加载
    lease->generate(...);                          // 用
}                                                  // 引用计数减一，不一定卸载
```

`acquire` 的语义：
1. 该槽已加载且引用计数 > 0 → 直接返回
2. 没加载 → 先算这个槽要多少显存；不够就按**优先级从低到高**卸载别的槽
3. 加载，引用计数加一

`Ephemeral` 的槽在最后一个 `lease` 析构时立刻卸载。`Cached` 的留着，
等下次显存不够时被驱逐。

#### 三条不显然的决定

**一、预算不是"显卡有多少"，是"给推理留多少"。**

`--max-vram` 要减去驱动上下文和别的程序占的。这个数从 `HardwareProfile`
探测出的可用显存出发，再留一个安全边际——探测值是瞬时的，别的程序随时可能
再吃掉一块。宁可保守：多分段只是慢，估高了是 OOM 直接崩。

**二、卸载不是免费的，所以要按阶段批量调度而不是按镜头。**

跑一集的正确顺序是"四十个镜头的首帧全出完，再统一出视频"，
不是"一个镜头出首帧再出视频，然后下一个"。后者每镜要换两次模型，
四十镜就是八十次换入换出，全花在磁盘 IO 上。

这一条直接决定了流水线的循环结构，不是加个调度器就能补的——
**阶段 5 的流水线要按阶段分批，不能按镜头串行**。

**三、这一层不做张量级的事。**

不要在 changji 里实现 LRU 驱逐张量、异步预取这些——sd.cpp 已经有了，
而且它有的信息（图切在哪、哪些张量下一段要用）这一层拿不到。
这一层只回答"哪个模型现在该在显存里"。

#### 验证

这个调度器不依赖 sd.cpp 就能测：加载和卸载函数注入，测的是策略——
引用计数、驱逐顺序、预算够不够的判断。**接 sd.cpp 之前先把策略测死**，
因为接上之后每个用例都要几分钟，没法反复跑。

### 模型文件走配置

Python 侧没有这一节——那边模型是 ComfyUI 自己管的，工作流 JSON 里按名字
引用，changji 根本不知道文件在哪。进程内推理之后没有这一层了，
得自己说清楚每个模型是哪个文件。

```toml
[models]
dir = "~/models"                                  # 相对路径的基准
llm = "Qwen3-14B-Q4_K_M.gguf"                     # 剧本、分镜
video = "Wan2.2-TI2V-5B-Q4_K_M.gguf"              # 文生视频
video_vae = "Wan2.2_VAE.safetensors"
video_text_encoder = "umt5-xxl-encoder-Q5_K_M.gguf"
image = "Qwen-Image-Edit-Q4_K_M.gguf"             # 首帧、图像编辑
```

四条设计决定，都对应一个具体的坑：

**没有默认文件名。** 每一项都得自己填。同一个二进制要在配置差很多的机器上
跑——24G 显存的机器和 8G 内存的树莓派，能装下的量化档完全不同。
猜一个默认值只会让人以为配好了，然后在加载模型时才炸。

**路径三分支**：绝对路径原样用（多机共享网络盘），相对路径接在 `dir` 后面，
`~` 会展开。`dir` 留空时回落到项目库下的 `models/`——模型和项目放一起，
整个 workspace 拷到另一台机器就能直接跑，不用记得单独拷模型。

**不做存在性校验。** `validate()` 什么都不查。模型动辄好几个 G，
装好程序还没下模型是常态；那时候如果配置加载直接失败，用户连界面都进不去，
也就没法在界面里看到到底缺哪个文件。存在性检查在 doctor 里，
报警告，程序照常起来。一项都没配是 OK 不是 WARN——走 ComfyUI 那条路的
用户根本不需要这一节，给他们报警告等于让报告长期挂一条永远不处理的黄字，
有常驻噪音之后真正的警告就没人看了。

**`/api/settings` 不返回它。** 那个接口回的是精选子集不是全量 dump，
不加就不破契约。等前端真要做模型选择器时再作为白名单项加。

环境变量前缀照旧：`CHANGJI_MODELS_DIR`、`CHANGJI_MODELS_LLM` 等。
容器里最常用的是 `MODELS_DIR`——镜像不打包模型，挂个卷进来指过去。

### `/ws` 从来没能送出过一条任务消息（2026-09-08 修）

阶段 4 判据里「WS 能实时看到阶段推进」从来没被验过。补了一层对拍
（连 `/ws`、订阅、起任务、收消息），**第一次跑就把真相验出来了**：

**`job_id` 从来不从任何接口暴露出去。** `POST /api/run` 回
`{started, queue}`（Python 也是这两个字段，加一个就破契约），
`GET /api/run` 那十几个字段里没有它，`Event` 里也没有。
而它是 `mt19937_64{random_device{}}` 随机生成的。
`Hub::subscribe` 要的正是这个 id，`broadcast` 又只发给订了该 id 的连接
——**所以任何客户端都永远订不上任何任务**。

配套的三件事也都指向"这条路没人走过"：Python 侧**根本没有 WebSocket**
（`web/server.py` 开头写明「不用 WebSocket，因为轮询够了，少一层
连接管理就少一类掉线问题」）；webapp 从来没开过 socket（每 1200ms
轮询 `/api/run`）；`broadcast_all` 零调用。

修法是让 `subscribe` 也认**任务类别**（`"run"` / `"write"`）。
补 `job_id` 到 REST 是另一条路，但那样前端得先打一次 GET 才能订阅，
而 WebSocket 本来就是来替掉那次轮询的；而且比 Python 多一个字段
就是一处破契约。按类订阅两样都不占，还能**在任务开始之前订上**。

然后把 webapp 接上了：Node 那层加中转（浏览器连同源的 `/api/ws`，
中转再去连引擎——引擎地址可配，发到前端去的话填错一次用户就打不开
改回来的界面了），两个 store 都改成"全量打底 + 增量推送 + 收尾再拉
一次全量"。轮询留着当兜底和补全：**推上来的是增量**，
`outputs` / `queue_total` / `episodes` 只有全量里有。

两个字段映射的坑，各钉了一条用例：流水线那边推的 `step` 对应快照的
`current`，写作那边对应 `done`。照抄另一边的映射，进度条一直是 0——
而那和"任务卡住"在界面上是同一个样子。

### 哪些测试真的和 Python 比过（2026-09-08）

### 出首帧会把整个进程崩掉（2026-09-08 修）

权重下齐之后跑阶段 5 的判据，第一次真的调 sd.cpp 出首帧，
**整个进程没了**——异常码 `0xc0000094`（整数除零），HTTP 服务连同
正在跑的那一集一起消失，日志里一个字都没有，只有 Windows 事件日志里
一条 Application Error。

原因是一段**故意写成那样**的代码。`sd_image.cpp` 里注释写着：

> 出首帧优先用图像模型……没配就退回视频模型出单帧——
> 这个选择和 Python 的 build_backend 是同一个判断。

那个判断**在 Python 那边成立，在这边不成立**。Python 走 ComfyUI 工作流，
把 `Wan22ImageToVideoLatent` 的 `length` 设成 1 就出单帧；
而 sd.cpp 的 C 接口里 **`sd_img_gen_params_t` 根本没有 `video_frames`
字段**（只有 `sd_vid_gen_params_t` 有），压根没法告诉 `generate_image`
要出几帧。Wan 这类视频模型进去之后帧数是 0，除下去就崩了。

**教训不是"别抄 Python"，是"抄行为要连 API 形状一起看"。**
两边的判断逻辑一模一样，坏就坏在下游接口的能力不一样，
而那一点在对拍里看不见——对拍比的是响应，比不到"这条配置会不会崩"。

触发它的配置一点都不刁钻：配置模板里 `[models]` 那几项写着"必须自己填"，
填了 `video` 没填 `image` 是最顺手的做法。

修法是拦下来给一句说得清的话（缺什么、为什么不能拿现有的顶、两条出路）。
**一次崩溃比一个错误严重得多**——它会把正在跑的整集连同服务一起带走。

判断拆进了 `sd_model_problem()`，放在 `#ifdef CHANGJI_HAVE_SD` **外面**：
测试目标编的是没链 sd.cpp 那一支，写在 `#ifdef` 里面就测不到。
和 `doctor/needs.hpp` 是同一个套路。四条用例，
其中一条钉"两个都没配时**不许**提顶替"——没有视频模型可顶，
说了只会让人困惑。

真要支持这条退路，得让出首帧也走 `generate_video` 出 1 帧再取第 0 张。
没做，记在这儿。

### 第二句台词配不出来——`--say` 结构上发现不了的那类 bug（2026-09-08 修）

`--say` 过了之后我把阶段 9 标成了 ✅。**那个判据是不够的。**

拿真流水线跑配音（`stages: ["audio"]`，两句台词），第一句好好的，
第二句必挂：`进程内配音失败：跑提示词时失败`。重启服务之后，
那一句自己又能出。

**隔离实验**是关键：重启进程 → 同一句话成功。这就把
「状态在两次调用之间没清」和「这句话本身有问题」分开了——
两者的修法完全不同。

原因：`inp.seq_id = 0` 每次都用同一个序列，而 `LlamaTts` 实例在整条
流水线上是**复用的**（模型 1 GB 出头，每句重载一遍不现实，
头文件里写着这一点）。KV 缓存不清的话，第二句的 token 接在第一句
后面，上下文越堆越长，`step_prompt` 直接返回负数。

修法是每次合成前 `llama_memory_clear(llama_get_memory(lctx), true)`。

**为什么 `--say` 发现不了：它建一次、用一次、进程就退了。**
真实用法是**顺序复用**同一个实例。头文件里"已知没验过：并发调用"
那一条其实指错了方向——破绽不在并发，在最普通的连续调用。

后果有多大：修之前，**任何一集里第一句之后的台词全部配不出来**，
而 523 条单元测试和 166 条对拍全是绿的。

这条是"实机判据"存在的最好理由。一个只跑一次的 CLI 判据，
验的是一条真实用法根本不会走的路径。

修完：一个进程里两句都出来了，都验过不是静音
（峰值 14032 / 5078，有声样本 76.6% / 76.1%）。

### 配置文件位置：值一样，取值的机制不一样（2026-09-08 记）

迁移期间两个后端**共用一份用户配置**——`check_template_compat.py` 整个
存在的前提就是这个。所以"两边算出来的位置一不一样"是承重的一条。

值是一样的：两边都给 `%LOCALAPPDATA%/changji/config.toml`，
项目级都是 `<项目>/changji.toml`，合并顺序也一样（先用户后项目）。

**但取值的机制根本不同**：

    Python  platformdirs → Windows 已知文件夹 API（ctypes）
    C++     直接读 LOCALAPPDATA 环境变量

实测：把 `LOCALAPPDATA` 设成别的值，platformdirs 的 env 版函数确实跟着变，
**但它实际调的是 ctypes 那版**，回的还是原来的路径。也就是
**Python 根本不看这个环境变量，而 C++ 只看它**。

今天一致纯属这台机器上两者恰好相同。会分叉的情形：

- `LOCALAPPDATA` 被改过（CI、沙箱、`set LOCALAPPDATA=...`）：
  **C++ 跟着走，Python 不跟**，两边读的就是两个文件
- 没设：C++ 退回 `home/AppData/Local`，Python 还是问 API；
  企业环境配了文件夹重定向的话这两个不一样

后果是**用户改了配置，一个后端看得见另一个看不见**——而且两边都不会
报错，只会表现为"改了没生效"。

**没改成一样**：让 C++ 也去调已知文件夹 API 要引 shell32，
而这个分叉只在迁移期间有意义（阶段 8 之后 Python 没了，C++ 怎么算就是
定义）。记下来，并且用例两头都钉：默认环境下两边一致、
以及"C++ 认这个环境变量"这个行为本身。

### 首帧阶段的状态变化：失败时 status 必须不动（2026-09-08）

这一层逻辑不多，但**每一条都写在镜头状态上**，而状态是后面每个阶段的输入：

    成功：status → frame_done，frame_path 填相对路径
    失败：**attempts 加一，status 不动**

两半都要紧，而且错了都不报错：

- `attempts` 是闸门的重试计数。加错了要么永远重试，要么第一次就判超限降级。
- `status` 不动，这一镜下一轮才会被再捡起来。改成推到别的状态它就被跳过，
  表现是"那一镜永远没有首帧"，而日志里只剩一条早就滚掉的失败。

补了五条语料（全成功 / 全失败 / 中间失败 / 第一个失败 / 单镜），
比 outcome 和跑完之后的镜头状态。一条不差。

⚠️ **一处两边不一样，语料够不着**：Python 只捕
`(FrameError, RenderError)`，**C++ 捕的是 `std::exception`**。
渲染器抛别的类型时，Python 让它穿出去（整个阶段中断），
C++ 算成"这一镜失败"接着跑。

哪个对不好说：C++ 更能扛，但也更会**把渲染器里的 bug 说成"这一镜失败"**。
今天那个 sd.cpp 的除零是直接崩进程、连 catch 都没走到，
所以这条差异当时没起作用。语料只喂两边都会捕的错误——
喂别的就不是在比同一件事了。

写这条用例时被这个差异绊了一下：第一版我抛的是 `stages::FrameError`，
而 **C++ 侧根本没有这个类型**——它捕 `std::exception`，
所以没必要定义专门的异常。

### 镜像换成 C++ 之后**并没有小一个数量级**（2026-09-08）

阶段 8 清单第 3 条写着"两个都要重写成拷一个二进制进去——这一步反而是收益：
镜像会小一个数量级"。做完了，**那句话是错的**，把真实数字记下来。

`Dockerfile.cpp` 建出来 **942 MB**。拆开看：

| | 大小 |
|---|---|
| 二进制本身 | **6.1 MB** |
| apt 那一层（ffmpeg + 思源黑体 + curl） | **568 MB** |
| debian-slim 底座 | 约 75 MB |

单看二进制确实小得离谱——6 MB 换掉一整个 Python 解释器加依赖。
**但镜像的大头根本不是它**：ffmpeg 和中文字体两边都要，
换不换语言都得带着。

apt 那 568 MB 里最大的几个：

  - `libllvm15` **114 MB**——`libgl1-mesa-dri` 依赖它，
    而那个是 `libglx-mesa0` 拖进来的，链子的源头是 ffmpeg 的 OpenGL 输出。
    **这个容器一次都不会用到 OpenGL**，纯是白带。
  - `fonts-noto-cjk` 91 MB——中文字幕烧录必须，省不掉
  - `libicu72` 36 MB、`libflite1` 27 MB（语音合成，ffmpeg 的）、`libmfx1` 27 MB

真想把镜像做小，该动的是 ffmpeg 那条依赖链（换静态构建的 ffmpeg，
或者只带用得上的那几个 codec），不是换实现语言。这条留给以后。

⚠️ **没能和 Python 镜像直接量着比**：拉 `python:3.12-slim-bookworm` 时
registry 断流（CloudFront EOF，这台机器的网络本来就不稳）。
所以上面那句"并没有小一个数量级"是**按构成推的，不是量出来的**——
两个镜像都要 ffmpeg 和思源黑体，而那两样就占了大头。
真要一个准数，等网络好的时候把 `Dockerfile` 也建一次。

**别的都验过了，不是只编过。** 容器 healthy，`/api/health` 200，
日志里中文不乱码，`/api/doctor` 报 Linux x86_64、找得到 `/usr/bin/ffmpeg`、
30 个 Noto 字体，而且照实说"没链 ggml""进程内配音没编进来"。
`/api/connections` 的 `env_locked` 里有 `models_engine`，
界面上那一项会显示成锁着的。

**为什么这一环特别要紧。** 每条字幕的起止时间来自
`line.actual_duration_s`——配音阶段量出来、写回台词的那个数

三处特别容易抄歪，语料专门覆盖，**牙口三处都验过且都是这条语料报的错**：

  - **不出字幕的台词照样推进游标**：空文本或时长为 0 不出 cue，
    但后面那句的起点仍然要往后挪。写成 `continue` 会让后面所有字幕提前。

导语料时又差点踩上那个老坑：第一版只记了排完之后的样子，
而输入的台词**从 cues 反推不出来**——"空文本不出字幕""时长 0 不出字幕"
这几条正是被测的行为，拿 cues 当输入等于把被测的那一步当成前提。

### 一个还原脚本的坑：文本模式读写会把整个文件的换行换掉（2026-09-08）

这一轮验牙口的套路是"改一处 → 编译 → 跑测试 → `finally` 还原"。
还原用的是 `io.open(p, encoding='utf-8')` 读、`newline=''` 写。
**读是文本模式，CRLF 会被规成 `\n`；写又不还原**，
于是一个 CRLF 的文件被整个改成 LF。

`pipeline.py` 上撞到了：609 行的文件，`git diff --stat` 显示
**609 insertions, 609 deletions**——看起来像一次大改，实际一个字符没变。
之前几次都没撞上纯属运气：那几个 C++ 文件本来就是 LF。

危险在于**它看起来像真改动**。要是当时没细看，diff 里那 1218 行会被
当成"改得挺多"混进提交。以后还原脚本一律用二进制读写，让字节原样回去。
（这次没造成损失：每次跑完都对过 `git diff --stat`，也确认了树是干净的。）

### ComfyUI 客户端：挑哪张图靠的是插入顺序（2026-09-08）

`comfy/workflow.py` 那一半早就有语料（工作流 JSON 逐块比），
`comfy/client.py` 一直没有——`contract_audit.py` 把
`test_comfy_client.cpp` 列在「两边都有、又只钉了意图」那一类里。
补了 `comfy_client.json`，32 条，覆盖四个能脱开网络跑的纯函数。

**最要紧的是 `first_file()`。** `outputs` 是「节点 id -> {images:[...]}」，
`files()` 把各节点的摊平，`first_file()` 取第一个。
也就是说**哪个节点排在前面，决定了成片用哪张图**。

Python 那边是 dict，走插入顺序（服务端 history JSON 里的顺序）。
C++ 用 `nlohmann::ordered_json`，也是插入顺序——**这是有意选的**。
可要是哪天有人顺手换成 `nlohmann::json`，它按键名字典序排，
`"10"` 就跑到 `"9"` 前面，`first_file()` 换一张图**而且一声不吭**：
文件在、格式对、流程全绿，只是画面不对。
语料专挑插入序和字典序相反的节点 id，**正反各一条**——
只有一条方向的话，"跟的是插入序"和"碰巧一样"分不开。
验过：把 `files()` 改成按键名排序再遍历，这份语料抓得到。

顺带钉住一条以前只写在头文件注释里、没人去问过 Python 的事：
**视频节点也把结果放在 `images` 键下**，带 `animated` 标记。
按 `"videos"` 找一个都找不到。

导语料时又撞出两处两边不一样，都是 C++ 有意做得更稳，都标在语料里
（`divergent` 字段），C++ 侧钉自己的行为，不拿 Python 的值当期望：

**一、`images` 不是数组的时候。** Python 的 `files()` 是
`out.extend(node_out.get(kind, []))`——喂个字符串进去它**按字符摊平**。
实测 `{"images": "坏掉的"}` 得到 `files() == ['坏','掉','的']`，
`first_file() == '坏'`：一个字符串，而调用方等的是带 `filename` 的字典。
于是炸在下游（`'str' object has no attribute 'get'`），
报错指向的地方离真正的原因隔了好几层。
C++ 判 `is_array()`，不是数组就跳过，`first_file()` 回 `nullopt`，
调用方当成"没有产出文件"正常报错。

**二、`execution_error` 里缺 `node_type` 的时候。** Python 是
`f"节点 {detail.get('node_type')} 执行失败：..."`，缺字段时 `None`
被 f-string 直接渲染进去，用户看到"**节点 None 执行失败**"
——一个中文句子里夹着 Python 的 `None`。
C++ 用 `str_or(detail, "node_type", "?")`，渲染成"节点 ?"。
两边都没信息，但 `?` 不会让人以为有个叫 None 的节点。

还有一件工具上的事：`contract_audit.py` 以前只打两个桶
（比过 / 只钉意图），**哪些"只钉意图"是真缺口，一直在我脑子里**——
跨会话必然走样，这一轮就发现我记的数和实际对不上。
现在免责名单连理由写进脚本，还会反过来提醒哪条已经不在"只钉意图"里、
该从表里删掉（补了语料之后不删，那张表会慢慢变成一份过期的免责声明）。
真待办打印在报告末尾，现在剩 1 条：`test_episode.cpp`。

### 配音阶段：一镜配音失败，Python 会把整集废掉（2026-09-08）

给 `stages/audio.cpp` 补语料（`audio_stage.json`，6 条）时挖出两处不一样。

要紧的是**时长回写**。`actual_duration_s` 是后面所有环节的输入——

**一、状态推进在不同的层**——不是行为差异，但差点让语料比错边界。

只比 `run`，Python 那边全是 `planned`，比的就不是下游真正读的东西。

**二、失败之后的样子，两边根本不是一个形状**（实测，不是读出来的）：

  - Python 的 run 是 `asyncio.gather(...)`，**没带 `return_exceptions`**。
    一镜抛错整个阶段就断，异常穿到 pipeline，
    那句 `for shot in todo: shot.status = AUDIO_DONE` 压根不执行。
    三镜、第二镜抛错的实测结果：抛 `RuntimeError`，**第三镜没跑**，
    **三镜全停在 `planned`**——连已经配好的第一镜也没推进，
    而它的 `actual_duration_s` 已经写进去了。
    下游按 `AUDIO_DONE` 挑镜头，于是**整集的配音白跑**，
    重跑一遍还是从头配。
  - C++ 逐镜 try/catch：失败那镜停在 `PLANNED`，其余照推 `AUDIO_DONE`，
    整条继续跑。重跑只补失败那一镜。

**C++ 这边是有意做得更稳**，和上面首帧阶段那处差异同一个形状。
语料**不覆盖失败**——两边形状都不一样，喂进去比不出东西来，
只会逼着我把其中一边的行为写进期望值里假装是契约。

### frames_for 的取偶：一个抄歪了也不报错的地方（2026-09-08）

帧数换算这段藏着一个很容易抄歪的地方：

    raw = int(round(duration_s * fps))
    n   = max(1, round((raw - 1) / 4))

Python 的 `round()` 是**四舍六入五取偶**，不是学校教的四舍五入。
`round(2.5)` 是 **2** 不是 3。而 `(raw-1)/4` 落在 .5 上一点都不少见——
`raw = 4x+3` 全都是，raw=11 就是 2.5：取偶给 **9 帧**，
四舍五入给 **13 帧**。

**抄歪了不会报错。** 4n+1 是 Wan 的硬要求，给别的数它自己截，
而截在哪儿不告诉你。表现是"出来的片比预期短一点"，
和"模型没跟上运动描述"混在一起，几乎不可能联想到是这个换算。

C++ 那边本来就用 `std::nearbyint`（默认取偶）对齐了——**有人想过这件事**。
缺的是「有东西盯着它别再变回去」：原来的用例只有三个手写期望值
（2.0→49、3.0→73），那是"我们以为应该是多少"，不是"Python 给多少"。

补了 74 条语料，专挑 .5 边界和 121 帧的上限截断。
**验过牙齿**：把 `nearbyint` 换成 `std::round`（最顺手会写成的那个），
当场挂。

另加一条**不依赖 Python 的**：每个结果都得满足 4n+1、≥5、≤上限。
两边一起抄错的话，比对那条照样绿，这条不会——**语料自己证明不了自己**。

### 一处构建 bug：钉的 httplib 版本从来没生效过（阶段 6 发现）

写 ComfyUI 的 multipart 上传时编不过，追下去发现的。

sd.cpp 把自己的 `thirdparty` 目录作为 INTERFACE 包含目录导出，那里面有
一份 `httplib.h`（0.28.0）。而 `httplib::httplib` 的头文件是以 **SYSTEM**
身份进来的（MSVC 上是 `-external:I`），**SYSTEM 目录永远排在普通 `-I` 之后**
——所以只要它是 SYSTEM，sd.cpp 那份就必赢。

后果：从链上 sd.cpp 那天起，`llm/client_http.cpp` 和 `doctor/doctor.cpp`
编的一直是 0.28.0，而不是 CMakeLists 里钉的 0.15.3。两边碰巧 API 兼容，
所以**从来没报过错**。

**一个版本号写在构建脚本里、实际编的是另一个版本，比编不过更危险**：
升级依赖时看着改了其实没改；照着 0.15.3 的文档写代码，跑的是 0.28.0。

修法：清掉 httplib 的 `INTERFACE_SYSTEM_INCLUDE_DIRECTORIES` 让它变成普通
`-I`，再 `BEFORE` 排到最前面；加 `util/httplib.hpp` 包一层把警告按下去，
用到它的三个文件统一走它。sd.cpp 的 `thirdparty` 里还有一份 `json.hpp`，
我们一律写 `<nlohmann/json.hpp>` 所以没撞上，但 stb 的两个头也改成了
`<thirdparty/stb_image.h>`，路径写全，不靠"谁先谁后"。

**这一条要推广成一条规则**：凡是两个依赖都 vendor 了同一个库的头文件，
就不能靠包含顺序碰运气。后面链 llama.cpp 时同样的事会再来一次
（它也 vendor 了自己的一套第三方头）。

### 一个 Crow 的坑：422 被静默改写成 500（对拍抓出来的）

**Crow 1.2.0 的状态码表里没有 422。** 遇到不认识的码它会打一句警告然后
把响应改成 500：

```cpp
if (!statusCodes.count(res.code)) { CROW_LOG_WARNING << ...; res.code = 500; }
```

后果：**所有 pydantic 风格的校验错误在 C++ 侧都是以 500 发出去的**，
而 body 是对的。前端按状态码分流的话，一个"表单填错了"会被当成"服务端挂了"。
缺必填字段、`extra="forbid"` 违规、缺必填查询参数，全中。

**单元测试看不见这个 bug**：那边直接调处理函数、检查 `ApiResult.status`，
根本不经过 Crow 写响应那一步。是实时对拍抓出来的——Python 回 422，
C++ 回 500。

上游在 master 上修了（`WEBDAV_UNPROCESSABLE_ENTITY = 422`，表也挪进了
`http_response.h`），但**还没进任何一个发布版**（v1.2.1 也没有）。
与其为一行修复把 Crow 换到未发布的 master（那边 `onclose` 的签名也变了），
不如打一个补丁：`cpp/cmake/patch_crow_422.cmake`。换 Crow 版本时它会
**响亮地失败**——找不到锚点就 FATAL_ERROR，而不是默默不打补丁然后又回到 500。

顺带补上的：C++ 侧原先没有"必填查询参数"这个概念，缺 `episode_id` 时
直接进处理函数，回 404「没有剧集 」（末尾那个空格就是空参数）。
现在有 `unprocessable_query()`，八条有必填查询参数的 GET 都过它。
**"没给"和"给了个空的"是两回事**：`?path=` 在 FastAPI 那边是合法的空字符串，
会进处理函数然后回 400，语料里有一条专门测这个。

### 对拍的第一次实跑（2026-09-08）

两个后端同时起（Python 8124、C++ 8123），**27 条一致、0 条不同**。

录制模式（拿录好的响应比）9 条全过；实时模式把路由表里每一条无参数
GET 都打了一遍。

抓到的三个问题：上面那个 Crow 的 422、必填查询参数缺失的状态码，
以及一个**这个程序自己的** bug——Windows 上 `argv` 是 ANSI 的，
中文项目路径传进来变成乱码字节，七条只读接口全回 500，
而 curl 手打同一个地址是好的（现在收进了 `paths::utf8_args`）。

**三条有意的差异写成了带理由的忽略规则**，而且每次跑都打印出来：

| 忽略 | 为什么 |
|---|---|
| `/checks/**` | 体检项两边查的东西不同：C++ 没有 Python 解释器，多了 sd.cpp 后端和本地模型两项。形状一致，前端照渲染 |
| `/**/error` | 错误消息的文字不算契约。这里的差异来自各自的 HTTP 库 |
| `/local` | C++ 侧多出来的键：本地模型清单。Python 那边模型归 ComfyUI 管 |

**忽略项必须打印出来。** 一份"全部一致"的报告后面藏着十条忽略规则、
而看报告的人不知道——那比对拍不通过更危险。

**数据层对拍也通了**（`--data`，不需要起服务）：把 Python 写的那份golden
项目拷一份，C++ 读进来再写回去，逐字段比——project.json 和 assets.json
**零差异**，只忽略 `updated_at`（存盘刷新它正是它存在的意义）。

这是阶段 1 完成标志的端到端版本。单元测试逐个字段查过了，但那是挑着查的；
真正要保证的是"一个字段都没丢、一个字段都没多"——少一个字段的表现是
C++ 存过一次之后，Python 那边再打开就丢了那项设置。

**写接口对拍也通了**（`--post`）：按 endpoints_episodes.json 的语料重放，
**每个案例给两个后端各拷一份干净的项目**（共用一份的话前一个案例改过的
东西会成为后一个案例的输入，而且两边互相踩，那时候的"不一致"是自己造的）。
比完响应**再比改完之后的 project.json**——响应一样不代表做的事一样，
一个接口可以回 `{"saved": true}` 然后什么都没写。

**编辑接口也接上了**（改镜头 14 + 改资产 12 + 批量操作 14）。这三份语料
和别处不一样：**里面的 `body` 是期望的响应，不是请求体**，请求体要现拼，
而且三份拼法各不相同（`patch` / `extra` / `req`）。拼法集中在一张小适配表里，
不散成三段几乎一样的循环。

拼错了不会报错——两边都回 422，然后对拍说"一致"。**那是最坏的结果：
绿的，但什么都没验。** 所以每条都自查一遍"语料说该 200，两边却都 422"，
撞上就当差异报出来。

改完之后比的是**整份 project.json 和 assets.json**，不照抄语料里那个窄投影
（`shot_after` 只有一个镜头，`shots_after` 只有六个字段）——整份比更严，
而且不用在 C++ 里把投影逻辑重写一遍。

**`/api/media` 的 Range 那一层**（17 条）是阶段 3 完成标志里的
"成片能拖进度条"。这条路和别处都不一样：回的不是 JSON，
**响应头本身就是契约**（`Content-Range` 差一个字节浏览器的时间轴就错），
状态码有 206 和 416 两个别处不出现的值。

它抓到两处，都是前面七层结构上看不见的——**因为那七层只比 body，不比头**：

**一、语法不认识和起点越界被混成了一种。** 原来两种都回 416。
Python（Starlette 的 `FileResponse`）分得很细：`bytes=abc`、`items=0-9`
这类回 **400**，只有起点落在文件外才回 416。对浏览器来说这两个含义不同：
416 带着文件真实长度，意思是"照这个重来"；400 是"你的请求本身是坏的"。
改法是照抄 Starlette 的判定顺序——**顺序换了结果就会变**，
`bytes=5000-6000` 在越界和大小关系上都不合法，先查哪个决定了它回 416 还是 400。
最刁的一条是 `bytes=--5`：Python 的 `int("-5")` 合法，起点算成
`file_size+5`，看着像语法错，判定却是 416。

**二、每一个接口的 `Content-Type` 都多了 `; charset=utf-8`。**
FastAPI 发的是不带参数的 `application/json`。JSON 按 RFC 8259 本来就必须
是 UTF-8，这个参数在 `application/json` 上根本没注册，加了不算更对。
这个差异存在于**所有** JSON 接口上，前面 143 条一条都没看见——
它们比的是 body。

比完之后**把比响应头这件事补进了另外五个模式**（写接口、编辑、上传、
LLM、实时 GET）。只比 `Content-Type` 一个头：别的（Date、Server、
Connection）两边必然不同而且不是契约，`Content-Length` 会被 JSON 的键序
影响而键序明确不算契约。补完再跑，**没有新差异**——那处 charset 是唯一的一处。

这件事本身是个教训：**一个类别的差异，只要没有哪一层去比，就能一直绿着。**
143 条"全部一致"里藏着一个存在于每一个接口上的头差异，而报告不会提它，
因为没人问过。

一处**有意的偏差**，验而不跳过：多区间（`bytes=0-99,200-299`）Python 回
206 + `multipart/byteranges`，我们当没看见这个头、回整个文件 200。
不实现的理由是那个格式的分隔串是随机生成的，两侧永远逐字节对不上，
对拍也验不了它；而浏览器的 `<video>` 从不发多区间。
顺带修好了一处**代码和自己的注释打架**：`media.hpp` 上写着"多区间按整文件回"，
`server.cpp` 里却回的 416。

**上传接口是唯一一条不走 JSON 请求体的路**（9 条）。multipart 的解析、
文件名的落盘、格式白名单——全是另一套代码，前面那几层一个字节都没碰过它。
比完响应要**比 refs/ 目录本身**：这个接口的全部意义就是把文件写到那儿，
响应里的 `saved` 只是它自己声称写了。目录比的是名字**加字节数**——
只比名字的话，两边写出同名但内容长度不同的文件（多个 BOM、把二进制
当文本转了行）照样是绿的。

那条"换格式重传"的用例正是靠目录比才有意义：传 webp 进去，
原来那个同名 png 必须消失，而响应里看不出这件事。

**四层加起来 51 条一致、0 条不同**（数据层 2 + 录制 9 + 实时 GET 25 +
写接口 21，另有 4 条因为语料里有 prep 前置步骤没法通用重放而跳过）。

写接口那一轮抓到一处：**422 的 `input` 应该是整个请求体，不是 null。**
FastAPI 报缺字段时把父对象放进 `input`，前端拿它回显"你提交的是这些"。
写 null 的话那一栏是空的。七个文件里的 `need_str` 都改了。
**430 条单元测试一条都没拦住这个**——它们查的是 loc 和 type，没查 input。

**LLM 阶段对拍通了一半**（`--llm-work`）：`tools/fake_llm.py` 是一个
**会录音的假模型**——把收到的提示词原样记下来，再回一个事先放好的答案
（不消耗，两个后端能各拿一次）。对拍把它夹在中间，同一个请求让两边各发
一次，然后**逐字节比两条提示词**。

这是唯一能真正验证"提示词的拼接必须逐字一致"的办法。单元测试比的是
C++ 自己拼出来的串和录好的串——那验的是"C++ 没改过"，验不了
"Python 现在还是这么拼的"。

**两侧各起一个假模型**（`tools/duiping.ps1` 一条命令把四个进程起齐）。
共用一个的话，`/api/plan` 的两次调用会让第二个后端拿到第一个剩下的，
永远错位一条。

`endpoints_scripting.json` 23 条、`endpoints_planning.json` 20 条全过。

排队时**问几遍由语料说了算，不靠猜**：`/api/plan` 不是固定问两遍——
资产库里已经有角色时它跳过圣经那一步，只问分镜。按"固定两遍"排的话，
那些案例的第一次调用会拿到圣经的答案然后报"大模型没有返回镜头列表"，
而且**两边都这么报**，看起来像"一致地失败"，其实是对拍自己喂错了输入。
语料里的 `prompts` 是录制时真实发生的调用次数，拿它当准。
`clear_assets` 那个前置条件同理，不照做的话整条用例测的是别的东西。

**语料里记了 `cpp_status` 的那几条不再跳过，而是当成"有意不一样"来验**：
既检查 Python 还是那个老样子（那个 StoryboardError 漏透 bug 没被悄悄修好），
也检查 C++ 确实回了我们想要的码。跳过等于放弃检查。

这一轮抓到两处 pydantic 校验错误的形状差异：
**越界错误少了 `ctx`**（`{"le": 1800.0}`，前端靠它填出"最大 1800"这种
中文提示，没有它只能把英文的 msg 整句显示出来）；
**边界值用 `std::to_string` 印成了 "1800.000000"**，而 pydantic 是 "1800"。

八层加起来 **164 条一致、0 条不同、跳过 0 条**。

### 第九层：推理层接上了（2026-09-08）

推理层一直空着，理由记的是"要真跑一集"，而跑一集要模型和 ffmpeg。
配音这一段绕开了那两样：只跑 `stages: ["audio"]`。

**这一条我前后错了两次，两次都记下来。**

**第一次**：我以为"ComfyUI 连不上时两边都会退回估算后端（写等长静音 wav）"。
不是——两边都有内置的配音工作流（Python 的 `workflows_loader`、C++ 的
`bundled_workflows.inc.hpp`），估算后端只在**连工作流都没有**时才用得上。

**第二次**：看到两边行为不同，我写成了"Python 一失败就整体中止，
C++ 跳过失败继续跑"，当成一处待定的策略分歧，还把对拍标红了。**那也不对。**
真正的机制查清楚是：

- Python 的 `load_all` **上来就加载 video**（`required=True`），而
  `video.json` 是**界面版**的，转接口版要问服务端要 `/object_info`。于是
  **光是加载**就要 ComfyUI 活着——哪怕用户只点了 `stages: ["audio"]`，
  哪怕配音这一段根本不碰视频。
- C++ 在 `[models].engine = "sd"`（默认）时**在加载任何 ComfyUI 工作流之前
  就返回了**（`run_deps.cpp` 里 `if (engine != "comfy") return b;`）——
  它有进程内的 sd.cpp，出视频不需要 ComfyUI。

**所以两边跑的根本不是同一条路，而那正是这次重构的目的，不是契约 bug。**
直接逐字段比这一条没有意义。

教训是同一条：**看到差异先查机制，别急着给它安一个解释。** "策略分歧"
听起来合理，但它把一个具体的、可定位的原因（`load_all` 急加载界面版 video）
换成了一个模糊的、没法动手的说法，还顺带把对拍标红了一轮。

**修法不是给它安一个说法，是把两边放到同一条路上。** 查的时候发现
`[models]` 那一节**每个键都有环境变量，偏偏 `engine` 没有**——而它正是
"走进程内还是走 ComfyUI"那个开关，容器里和对拍时最需要临时翻的就是它。
补上 `CHANGJI_MODELS_ENGINE`（顺带补了漏掉的 `MODELS_TTS`、
`MODELS_TTS_DECODER`），`duiping.ps1` 给 C++ 那一侧设成 `comfy`，
两边就走同一条路了。

于是这一条从"有意不一样"改回**逐字段真比**：跑完的快照、`project.json`、
`audio/` 目录，全都一致。

⚠️ **但要说清楚它比的是什么。** 没起 ComfyUI 的时候两边都停在加载工作流
那一步，所以这一条验的是"**两边在同一处、以同样的方式停下**"，
**不是"配音出了声"**。对拍跑的时候会把这句话打出来，免得被误读。
要验真出声，得有 ComfyUI 活着，或者阶段 9 的进程内配音接上权重。

### 跳过等于放弃检查：那 4 条跳过是专门去挣掉的（2026-09-08）

### 阶段 6 的两个决定（2026-09-08）

**一、WebSocket 客户端自己写。**

项目里 WebSocket 有两个方向：Crow 做服务端（前端连过来看进度），
ComfyUI 那边我们是客户端。**Crow 只有服务端。** 为一个客户端再拉一个库
代价不小——Beast 要整个 Boost，websocketpp 停更多年且依赖旧版 asio，
而这两条都和"零运行时依赖 + 交叉编译到树莓派"直接冲突。

我们要的功能很窄：**收文本帧**。发只发一次握手，ping 只回不发，
不支持 wss（要 TLS 的部署走反向代理，那时候退回轮询）。
协议部分（握手串、帧编解码）抽成纯函数单独测死——那些错了不会崩，
只会"连不上"或者"收到乱码"，而在真实服务端上试错一次要几十秒。

**二、`/api/voices` 有意偏离 Python 一处。**

那边的 `list_voices` 把异常吞掉返回空列表，于是"ComfyUI 连不上"和
"一个音色都没装"回的是同一个空下拉框，用户没有任何线索。
C++ 侧连不上时回一句话。形状没变（前端本来就在读 `error` 字段，
角色页那段代码已经有了），所以这是纯增益，不算破契约。

## 六、对拍验证

Python 引擎保留的唯一目的：**当回归基准**。删除之前必须完成对拍。

### 对拍程序

纯 C++ 写，放在 `cpp/tests/compat/`。同时驱动两个后端，深比较响应。

pytest 那 5,781 行不直接复用，但里面积累的请求语料要留下来：写一个
用完即弃的 Python 脚本，把请求体和预期响应导出成 `cpp/tests/golden/` 下的
JSON，之后对拍程序纯 C++ 读这些文件。导出脚本是一次性的，不进仓库的
长期维护范围——这样"彻底去 Python"和"不丢掉三千多行测试里的边界情况"
两件事可以同时做到。

### 配置隔离

两个后端**不能**共用同一份用户全局配置。`[llm]` 段的字段在 C++ 侧要变，
而 Python 的 `Settings` 是 `extra="forbid"`，多一个键整份配置就加载失败；
`/api/settings` 又是可写接口，两边会互相覆盖。

对拍期两个后端各用 `--config` 指一份自己的配置，对拍程序负责把两份调成
等价。代价是"改一个地址就能切后端"变成"改地址加换配置文件"。

### 数据层对拍（阶段 1-3）

Python 和 C++ 读写同一批项目文件，逐字段比对。差异必须为零——字段顺序
无关的深比较、浮点数精度、空值处理。

**语料必须包含中文项目名、中文角色名、中文台词。** 项目目录现在就在
`E:\AI短剧\` 下，而 `std::filesystem` 在窄字符路径上的行为是这次移植
第一个会撞的坑（构建期的同类问题已经在 [cpp/README.md](../cpp/README.md)
里记过一次）。不专门造中文语料的话，会在阶段 1 的最后才发现。

### 接口层对拍（阶段 2-4）

两个后端同时启动在不同端口，同一组请求打过去比对响应体。破契约白名单里
那四项不参与对拍。

### LLM 阶段对拍（阶段 4）

LLM 输出不确定，不能直接对拍。做法：

1. 用 Python 跑一遍，把每次 LLM 的请求和响应录成 JSON 文件
2. C++ 侧接一个"回放模式"，读录制文件而不真的推理
3. 比对提示词拼接结果（必须逐字节相同）和后续解析结果

提示词拼接尤其要严：[render.py](../src/changji/stages/render.py) 里的分层顺序
（身份层 → 场景层 → 镜头层 → 风格层）不能变，顺序一改画面重心就变。

注意这里的"逐字节"是对**提示词字符串**说的，和第三节收回的那个"接口
逐字节兼容"是两回事。提示词是喂给模型的输入，差一个空格出图就不同。

### 推理层对拍（阶段 5）

不能要求逐像素相同——不同的实现、不同的量化格式必然有数值差异。
做法是固定种子生成同一个镜头，人工比对画质，重点看：

- 角色长相是否一致（这是整个项目的核心指标）
- 有无量化导致的色带、糊面、细节丢失
- 分块 VAE 解码有无可见接缝

## 六点五、多卡和多机怎么用起来

低配单卡（6 GB）、单机 8×48 GB、多台 8×48 GB——**这三种不是同一个设计的三种
配置，是三种不同的瓶颈**，各要一条不同的并行轴。把它们当成一件事调参数，
结果是三种上都不快。

### 先说清楚代码现在站在哪

| 事实 | 在哪 | 对多卡意味着什么 |
|---|---|---|
| `Scheduler` 只有**一个**全局显存预算 | `scheduler.hpp` 的 `budget_` / `set_budget` | 两张卡会被当成一个池子，调度决策全错 |
| `SlotSpec` **没有设备字段** | `scheduler.hpp:54` | 没法说"这个模型放卡 1" |
| `acquire(Slot)` 一种模型只有一个实例 | `scheduler.hpp:130` | 同种模型没法在两张卡上同时跑 |
| `detect_gpu` 只读 `nvidia-smi` 的**第一行** | `hardware.cpp:158` | 报的是卡 0 的显存。**这对档位是对的**（一个模型跑在一张卡上，画质上限由单卡决定），但系统完全不知道还有别的卡 |
| sd.cpp 的进度回调是**全局的** | `sd_image.cpp:66` 的 `ActiveGeneration` 单例 | **同进程内不能并发出图** |

最后一条是硬约束，而且代码里那句注释把假设写明了：

> "这意味着同一时刻只能跑一次生成——但那本来就是事实：**显卡只有一张**，
> 并发只会更慢。"

那句"显卡只有一张"是当时的前提。多卡的第一件事就是**承认它不再成立**，
而不是绕过它。`sd_set_progress_callback` 不带 ctx，这是上游的接口形状，
改不了；所以**同种模型的多实例只能靠多进程，不能靠多线程**。

### 三种规模，三种做法

**一、低配单卡（现状，6 GB）——瓶颈是显存。**
现在这套就是对的，不用改：一次只放一个模型、按阶段分批（四十个镜头的首帧
全出完再统一出视频，加载 2 次而不是 80 次）、权重常驻内存按需搬
（`params_backend = "cpu"`）。这一档的优化方向是**少换模型**，不是多并行。

**二、低配多卡（2~4 张小卡）——瓶颈还是显存，但可以不换模型了。**
一卡一模型钉住：图像常驻卡 0、视频常驻卡 1，谁也不用卸谁。
收益不是并行度，是**消灭反复加载**——这台机器上光加载 Wan 就要几分钟，
而按阶段分批本来就是为了绕开这件事。有两张卡就能连绕都不用绕。
顺带首帧和出视频可以真重叠：镜头 N 在卡 1 出视频时，N+1 在卡 0 出首帧。
需要的改动：`SlotSpec` 加设备字段，预算从一个数拆成每卡一份。

**三、单机 8×48 GB——瓶颈不再是显存，是吞吐。**
每个模型单卡都放得下还剩一半（Qwen-Image Q8 约 20 GB、Wan 5B fp16 约 10 GB、
14B 语言模型约 28 GB）。这时候再谈"该卸谁"没有意义，
`Scheduler` 那一层的驱逐逻辑基本退化成空转。
要的是**多少个镜头同时在跑**：八张卡起 8 个工作进程，每个进程一套完整模型，
镜头分派下去。四十个镜头本来就彼此独立，这是最自然的一条并行轴。
分派比例按阶段实测耗时调（出视频远比出首帧贵，卡的分配就不该一比一）。
**必须多进程**，原因见上面那条全局回调。

**四、多台 8×48 GB——变成一个分发问题，不再是显存问题。**
工作单元是**镜头**（或者"镜头的某个阶段"），协调者持有项目状态、
分发任务、收回产物。ComfyUI 那条路天生就是网络的（地址填哪台就用哪台），
所以横向扩展在那一侧几乎免费；进程内这条路要自己做一个协调者。
真正的难点不是算力调度，是**产物回传和项目文件的单一真相**——
八台机器各出各的镜头，project.json 谁来写。这一条没想清楚之前不要动手。

### 明确不做的

**单模型跨卡切分（tensor parallel）。** 这条流水线里每个模型单卡都放得下：
48 GB 上绰绰有余，6 GB 上靠 offload 也能跑。切分带来的是 PCIe 上的通信开销
（消费级卡没有 NVLink），在这种"模型放得下、只是想更快"的场景里，
通信开销通常比省下的时间还多。

**跨镜头攒批（batching）。** sd.cpp 和 Wan 都是一次出一张/一段，
攒批要模型侧支持，而收益在多进程之上很有限。

### 想清楚之后：一个决定定全局

**一卡一进程，协调者独占状态。** 这一句定了下面所有东西。

两个理由，都是代码里的事实，不是偏好：

1. **sd.cpp 的进度回调是全局的。** `sd_set_progress_callback` 不带 ctx，
   `sd_image.cpp` 只能用一个 `ActiveGeneration` 单例。同进程里两个生成
   同时跑，取消和进度会互相串。上游接口形状改不了。
2. **`Shot` 是就地改的，`project.json` 由 `run_episode` 的 `save()` 写。**
   八个线程各改各的镜头再一起存盘，最后一个写的赢——和 `audio.hpp` 里
   那条注释说的是同一件事。单一写者是这个项目已经选过的路。

进程切开之后，**每个工作进程就是现在这个单卡程序**：自己的 `Scheduler`、
自己的显存预算、自己的 `ActiveGeneration`。48 GB 上全驻留不换模型，
6 GB 上照样换——**`Scheduler` 一行不用改**。
上一版说要给 `SlotSpec` 加设备字段、预算按卡记账，**那是多余的**：
进程边界把"每卡一份预算"白送了。那两条从落地顺序里划掉。

### 工作单元：一镜一阶段

任务 = （剧集，镜头，阶段，输入）。输入是协调者算好的：提示词已经拼完、
档位已经算完、参考图路径、产物该落在哪。**工作进程不碰项目文件，
不做判断，只算。** 结果 = 产物路径 + 量到的数（配音时长之类）+ 错误。

**协调者的阶段循环从"逐镜算"变成"派出去、收回来"：**

```
挑出 todo（不变，pick() 那套）
派：每个镜头交给一个空闲的工作进程，同时在跑的不超过工作进程数
收：结果到一个应用一个——**在协调者的线程上顺序改 Shot、顺序 save()**
```

并行的是推理，不是状态改动。这一条守住了，单一写者不破。
`JobProgress::report` 本来就有锁（`jobs.cpp:117`），工作进程回传的逐步进度
从别的线程进来没问题；`Event` 自带 `shot_id`，八个镜头同时报"第 3/8 步"
分得开。

**种子不用动。** `frame_seed(shot_id, attempts)` 是 SHA-1 算的，
和跑在哪张卡、跑第几个没关系——并行出来的图和串行出来的一模一样。
这是能放心并行的前提，而它已经在了。

### 换实现的接缝已经存在

`FrameRenderer` / `VideoRenderer` 是 `std::function`（`frames.hpp:53`、
`render.hpp:81`），ComfyUI 那条路就是从这里换的实现——那本质上是
"把渲染交给另一个进程"。工作进程池是**同一个接缝上的第三种实现**，
和 ComfyUI 那种没有结构上的区别，只是另一头跑的是我们自己的 sd.cpp。
`run_deps.cpp` 按配置挑：空就进程内（现在的行为），有就用池。

### 派发模式：先做屏障，后做数据流

**屏障模式**：一个阶段的所有镜头做完，再开下一个阶段。现在的结构就是这样
（按阶段分批），只是每个阶段内部从串行变成 N 路并行。
8×48 上每一轮所有卡都忙，阶段边界上有点空转，可以接受；
单卡上退化成现在的样子，一行不用改。

**数据流模式**：一镜的首帧一出来，它的视频就可以开始。
这是"一卡钉一个模型"那种用法真正需要的——不然出视频那张卡在整个首帧
阶段都闲着。它要一个逐镜的状态机而不是逐阶段的循环，进度的 current/total
也变得不好定义。**先不做**，把它记成第二步。

两张小卡在屏障模式下也有收益：两个进程各做一半的镜头，换模型的次数
每个进程和原来一样，但吞吐翻倍。钉模型是再往上的优化。

### 各档拿到什么

| | 工作进程 | 每个进程 | 拿到的 |
|---|---|---|---|
| 单卡 6 GB | 0（进程内，现状） | 换模型 | 不变 |
| 2~4 张小卡 | 每卡一个 | 照样换模型 | 吞吐 ×N；数据流模式之后再钉模型 |
| 8×48 | 每卡一个 | 全驻留，不换 | 吞吐 ×8，且**没有一次模型加载是重复的** |

### 协议和配置（够用就行）

工作进程就是同一个二进制加 `--worker --gpu k --port p`，起一个只有四条路由的 Crow：

```
POST /task            {stage, shot, prompts, spec, dest, refs}  → 202 {id}
GET  /task/{id}       {state, step, steps, loading, result | error}
POST /task/{id}/cancel
GET  /health          {gpu, vram, resident, busy}
```

```toml
[workers]
# 空 = 进程内，现在的行为
# ["local:0", "local:1"] = 自动起本地工作进程，各绑一张卡
# ["http://某台:9001"]  = 连外部工作进程——这就是多机的雏形，同一个协议
endpoints = []
```

多机那一档在协议上和单机没有区别，差的只是**产物怎么回来**：单机共享
文件系统，工作进程直接往项目目录写；跨机要么挂共享盘，要么结果里带文件
内容回传。这一条定了之后多机才能动手，协议本身不用重设计。

### 顺带白送的一条：崩溃隔离

今天 `sd_image` 那个 0xc0000094 是**整个服务进程**没了——正在跑的一集、
WebSocket 连接、排队的任务全部丢掉。切成工作进程之后，一个进程崩了
协调者只看到"这一镜的连接断了"，记一次失败、按需重起那个进程、接着跑。
**这一条不需要多卡也值得做**，单卡起一个工作进程就有这个效果。

### 要改的地方，和不改的地方

改：
- `FrameStage::run` / `RenderStage::run`：循环体从"算"改成"派—收"，加并发上限
- 新增 `worker/`：工作进程的主循环和那四条路由；`worker_pool.cpp`：
  客户端那一侧，实现 `FrameRenderer` / `VideoRenderer` 签名
- `main.cpp`：`--worker --gpu --port`
- `HardwareProfile`：认识有几张卡（现在只读 `nvidia-smi` 第一行）。
  **档位仍按卡 0 算**，画质上限本来就由单卡决定；卡数只用来决定起几个
- `run_deps.cpp`：`[workers]` 非空就用池
- 界面：制作页从"一个进度条"变成"N 个同时在跑的镜头"

不改：
- `Scheduler`——每个进程一份，原样用
- `pick()` 和各阶段的入口状态
- 种子
- 配音、语言模型、装配——不是瓶颈，先留在协调者进程内

### 先验什么再动手

1. **工作进程绑卡到底怎么绑。** `CUDA_VISIBLE_DEVICES` 对 ggml 的 CUDA 后端
   管不管用、`nvidia-smi` 又不认它（要 `-i k`）。这一条不实测就写代码，
   八个进程全挤在卡 0 上，看起来在并行，实际在排队——而且不报错。
2. **一个工作进程同时被派两个任务时会怎样。** 应该拒绝（409）而不是排队，
   排队会让协调者的并发上限失效。
3. **协调者收结果那条线程和 `save()` 的顺序。** 两个结果同时到，得串起来。

配音 → 首帧 → 草稿 → 装配，全链路在 8×L20 上跑通。

| | |
|---|---|

配音阶段还按「台词一次装不下」把 sh007 拆成了 sh007_b，三镜都出了片——

#### 但八张卡里只用了一张，要说清楚

跑的时候显存是这样的：

    显存 11575 0 0 0 0 0 0 9003
          ↑卡0                ↑卡7（协调者配音）

**六个 worker 里只有一个在干活。** 不是绑卡失效——那个单独验过，两张卡
同时满载过。是因为**阶段循环还是逐镜串行的**：

    FrameStage::run / RenderStage::run 里仍然是
        for (shot : todo) { render(shot); }   ← 一次一个

池只是把"render 这一镜"换成了"派给某个 worker 并等它回来"，
**并发上限是 1**。方案「落地顺序」里的第 3 步（阶段循环改成派—收）还没做。

所以现在的状态是：**并行的能力验过了（八卡同跑、逐字节一致），
但流水线还没用上它。** 一集三镜串行跑完用了约 7 分钟，
真派开的话应该是一镜的时间。

这一条不改，8 卡机器的价值只体现在"每张卡都能独立跑"，
而不是"一集跑得更快"。下一步就是它。

#### 改完了，6 张卡 5.45 倍（2026-09-09）

阶段循环改成了派—收：派那一段多线程从一个原子下标领活，只跑渲染
（渲染器收的是 `const Shot&`，只读）；收那一段在调用线程上按镜头
原顺序改 `Shot`。写回集中在收，是因为存盘那份 project.json 只能有
一个写者——让线程各写各的，两个线程同时改同一批镜头时最后一个写的赢，
而且一声不吭。

同一批 12 镜草稿档，只改工作进程数：

| | 墙上时间 | 同时在忙的卡 | 失败 |
|---|---|---|---|
| 1 个工作进程 | **653.8 秒** | 最多 1 张（只有卡 0） | 0 |
| 6 个工作进程 | **120.0 秒** | 最多 6 张（卡 0～5） | 0 |

**5.45 倍，六卡效率 91%。** 掉的那 9% 是每镜都要等模型从内存搬进显存
（`params_backend = "cpu"`），那一段是各卡独立的，本来就摊不掉。

量这个数的路上错了两次，都记下来免得再犯：

**一、往项目目录里塞 changji.toml 换 endpoints，两轮读的其实是同一份
配置。** `run_deps` 用的是进程启动时的全局快照，不按项目重读；而
`main.cpp` 调 `load_settings()` 时压根没传项目目录。第一轮跑出
118 秒对 120 秒，我差点当成"并行没生效"。真正的换法是换整个
`XDG_CONFIG_HOME`。这件事本身是个 bug，已经补了 `--project`。

**二、拿显存峰值当"这张卡忙过"的证据。** 工作进程跑完不卸模型，
显存一直占着——上一轮的残留让下一轮看起来八张卡都在忙，
两轮都报"7 张卡忙过"。改成采 `utilization`，并且记**同一时刻**
有几张卡在忙的最大值，那才是并行度。

### 第一次整套流程：编剧 → 成片，以及它暴露的三件事（2026-09-09）

八张卡：0～5 六个工作进程，6 起 llama-server（Qwen3-14B Q4_K_M，
json_schema 出来的是干净 JSON，66 tok/s），7 协调者进程内配音。
`--help` 里承诺的"项目目录的 changji.toml"这次也真的接上了（`--project`，
以前 `main.cpp` 从没传过项目目录，那一支是死代码）。

**一、`vram_gb_override = 20`，不是 44。** 44 GB 那一档的成片是 1920×1088/30 步，
而 Wan 2.2 TI2V-5B 训练分辨率是 1280×704——超出去只会更慢（静态表估 908 秒
对 392 秒一镜）不会更好。20 GB 那一档的成片档正好是 1280×704。这个数只影响
档位表和 sd.cpp 的分段预算（实测峰值 14.9 GB，在 18 GB 预算之内），不影响
真正装了什么。

**二、14B 写不出 10 分钟的剧本。** 提示词是合同（和 Python 逐字节一样），
要的是"所有对白控制在 N 个字左右"——600 秒对应约 1700 字，模型给 450 字；
分镜配额要 600 秒，模型给 80 秒。开思考模式更差（50 秒）。没有截断（llama-server
`truncated = 0`）。**这不是移植的问题，是模型的。** 决定：LLM 不在这台机器上验
（另起服务器），这一轮就用它写出来的十集（合计 882 秒）跑全流程，
重点转到调度器。预告片接口上限是 120 秒（pydantic `le=120`），第一版驱动脚本
没看状态码，422 之后还把空剧本存成了一集——现在每一步都看状态码。

**三、按集排的队列让八张卡反复空转。** 每一集都要经历配音（串行、协调者
那张卡）→ 首帧 → 草稿 → 成片 → 装配（CPU），其间工作进程空转；每个阶段结尾
一条"等最慢那镜"的尾巴；每换阶段所有工作进程换一次模型。十一集就是十一遍。

补了 `order = "stage"`（C++ 独有，默认仍是 Python 的按集）：所有集先配音，
再所有集出首帧……阶段内部的代码一行不动，每个阶段就是 `run_episode` 带
`only={那一个}` 跑一遍，挑镜头仍按状态来。尾巴从十一条变一条，模型每个阶段
只换一次。两轮同一批活（`force=true`）的对比数字在跑，见下一条。

### 八张卡为什么只有三成在干活：权重一直在 PCIe 上搬（2026-09-09）

基线跑法（按集排、六个工作进程 + 卡 6/7 各再起一个，共八条）30 秒一采的
数字是"八卡平均 50%，平均 4.3 张在忙"。看着像调度问题，**1 Hz 采样看的是另一回事**：

    逐秒在忙的卡数：0085005500500500500500520051050050055005
    五个在跑的工作进程：CPU 60～80%

每张卡 1 秒忙、2 秒闲，利用率 35%，工作进程在忙 CPU。这是
`sd_image.cpp` 里写死的 `params_backend = "cpu"`：权重放系统内存，用到才
搬进显存。6 GB 卡上能跑全靠它——但 44 GB 的卡上视频模型（9.4 GB）+
编码器（11 GB）+ VAE 装十遍都够，却还在按小卡的方式一段一段往显存里搬。
**这一条比队列顺序更大。**

改法是把决定权交给 sd.cpp 自己的 `auto_fit`（`[models].weights = "auto"`，
默认 `cpu` 一个字不变）：它枚举这张卡真实的空闲显存，逐个组件放，装得下的
常驻，装不下的才放内存。两个细节：

- sd.cpp 只在 `backend` 和 `params_backend` **都为空**时才启用 auto_fit
  （`stable-diffusion.cpp` 里那一行 `&& params_backend_spec.empty()`）。
  所以 auto 模式下那个字符串必须是空的，填 "gpu" 之类反而关掉了 auto。
- 预算按物理显存（`profile.gpu`）算，不按 `vram_gb_override`。override 是拿来
  挑档位的，拿它当预算的话 auto_fit 会把本来装得下的编码器赶去内存。

**首帧那条路解不了。** 图像模型 39 GB bf16 在 44 GB 卡上装不下，auto 会把它
留在内存，出图阶段仍然是 PCIe 瓶颈。要解得换 fp8 权重（约 20 GB），另记。

对比实验在两集的子集上做（十一集一轮要两三个小时，三轮就是一夜）：
A 按集/cpu、B 按阶段/cpu、C 按阶段/auto，同一批镜头 force 重跑。数字见下一条。

### 两集子集上的四轮对比：怎么设计、顺手修掉的两件事（2026-09-09）

基线（按集排、权重放内存）在十一集上跑到 ep01 出完成片用了 24 分钟，
整套要四个多小时。**停掉了**——它的作用是给个参照数，而参照数在两集的
子集上一样能量，用不着烧四小时。四轮，同一批 41 镜，force 重跑：

| | 队列 | 权重 | 图像模型 |
|---|---|---|---|
| A | 按集（Python 的顺序） | cpu | bf16 39 GB |
| B | 按阶段 | cpu | bf16 |
| C | 按阶段 | auto（sd.cpp auto_fit） | bf16（装不下，仍在内存） |
| D | 按阶段 | auto | **fp8 20 GB**（能常驻） |

B 比 A 量的是队列顺序；C 比 B 量的是视频模型常驻显存；D 比 C 量的是
图像模型也常驻。三个变量分开看，哪个有用哪个没用一目了然。
数字见下一条。

顺手修掉的两件事，都是这一轮暴露的：

**工作进程收到 SIGTERM 会 abort。** `systemctl restart` 时 journal 里是
"Stopping… → 6 秒后 code=dumped, status=6/ABRT"。Crow 收到信号后 `app.run()`
返回，main 往下走进静态析构，而出片那个线程是 detach 的，还在 sd.cpp 里；
调度器里的 SdContext（带 CUDA 上下文）在它脚下被析构，最后 std::terminate。
现在 run() 返回后先取消当前任务、等它退出来（最多 30 秒），然后 `_Exit(0)`
跳过所有析构——工作进程没有任何值得析构的东西。

**池子每 500 毫秒问一次进度就报一次。** 同一步在事件里出现三四遍；快照只留
最后 200 条，几镜并行时全被这种重复填满，真正的 warn / gate 被挤出去。
现在 (step, steps, loading) 变了才报。

一个跨机器同步的坑也记一下：用 tar 把源码同步到服务器时 mtime 是本机的，
两边时钟不一致的话 cmake 可能认为目标文件比源码新、不重编——静默地跑旧
二进制。这次是虚惊（时间戳恰好对），但以后同步完要 touch 改过的文件再编。

### 抽帧看了才知道：草稿档和首帧出来的全是噪点（2026-09-09）

对比实验跑到一半，看闸门日志：ep01 的 22 镜里 8 镜被判"画面近乎纯色"降级，
17 镜重试过。把片子抽帧出来看：

- **成片档（1280×704，30 步）是对的**——一个人在暗室里看手机，就是剧本那场戏。
- **草稿档（640×352，10 步）是纯噪点**，彩色雪花。闸门判"近乎纯色"的那些是
  第一帧还有内容、后面塌成一片灰；判"过"的那些是雪花——展布够大就过了。
  之前那次端到端的草稿也是雪花。

  取值种数——**雪花的方差比真图还大**。这一条又是"看起来验了、其实什么都
  没验"，和 config 模板、webapp 截断那两次同一个形状。看一眼图，十秒钟的事。

图像那条路查到三个直接原因，任何一个都够把画面推成噪点：

1. 模型用错了：`qwen_image_edit`（图生图**编辑**模型，上游文档每条命令都带

`[models]` 加 `video_cfg / video_flow_shift / image_cfg / image_flow_shift`，
默认照上游文档；图像换基础模型 + bf16 编码器；草稿档步数用现成的
`/api/settings` 档位覆盖抬到 20，先跑探针看图，再定全流程用哪套。

### 一台机器崩了不该烧掉镜头的重试次数（2026-09-09）

`weights = "auto"` 的 OOM 修好之后重跑预告片，16 镜里 **11 镜还是静帧**，
原因换了一个，而且更值得记：

    trailer_sh001 fallback | 渲染连续失败：连不上工作进程 http://127.0.0.1:9001
    ...（连着十一条，全是同一个地址）

卡 0 的工作进程崩了、systemd 正在重启它的那几十秒里，**十一个镜头连着挑中
它**，每个的 `attempts` 加到 3 直接降级。池子里另外七个好好的，一个都没被试过。

根子在 `run_task` 把两件完全不同的事混成了一个异常：

  「这一镜渲染失败」——模型的问题，换个种子重试有意义，**该记 attempts**。
  「这个工作进程连不上」——机器的问题，换台机器立刻就好，**不该记 attempts**。

改成：连不上就把那个工作进程标坏、任务换一个再试，每一轮换一个，直到有一个
接住、或者全部都不通才抛。坏掉的过 30 秒放回来（systemd 重启大概就这个量级，
不放回来一次抖动就等于永久少一张卡）。

顺带把"派给谁"这段策略拆成 `worker_roster.hpp`——**不含网络代码，能测**。
`worker_pool.cpp` 链 httplib，按 CMakeLists 里那条既定做法不进单元测试目标，
理由是"逻辑部分都已拆到不依赖网络库的文件里"；换机重试这段以前没拆，
所以从来没被测过，而它恰恰是多卡跑批里后果最重的一段。七条用例钉住：
坏的跳过去换一个、过了冷却放回来、全坏也要挑一个试（不然整批卡死）、
每一个都试过了才判失败、忙着的不能被挑走。

### 换 5090 之前，把这台机器上学到的东西固化下来（2026-09-09）

用户要停掉 8×L20 换 5090（便宜很多）。这台机器上确认过的事实里，
有几条会直接决定新机器怎么配：

**显存门槛。** 一进程一张卡、不做跨卡切分，所以只看单卡：
出片要 Wan 5B fp16 9.4 + umt5 11 + VAE 1.4 ≈ **22 GB**，32 GB 装得下；
出首帧要 Qwen-Image fp8 20 + Qwen2.5-VL **bf16** 16 = 36 GB，32 GB 装不下，
**必须换 fp8 编码器**（8.8 GB）→ 28.8 GB，刚好进得去。L20 的 44 GB 才允许
两套都常驻、随便用 bf16。

**过了门槛就看带宽。** 今天量到的是：权重一旦常驻显存，卡就能跑满 100%；
权重放系统内存时每张卡 1 秒忙 2 秒闲（35%）。5090 的 1792 GB/s 对 L20 的
864 GB/s，这一项上 5090 明显更强（**这句是按规格推的，我只实测过 L20**）。

**同架构少一类惊喜。** 用户在本地 5080（Blackwell sm_120）调参，云上也是
5090 同架构，CUDA 核和 flash-attention 走同一条路。跨架构（L20 是 Ada sm_89）
构图一样但数值路径不同——**参数能带走，像素不能**：提示词、cfg、flow_shift、
步数、分辨率、种子（SHA-1 派生，跨机器一致）、模型选择全都照搬即可；
`weights` / VAE 分块 / 显存预算是跟显存走的，不能照搬。档位表按显存推，
16 GB 的 5080 和这台机器现在用的 `vram_gb_override = 20` 恰好落在同一档
（≥15.5 GB：草稿 640×352、成片 1280×704/30 步）——保险起见两边都写死。

### 测试一直只在 Windows 上全绿，而部署在 Linux（2026-09-09）

换到 5090 那台（Ubuntu）之后编了一份纯 CPU 的测试目标，578 条里挂 7 条断言。
在 8×L20 那台上也挂过同样几条，当时我记成"4 条 Windows 专属期望，不是 bug"
就过去了。**那个判断是错的**：不是"期望值恰好是 Windows 的"，而是
**那几条用例在 Linux 上根本没在测它们该测的东西**。

三处，都是"语料里存了生成那台机器的东西"：

**一、`user_dirs.json` 存的是 `C:/Users/ultra/AppData/Local/changji`。**
连用户名都在里面——换一台 Windows 机器也会挂。改成按平台存、相对家目录
（windows → `AppData/Local/changji`，linux → `.config/changji`）。Linux 那份
是在 5090 上用真 platformdirs 3.10.0 算的，不是我推的。生成器只更新自己
这个平台那一项，别的原样留着——不然在 Windows 上跑一遍就把 Linux 那份抹掉。

**二、`test_models_config` 写死 `D:/模型`。** 那在 Windows 上是绝对路径，
在 Linux 上是**相对**路径，于是 `resolve` 把它接到工作区后面，四条断言全错。
而这几条钉的是"绝对路径原样用、相对路径接 dir 后面"，和盘符没关系。

**三、`test_readonly` 最严重。** 语料里的路径参数被**原样喂给接口**，
Linux 上那个目录不存在，回的是"这里不是一个项目目录"——和语料里的项目摘要
逐条不等。也就是说 `/api/project`、`/api/assets`、`/api/shots` 这几条
"与 Python 一致"的用例，**在 Linux 上比的是两个错误消息**，什么都没验。
现在把语料里的项目目录映射到本机语料目录，比较前两边都把语料目录归一化
成 `<GOLDEN>`；显卡型号改成只比形状不比值（显存已经用 `pinned_vram_gb`
钉住，档位表那一堆仍然逐条比）。

改完 **578/578 在 Windows 和 Linux 上都过**，对拍 171 一致，
28 个生成器仍然能原样重生成语料、0 漂移。

**为什么这条对阶段 8 要紧。** 删掉 Python 之后，全部指望
`tests/golden/` 那几十份 JSON 当安全网。网只在开发机上成立、在部署平台上
破着，那"删了之后 C++ 有没有改坏还测得出来"这句话就不成立。
这件事我在 L20 那台上看见过一次，当成"已知的平台差异"放过去了——
**"已知"和"不是问题"是两回事。**

### 全尺寸出图跑通了，而我那套「装不装得下」的算术前提就是错的（2026-09-09）

38 GB 的 bf16 图像模型 + 8.7 GB 的 fp8 编码器，在一张 L20 上跑通了。
产物 768×448 的 PNG，944 KB，方差 14022、256 种取值——有真实内容不是空图。

**峰值显存 14880 MiB。** 而我之前算的是 43.7 GiB，还说"只剩 0.7 GiB 余量，
很可能塞不下"。差了近三倍。

#### 错在哪

那套算术假设**整个模型必须常驻显存**。可代码里 `params_backend = "cpu"`
是有意选的——权重留在系统内存，用到哪一段搬哪一段进显存
（`sd_image.cpp` 里那句注释写着"**这是 6GB 卡上能跑的关键**"）。
所以模型多大和显存峰值根本不是一回事。

我拿"文件大小之和"当"显存需求"，而这个项目从第一天起就不是这么跑的。

这条错误还连累了别的判断：为此专门下了一份 fp8 编码器（8.74 GB）
而不是 bf16（15.45 GB），理由是"bf16 那份加起来 53.5 GB 装不下"。
按实测，bf16 那份多半也装得下。fp8 仍然值得用（Ada 有原生 FP8 张量核，
更快），但**理由是速度，不是容量**——我当时给的是容量理由，那个理由是错的。

#### 实测的容量账

| | 峰值显存 |
|---|---|
| 出图（Qwen-Image-Edit bf16 + fp8 编码器） | **14.9 GB** |
| 出片（Wan2.2-TI2V-5B fp16） | **10.2 GB** |
| 配音（Qwen3-TTS 1.7B bf16，绑一张卡） | 约 1 GB |
| 一张 L20 | 44.4 GiB |

**一张卡装得下两三个出图 worker。** 之前"一卡一 worker"是按错误的容量算的，
现在看有加密的空间——不过瓶颈已经转到别处了（八卡同跑时是磁盘 IO），
真要加得先测。

#### 教训

**"模型文件多大"和"要多少显存"是两个数，中间隔着一整套调度策略。**
把前者当后者，会得出"装不下"这种结论，然后据此做一串下游决定
（下哪个量化档、一卡放几个 worker、要不要 offload）——而那些决定全建立在
一个没验过的数上。

正确的顺序是：先跑一次看峰值，再谈装不装得下。这台机器上跑一次只要几十秒。

### 逐字节比抓到了池的一个真 bug：出片用错了种子函数（2026-09-09）

方案第二步的完成判据是「产物和进程内的逐字节比」。开发机上出一张图 20 分钟、
跑两遍 40 分钟，一直欠着。上了 8 卡机器补上了——**一比就不通过**。

同一个项目跑两遍，一遍 `[workers]` 留空（进程内），一遍指向工作进程（走池）：

    进程内 ep01_s01_sh001.mp4  186618 字节  ea3254a9...
    走池   ep01_s01_sh001.mp4  180688 字节  b43e6e5f...

**但这还不能判池有 bug。** 得先分清是"池改变了结果"还是"GPU 本来就不确定"
——扩散推理在 CUDA 上非确定是常见的。同一条路跑两遍：

    ✓ 两遍一样  ep01_s01_sh001.mp4
    ✓ 两遍一样  ep01_s03_sh007.mp4

GPU 是确定的。所以差异是真 bug。

#### 差在一行

    worker_pool.cpp:206（出片）  t.seed = frame_seed(shot_id, attempts);   ← 错
    sd_video.cpp:116（进程内）   render_seed(shot_id, attempts)

**`frame_seed` 和 `render_seed` 是两个不同的函数。** 出图那条用 `frame_seed`
是对的（`worker_pool.cpp:184`），出片那条抄下来时没改。

写错了**不报错、不变慢、产物大小也在正常范围**，只是走池出来的片和进程内的
不是同一个画面。没有任何一层会去比这个——单元测试比不到（要真跑模型），
对拍比不到（那是 Python 和 C++ 之间的事），
连"八张卡产物 md5 各不相同"那条都验不出来（种子不同本来就该不同）。

修完再比：**逐字节相同**，而且 md5 和修复前的进程内那份一致
（`ea3254a9...`）——说明进程内一直是对的，错的是池。

#### 这条判据为什么必须留着

它是唯一能发现"两条路算出不同东西"的手段。而这种错的形状是最难查的：
八张卡都在转、进度条都在走、产物都能播，只是画面和单机跑出来的不一样，
而**没有人会去逐字节比一段视频**。

判据的顺序也重要：**先证明同一条路可重现，再比两条路**。
少了前一步，看到差异只会得出"GPU 不确定，没办法"这种把真 bug 放过去的结论。

### 八张卡同时出片：26 秒 8 条，产物互不相同（2026-09-09）

两张卡验通之后，直接上满八张。

    12:08:54    295  315  295  315  315  315  295  315   ← 八张同时开始
    12:09:04   2911 2911 3827 7849 8167 3135 2995 7905   ← 八张同时在跑
    12:09:09   3829 3829 3829 3829 3829 3829 3829 3829
    12:09:14    425  425  425  425  425  425  425  425   ← 八张同时释放

**26 秒出 8 条**（派出去到全完）。串行按热启动 15 秒一条算是 120 秒，
约 **4.6 倍**。没到 8 倍——八个进程同时从盘里读 10 GB 模型，
瓶颈从算力转到了 IO。这也再次印证「少换模型」比「多并行」更值钱。

产物验过不是空壳：h264 448×256、25 帧、1.0417 秒、帧间差非零（在动），
**八个 md5 全不相同**——各自的种子真的传到了、没有互相串。
`frame_seed(shot_id, attempts)` 由协调者算好下发那条设计成立。

#### systemd，不要 nohup

八个 worker 一开始用 `setsid nohup ... &` 起，**不可靠**：SSH 一断进程经常
跟着没，起来了也说不清是哪一个。换成 systemd（`install_workers.sh`）：
一卡一个 unit、端口 9001+k、崩了自动重起、日志分开、开机自启。
八个 unit 一条命令装完，顺便把协调者要填的 `[workers].endpoints` 打出来。

#### 两个只有真跑才会撞到的坑

**一、systemd 不给服务设 `HOME`。** 而配置是按
`$HOME/.config/changji/config.toml` 找的。少了它 worker 读的是内置默认值，
表现是"配置里明明填了 `[models].video`，八个 worker 却同时说没配"——
一句莫名其妙的话乘以八。unit 里显式给 `HOME` 和 `XDG_CONFIG_HOME`。

**二、`std::thread` 在还 joinable 时被析构 → 进程直接 terminate。**
`Live` 结构原来存着 `std::thread`，只在**有人来查状态**时才 detach。
没人查、或者进程收到 SIGTERM，析构就 terminate，日志里只有
`terminate called without an active exception` 一行，看不出和线程有关系。
改成建完就 detach，靠 lambda 捕获的 `shared_ptr<Live>` 保证对象活到线程结束。

#### worker 接任务前自检（这条是烧出来的）

第一次跑出片，扩散 8 步全跑完、到最后编码那一步才报「找不到 ffmpeg」——
白烧一次。本机上 doctor 会在起跑前拦，但直接给 worker 派任务绕过了那道检查。

加了 `cannot_do()`：接任务前查扩散模型、VAE、出片要的 ffmpeg、产物目录，
缺什么当场 400。实测**42 毫秒拒掉，显存 0 MiB，模型压根没加载**。
在 8 卡机器上，"跑几十秒再失败"乘以八就是几分钟白烧。

而且它当场就把上面那个 `HOME` 的问题说清楚了（"[models].video 没配"），
否则要等八条都跑完才知道哪里不对。

### 多卡真并行验通了：两张卡同时满载，其余六张为 0（2026-09-09）

整个多卡设计里唯一没法在单卡上验的那一环，通了。

#### 判据是显存，不是"看起来在跑"

两个 worker 分别绑卡 0 和卡 1，同时派一个出片任务，逐 5 秒采样八张卡的显存：

    11:47:12    1177  1177     0 0 0 0 0 0    ← 同时开始加载
    11:47:17   10227 10227     0 0 0 0 0 0    ← **两张卡同时满载**
    11:47:23    3829  3829     0 0 0 0 0 0    ← 同时释放
    11:47:28     425   425     0 0 0 0 0 0    ← 两个都完事

**其余六张始终是 0。** `CUDA_VISIBLE_DEVICES` 对 ggml 的 CUDA 后端确实生效，
`worker_server.cpp` 里那句 `set_env` 成立，八路并行不会全挤在一张卡上。

之前只验到"一个 worker 绑卡 0 时只有卡 0 有占用"，那还不足以排除
"第二个进程会抢卡 0"。两张同时满载才是完整的判据。

#### 实测数字

| | |
|---|---|
| Wan2.2-TI2V-5B fp16 满载显存 | **10.2 GB** |
| 一张卡（44.4 GiB）装得下 | **约 4 份** |
| 热启动出一段 25 帧 | **约 15 秒** |
| 冷启动同样一段 | **约 70 秒** |

**冷热差 4 倍以上，差别全在从盘里读那 10 GB 模型。** 这印证了「按阶段分批」
那条的分量：模型加载是大头，不是采样。也说明一卡多 worker 值得试——
显存装得下四份，而多一个常驻实例就少一次加载。

#### 出片这条路本身也验过了，不是"跑完没报错"

产物 `ffprobe` 出来：h264、448×256、24 fps、**25 帧**（4n+1，Wan 的硬要求）、
时长 1.0417 秒。逐帧亮度 26.8 → 28.3 → 27.3 → 24.1 → 21.9 → 20.3 → 18.9，
帧间差 7.3 / 2.5 / 3.6 / 2.4 / 2.8——**在动，不是同一张图重复 25 遍**。
和「验过不是静音」「验过不是空图」同一条标准。

#### 一处该改的：worker 接任务前不自检

第一次跑扩散全跑完了、到最后一步才报「找不到 ffmpeg」——**白烧一次**。
本机上 doctor 会在起跑前拦下这类事，但直接给 worker 派任务绕过了那道检查。

**worker 应该在接任务前自检一次**（出片要 ffmpeg、出图要模型文件），
而不是指望调用方记得先跑 doctor。派任务时缺什么就当场 400 拒掉，
比跑几十秒再失败诚实。这一条记着，还没改。

### 一个只设了半边的 CUDA 开关：编出来的二进制全跑在 CPU 上（2026-09-09）

上机第一次带 CUDA 编，`[520/520] Linking` 一切正常。**但那个成功是假的。**

    build（CHANGJI_LLAMA=ON）：  GGML_CUDA:BOOL=OFF，连 libggml-cuda.a 都没有
    build-worker（LLAMA=OFF）：  有 libggml-cuda.a，112 个 FP8 符号

`CHANGJI_SD_CUDA` 只设了 `SD_CUDA=ON`。**开了 `CHANGJI_LLAMA` 时 ggml 由
llama.cpp 提供，而它的 CUDA 后端由 `GGML_CUDA` 控制，不认 `SD_CUDA`。**
于是编出一个完全没有 CUDA 的二进制——不报错、跑得动、全在 CPU 上，
表现就是"能跑但莫名其妙地慢"。在一台 8 卡机器上这个错能藏很久。

已修：`CHANGJI_SD_CUDA` 现在同时设 `GGML_CUDA`。

#### 查这个 bug 时我自己先错了一轮，值得记下来

看到 configure 日志里五行 `error: patch failed: ggml/src/ggml-cuda/...`，
我判定"FP8 补丁没打上"，还查了补丁内容、确认那几个 hunk 正是 FP8 路径，
写好了一整套解释。**全错。**

那五行是 `git apply --reject` 的**预期输出**——脚本注释里就写着
"返回码非零是预期的，有 .rej 就会非零"，紧接着的 `resolve_llamacpp_conflicts.py`
会把那几个 reject 按锚点解掉，日志里 7 个 hunk 全是 `[ok]`。
补丁一直是好的。

**我为什么会错**：拿 `nm ... libggml-cuda.a | grep -c fp8` 当判据，
得到 0 就下了结论。可那条命令**分不清"库里没有 FP8"和"根本没有这个库"**
——glob 匹配不到文件时 `grep -c` 一样回 0。
和这次会话里反复出现的是同一个形状：**一个恒真或恒假的判据，
看着在验，其实什么都没验。**

正确的判据是先问"库在不在"，再问"库里有什么"。分两步，两个都要看。

#### 顺带一个真结论：工作进程让「两份 ggml 共存」不再是必答题

那套补丁存在的理由是"sd.cpp 和 llama.cpp 要在同一个二进制里共用一份 ggml"
（见「决策 17」）。有了工作进程，**它们可以不在一个进程里**：

| 进程 | 编译选项 | ggml 从哪来 |
|---|---|---|
| 工作进程（出图、出片） | `SD=ON SD_CUDA=ON LLAMA=OFF` | sd.cpp 自带的 leejet fork，FP8 原生 |
| 协调者（配音、装配、接口） | `SD=OFF LLAMA=ON` | llama.cpp 的，给 TTS |

而且这个切分不是为了绕开什么才凑的——**池本来就只把 frame/video 派出去，
TTS 从一开始就留在协调者**（`worker_pool.cpp` 只实现了那两个 renderer）。
进程边界正好落在两份 ggml 的分界线上。

补丁集仍然要维护：单二进制那条路（小机器上一个进程既出图又配音）还要它，
而且现在确认它是好的。但多卡部署下可以完全绕开。

### 上机实测：两个数字推翻了纸上的算术（2026-09-09）

机器到手，先验了三件在单卡上验不了的事。**两件和纸上算的不一样。**

#### 一、`CUDA_VISIBLE_DEVICES` 对 CUDA 应用确实生效 ✅

这是所有并行的地基。**但验的方法一开始就错了**：先拿 `nvidia-smi` 试，
三个值看到的 UUID 一模一样，差点判成"不生效"。
实际上 `nvidia-smi` **按设计就不认这个变量**——它是管理工具不是 CUDA 应用，
要过滤得用 `-i`。（`gpu_preflight.sh` 里那句注释当时写反了，已改。）

真判据得拿一个 CUDA 程序问。写了个 `cudaGetDeviceCount` + `GetDeviceProperties`
的十行程序：

    不设变量            → 看得见 8 张，[0]..[7]
    CUDA_VISIBLE_DEVICES=3 → 看得见 1 张，而且**在它眼里就是 [0]**
    CUDA_VISIBLE_DEVICES=7 → 同上

正是工作进程要的语义：每个进程只看得见自己那张，且编号为 0。
`worker_server.cpp` 里那句 `set_env` 成立。

#### 二、单卡显存是 **44.4 GiB**，不是 48 GB ⚠️

`nvidia-smi` 报 46068 MiB，CUDA 报 44.4 GiB。**厂商标称的 48 GB 是十进制**。
这把前面那道"装得下"的算术推翻了：

| | 纸上（按 48 GB） | 实测（44.4 GiB） |
|---|---|---|
| 图像 bf16 38.05 GB | 38.05 | **35.4 GiB** |
| fp8 编码器 8.74 GB | 8.74 | **8.1 GiB** |
| 图像 VAE | 0.24 | 0.2 GiB |
| 合计 | 47.0 / 48 ✅ | **43.7 / 44.4** ⚠️ |

**只剩 0.7 GiB 余量**，而这还没算 CUDA context、激活值、中间张量。
**很可能塞不下**，得实测。塞不下的话往下走一档：
编码器已经是 fp8 了，再降就得动扩散模型（Q8_0 的 GGUF 是 20.27 GB = 18.9 GiB，
加编码器 27 GiB，余量就很宽裕了）。

教训是老的那条：**十进制的 GB 和二进制的 GiB 差 7%**，
在"刚好够"的边界上就是够和不够的区别。以后算显存一律用 GiB。

#### 三、环境

  - Ubuntu 24.04.4，内核 6.8，驱动 580.126.09，CUDA 13.0.88
  - **8 张 L20，每张 44.4 GiB**，计算能力 **8.9**（`CHANGJI_CUDA_ARCH=89` 猜对了）
  - **内存 1006 GB**、128 核、磁盘 947 GB 可用

内存 1 TB 改了一个结论：之前说全 bf16 编码器（53.5 GB）必须砍，
理由是 8 个进程各 53.5 GB 常驻内存怕 swap。1 TB 装得下，
所以那条路重新可行——代价是 offload 带来的速度损失。
两份编码器都下了（fp8 8.74 GB + bf16 15.45 GB），配置换一行就切，用来对比画质。

### 8 × L20（48 GB）这台机器：算出来的账

L20 是 Ada（**sm_89**）、48 GB GDDR6、**没有 NVLink**。后面这两条各自决定一件事。

#### 显存：全尺寸装不下，得砍一刀

|  | bf16 全尺寸 | 装得下的那一档 |
|---|---|---|
| 图像 Qwen-Image-Edit | 38.05 GB | 38.05 GB（不动） |
| 它的文本编码器 Qwen2.5-VL | 15.45 GB | **fp8_scaled 8.74 GB** |
| 图像 VAE | 0.24 | 0.24 |
| **一张卡上合计** | **53.5 GB ❌** | **47.0 GB ✅** |

**53.5 > 48，一张 L20 装不下。** 而且 8 路并行是**每个进程在自己那张卡上放满
一套**，不是八张卡分着放——所以这不是"总共 384 GB 够用"的问题。

砍文本编码器而不是砍扩散模型：画质由扩散模型决定，编码器的精度影响小得多。
而且 **L20 是 Ada，有原生 FP8 张量核**，fp8 这一档不是模拟出来的。

不想砍的话只有两条路：一是靠 offload（代码里已经是
`params_backend = "cpu"`，今天这台 6 GB 卡跑 6.6 GB 模型就靠它），
但**要保证内存够**——8 个进程各 53.5 GB 常驻内存是 428 GB，机器配不够就
swap 到死；二是一个进程占两张卡，**当前代码不支持**（`CUDA_VISIBLE_DEVICES`
设的是单张）。

#### 磁盘：全尺寸档 70.5 GB

`download_models.ps1 -Preset full` 那八个文件加起来 70.5 GB
（扩散模型 bf16 + 编码器 fp8）。加上构建（Linux+CUDA 约 8）、
Docker、产物累积，**开 250 GB**；160 GB 是能跑的下限。

**写剧本那个 Qwen3-14B bf16（27.5 GB）没算进去**——到今天为止流水线一次都没
用过它（剧本分镜走外部 Ollama 或手写）。要进程内跑再单独加。

#### 没有 NVLink：坐实了"不做跨卡切分"

卡间只有 PCIe。上面「明确不做的」那一条本来就是这个理由，L20 更是如此。

#### sm_89：必须显式指定，否则不报错但很慢

`CMakeLists.txt` 以前**从来没设过 `CMAKE_CUDA_ARCHITECTURES`**，只设了
`SD_CUDA=ON` 就交给默认值。默认值不含目标卡的架构时，CUDA 退回 PTX JIT——
**不报错**，第一次跑每个内核现编一遍，表现是"能跑，但莫名其妙地慢"，
而且慢在哪儿完全看不出来。

补了 `CHANGJI_CUDA_ARCH`，默认 `89`：

    cmake -S cpp -B build -DCHANGJI_SD_CUDA=ON -DCHANGJI_CUDA_ARCH=89

（L20/L40S/4090 是 89，A100 是 80，H100 是 90，3090/A10 是 86。
容器里构建**别用 `native`**——构建机和跑的机器不一定是同一张卡。）

#### 上机第一件事仍然是验绑卡

`CUDA_VISIBLE_DEVICES` 对 ggml 的 CUDA 后端到底管不管用，单卡机器上验不了。
不生效的话八个进程全挤在卡 0 上，**看着在并行，实际在排队，还不报错**。
后面所有并行收益都建立在这一条上。

### 落地顺序

1. `HardwareProfile` 认识卡数（只加不改）
2. 工作进程 + 池，`[workers]` 留空时行为不变——**这一步单卡也能验**：
   起一个本地工作进程，整条流水线走一遍，产物和进程内的逐字节比
3. ~~阶段循环改成派—收。先首帧，再出视频~~ **✅ 做完了**（6 卡 5.45 倍，见上）
4. ~~界面显示多个在跑的镜头~~ **✅ 做完了**（WS 消息带 kind、快照 current 单调、界面列出正在跑的几镜，见下）
5. 数据流模式（钉模型用）
6. 多机：先定"产物怎么回来"

## 七、风险

### 风险一：配音的 C++ 化没有先例（高）

现有 `models/TTS/` 里 17GB 权重是 CosyVoice、Qwen3-TTS、higgs_audio_v3，
全部是 Python 模型，没有 C++ 实现。[选型结论.md](选型结论.md) 里的主力是
Qwen3-TTS 1.7B（Apache 2.0，中文综合最强）。

要把它链进二进制，路径是：Qwen3 骨干转 GGUF 交给已经链在里面的 llama.cpp，
codec 解码器/声码器用 ggml 自己写。已知的未知有三个：llama.cpp 现在的 TTS
支持只覆盖 OuteTTS 那一档；Qwen3-TTS 用的是哪种 codec、声码器规模多大；
骨干能不能干净地转成 GGUF。这三个都要先查，查完才能估工期。

**决定：硬做，不接受退路。** sherpa-onnx 那一档的中文质量会丢掉选型结论里
TTS 那一节的筛选成果，不接受；Python 侧车违背单一二进制，不接受。

#### 三个「已知的未知」查完了（2026-09-08）：全部作废，难点换了地方

方案说"这三个都要先查，查完才能估工期"。查完了，结论比原来假设的好得多——
**上面那段"没有 C++ 实现""codec 解码器/声码器用 ggml 自己写"已经过时。**

| 原来的未知 | 查到的 |
|---|---|
| llama.cpp 的 TTS 只覆盖 OuteTTS 那一档 | **不再是。** PR #26254「mtmd: support Qwen3-TTS」**2026-08-04 已合并进主线**，走 mtmd 那套多模态框架，支持中英德意葡西日韩法俄，带说话人参考音频 |
| Qwen3-TTS 用的是哪种 codec、声码器多大 | 12Hz 那一路：12.5 Hz、16 层多码本，解码器是 SEANet + ConvNeXt + DAC v2 + RVQ 的轻量因果卷积网。25Hz 那一路是 block-wise DiT + BigVGAN，重得多——**我们要的是 12Hz 这一路** |
| 骨干能不能干净地转成 GGUF | **已经有人转好并发布了。** talker（Qwen3 LM + code predictor MTP 头 + 可选说话人编码器）1.7B Q4_K_M **1.2 GB**；tokenizer（12Hz 码 ↔ 24 kHz 波形）Q4_K_M **255 MB**。合计约 1.5 GB，装得进 6 GB 的预算，比第三节那张表里写的"~1 GB 待定"多半个 G |

许可证：Qwen3-TTS 模型和音频 codec 都是 Apache 2.0。

**"配音的 C++ 化没有先例"这条风险不成立了**，可以从「高」降下来。

原来的路径写的是"交给**已经链在里面的** llama.cpp"。那半句是假的——
决策 4 把大模型挪到远端（`[llm]` 配置段）之后，`CMakeLists.txt` 里只有
stable-diffusion.cpp，llama.cpp 没有链进二进制。

> **一处要纠正的记录。** 这一节最初写的是"难点从『写 codec』换成
> 『两份 ggml 共存』，工期的大头在这儿，而且还没验"。**后半句是错的**：
> 两份 ggml 的问题在前置验证工程里早就解掉了（决策 17），
> `patches/` 下的补丁集 CPU 和 CUDA 两条链都跑通过，
> 见 [verify/RESULTS.md](../cpp/verify/RESULTS.md)。
> 写那句话的时候我没有先读 `verify/`，凭"llama.cpp 不在 CMakeLists 里"
> 就推断"没验过"。**不在主工程里 ≠ 没验过**——那正是验证工程存在的意义。

所以阶段 9 的实际路线是现成的：

1. **统一的 ggml = llama.cpp 自带的那份 + leejet 扩展补丁**（决策 17，已验）。
2. **把那套手工步骤自动化**（`patches/apply_to_llamacpp.py`），
   接进主工程的 `CHANGJI_LLAMA` 开关。verify/ 是一次性工程，人可以在
   拉完源码之后插一次手；主工程靠 FetchContent 拉，没人插得进去。
3. 接 llama.cpp 的 mtmd TTS，做成第四个 `TTSBackend`。

**第 3 步先做了编译和链接那一半**（2026-09-08）。两件事：

**一、Qwen3-TTS 的实现在 mtmd 里，不在 libllama 里**
（`tools/mtmd/models/qwen3tts-gen.cpp`、`qwen3tts-spkenc.cpp`）。
mtmd 挂在 `tools/` 底下，而我们把 `LLAMA_BUILD_TOOLS` 关了——
只链 llama 是拿不到配音的。上游正好留了 `LLAMA_BUILD_MTMD` 这个钩子，
可以单独编 mtmd，不用把整个 `tools/` 和 `common` 拖进来。
`MTMD_VIDEO` 要关：它要 `LLAMA_SUBPROCESS`，运行时还要 PATH 里有 ffmpeg，
而配音只出音频。

**二、加了一条运行时探针，不满足于"编出来了"。** mtmd 是静态库，
而我们还没有任何地方调它的函数——链接器完全可以把它整个丢掉，
构建日志里照样有一行 `Linking CXX static library mtmd.lib`。
所以 `/api/doctor` 里那项"进程内配音"真的调两个纯函数
（`mtmd_default_marker`、`mtmd_context_params_default`），
叫得动才算数。实测回的是 `mtmd 已链入，媒体标记 <__media__>，默认 4 线程`。

**合成路径写完了，但一次都没跑过**（2026-09-08）。`infer/llama_tts.hpp`：
载模型（talker + tokenizer 两份 GGUF）、逐帧驱动、写 wav、回时长。
参照的是 llama.cpp 自带的 `tools/tts/tts.cpp`，那个文件开头自己写着
"this is NOT a production-ready binary"，只是它把模型相关的部分都推给了
`mtmd_helper::gen_audio`，剩下的循环不到四十行。`common` 那几个依赖
（`common_init_from_params`、`common_sampler_*`）都换成了 llama.h 里的
原生对应物，所以不用把 `LLAMA_BUILD_COMMON` 打开。

⚠️ **编得过 ≠ 是对的。** 机器上没有权重，这条路径一次都没有真正执行过。
头文件里把这一点写在最前面了，还钉了一句：mtmd 的音频生成 API 标着
EXPERIMENTAL，升级 llama.cpp 时**这一段要重新对照上游的 tts.cpp 看一遍**。

**链接时撞到一个真问题：两份 stb。** 开了 `CHANGJI_LLAMA` 之后 mtmd 也带
一份 stb（`vendor::stb`），和我们 `sd_image.cpp` 里那份 `STB_IMAGE_IMPLEMENTATION`
撞出几十个重复符号，直接 LNK1169。修法是给我们那份加 `STB_IMAGE_STATIC`
（内部链接），不是改成用 mtmd 那份——两份 stb 的版本不一定一样，
借用别人的实现等于把自己的行为绑在对方的升级上。
**这正是风险二说的那类问题，只是这次撞在第三方小库上而不是 ggml 上。**

两处顺手挡掉的坑，写在代码里：
- **不调 `llama_backend_free()`。** 它是全局的，配音后端销毁时调它会把
  同一个进程里 sd.cpp 正在用的 ggml 后端一起拆掉。进程退出时操作系统会收。
- **context 必须开 `embeddings`。** 每一帧都要把骨干的隐状态喂给解码器，
  关着的话 `llama_get_embeddings_ith` 返回空，症状是第一帧就失败。

**接进 `TTSBackend` 也做完了**（2026-09-08）：`[tts].backend = "local"`，
模型路径在 `[models].tts` / `[models].tts_decoder`。

**`local` 这个取值是加法，不是破坏。** Python 那边 `backend` 是个没有枚举
校验的普通字符串，填 `local` 它不报错、只是认不出来然后退回估算后端；
原有的 `comfy` / `http` 两个取值行为一个字没变。模型路径放进 `[models]`
是因为**那一节本来就是 C++ 侧独有的**（Python 的 Settings 是
`extra="forbid"`，见"配置隔离"），C++ 独有的键集中在一处最容易分辨。

`tts` 和 `llm` 分成两个键：talker 只有 1.7B，写剧本那个是 14B，
共用一个键的话换写剧本的模型会把配音一起换掉。

**载不起来时不往哪儿写日志。** `run_deps.cpp` 没有日志设施，为一条错误
现造一个不合适。用户看得见的地方有两处，都已经覆盖：配音阶段的 start
事件会报后端名字（退回了就是 `estimate`），以及 `/api/doctor` 的
"进程内配音"——它现在真的去查那两个模型文件在不在，
**并且只在 `[tts].backend` 真选了 `local` 时才判 FAIL**：
编进来但不用它是完全正常的形态，报警告等于让报告长期挂一条黄字。

**一个反直觉但必须保住的不对称**（2026-09-08 补）：
配置文件认 `local`，**`POST /api/connections` 有意不认**。

Python 那个接口明写着 `if new_tts.backend not in ("comfy", "http")` 就回 400，
而它在对拍覆盖范围内——放 `local` 过就是一处真的破契约，
而阶段 8 之前两个后端在接口上必须一模一样。所以 `local` 走配置文件那条路，
和 `[models]` 那一节同样的道理：C++ 独有的东西留在文件里，
不进这个两边共用的接口。阶段 8 删掉 Python 之后这条限制可以放开。

这个不对称写了一条用例钉住（`test_config_api.cpp`），因为它**很容易被
"顺手补齐"**——补齐的代价是对拍多一条不同。

**权重怎么拿：`download_tts_gguf.ps1`**（2026-09-08 加）。
一条命令下齐两份，断点续传，默认走 hf-mirror（国内直连 huggingface
常断在半路），下完把要贴的配置行打印出来。

和 `download_tts_model.ps1` 不是一回事：**那一份下的是 safetensors，
给 Python / ComfyUI 那条路用**；这一份下的是 GGUF，给 C++ 进程内的
llama.cpp + mtmd 用。两条路的权重格式不通用。

骨干选 `customvoice` 而不是 `base`：mtmd 那套接口的输入正好是一个
`speaker_ref`（一段参考音频），而短剧要的是每个角色一个声音。
`base` 是模型自带的几个预置音色，但 **mtmd 的接口里没有"挑哪个预置音色"
这个参数**，实际拿到的是默认那个。`voicedesign` 要一段文字描述，
changji 目前没有地方填。

实测两份的真实大小（HEAD 查的，不是估的）：talker 1127 MB + 解码器 243 MB
= **1.34 GB**。

**实机判据做成了一条命令：`changji.exe --say "念一句"`**（2026-09-08）。

那条合成路径代码写完很久了，但一次都没执行过。权重到位之后这是最短的
验证路径——**不用起服务、不用建项目、不用 ffmpeg**，出不出得了声一句话

`--tts-model` / `--tts-decoder` 可以临时盖过配置里的路径。加这两个是因为
写完之后发现：想拿 `--say` 试一份刚下好的模型，得先去改配置文件，
而"改了配置去试、试完再改回来"这件事本身就容易忘记改回来。

**三条失败路径逐条验过**，每一条都说清楚下一步该干什么：

**`/api/voices` 也跟着改了**（2026-09-08）：`[tts].backend = "local"` 时
不去问 ComfyUI，直接回空列表加一句"音色来自参考音频"。

原来那个接口不管配的是哪个后端，一律去读 ComfyUI 的配音工作流再问服务端

答非所问比答不出来更糟：他会去查 ComfyUI，查半天发现根本不相干。

用例里那个假 transport 一被碰就让用例失败，**通过本身就证明了它没去问**。

**照着对 sd.cpp 那套办法，把 `llama_tts.cpp` 也对了一遍**（2026-09-08）。
这段代码是照着 `tools/tts/tts.cpp` 写的，而那个文件走 `common`——
我把 `common` 那几个依赖换成了 llama.h 的原生对应物，**换的时候丢了默认值**：

| | 参考实现（走 common） | 我原来写的 | |
|---|---|---|---|
| `n_ctx` | `common_params.n_ctx = 0`，注释写着 "0 == context the model was trained with" | `llama_context_default_params()` 给的 **512** | ❌ 已改成 0 |
| `pooling_type` | common 按需要设 | 默认 `UNSPECIFIED`，靠模型 hparams 兜底 | ⚠️ 改成显式 `NONE` |

**512 是不够的**：骨干是自回归跑的，提示词的 token 加上最多 512 帧都要占
位置，一句长一点的台词就撑爆，而症状是"生成中途失败"，指不到"上下文开小了"。

`pooling_type` 那条大概率本来也没事（Qwen3 骨干的 hparams 多半就是 NONE），
但这里依赖 `llama_get_embeddings_ith(ctx, -1)` 取最后一个 token 的隐状态，
一旦哪个模型带了池化类型就悄悄取到别的东西。显式写死，不赌默认值。

**教训和 sd.cpp 那两处是同一个：把一个"带默认值的封装"换成"直接调底层"时，
封装里那些默认值会静默消失。** 换的时候只看了签名对不对得上，没看默认值。


**合成那一段为什么还没接：**
mtmd 的音频生成 API 在头文件里明写着
`EXPERIMENTAL API for audio generation, subjected to breaking changes`，
而且**是无状态的**——`mtmd_gen_audio_process` 的注释说
"caller must handle state management and audio frame accumulation"。
这不是"调一个函数出一段音频"，是要自己驱动骨干模型逐 token 跑、
把隐状态喂进 `GEN_CODE`、攒够码本再走 `GEN_WAV`。那是几百行，
而且**在拿到权重之前一行都验不了**。先把编译链接这一段做扎实、能自检，
比先写一堆跑不了的代码有用——阶段 5 和 7 的教训就是"代码写完了、
实机判据卡住"这个状态本身要标出来，不要假装完成。

第 1、2 步已经做完（2026-09-08）：`CHANGJI_LLAMA=ON` 时 llama.cpp 和 sd.cpp
在同一份打过补丁的 ggml 上编出**一个 57 MB 的 changji.exe，没有外挂 DLL**。
拿它跑完整对拍：**164 条一致、0 条不同**——链进 llama.cpp 之后接口行为
一个字没变。默认仍然关着：阶段 8 之前没有主线功能用得到它，
开着只是让每次干净构建多编一份 llama.cpp。

**验证工程里那个 ABI 探针搬进了 `/api/doctor`，一接上就抓到一处存量问题。**

那份验证报告称它是"这次验证最有价值的一条"，理由是它防的那类问题
没有别的信号：`ggml` 按 64 编、本体按 160 编，`ggml_tensor` 大小不一致，
**编译过、链接过、起得来**，只有读写张量时慢慢踩坏内存。搬进体检报告是因为
验证工程是一次性的，而这个风险跟着二进制走——谁改了构建脚本、
谁换了 ggml 的来源，都可能悄悄把它打破。

接上之后**默认构建当场报 fail：库是按 160 编的，本体是 64。**
原因是 sd.cpp 的 `add_definitions(-DGGML_MAX_NAME=160)` 只作用于
**它之后的目录作用域**——加到了 ggml 上，没加到我们自己的源文件上。
这个状态存在很久了，只是本体里没有人直接读写 `ggml_tensor` 的字段，
所以一直没出事。修法是把这个定义提到顶层，链了 ggml 就定义，
不管它是 sd.cpp 还是 llama.cpp 带进来的。

> **探针自己也差点放过它。** 第一版判据写的是"读回 100 就算过"，
> 于是默认构建报了一句自相矛盾却是绿的话——"库和本体都是 64"，
> 而它明明读回了 100。**读回来的长度反映的是库按多少编的，不是本体按多少编的**，
> 要先从探针反推库的值，再和本体比。一个只会说"对"的检查比没有检查更糟：
> 它占着"这里查过了"的位置。

**自动化时撞到一个验证工程没撞上的坑**：sd.cpp 的三个 .cpp 里写着
`#include "ggml/src/ggml-impl.h"`——相对它自己那个 ggml 子模块的路径。
我们不拉那个子模块（ggml 由 llama.cpp 提供），于是编不过。
验证工程钉的 sd.cpp 是 `d8fb10c`(master-846)，主工程钉的是
`9cdb6b6`(master-848)，中间那两个提交新增了 `compute_workspace.cpp`。
**"验证工程验过"不等于"换个版本还成立"。** 修法是把 llama.cpp 的源码根
加进 sd.cpp 的搜索路径（它底下正好也是 `ggml/src/ggml-impl.h`）——
头和库必须同源，否则又回到 `GGML_MAX_NAME` 那类"编得过、跑起来踩内存"的问题。

一条备选没走：**只链 qwentts.cpp**（MIT，C++17/GGML 的独立实现，
就是发布上面那批 GGUF 的那个）。表面积比整个 llama.cpp 小得多，
但仍然要一份 ggml、仍然要过同一个补丁集这一关，而且是第三方单点维护，
上游不跟 Qwen 的新版本就得自己跟。走主线的那条更稳。

**还没验的（不要当成已经确定）：** 合并进主线的那个 TTS 实现在
Windows + MSVC 上编不编得过；6 GB 显存上和首帧/视频模型轮换时的实际表现；
中文的实际音质。上面关于 PR 和权重的结论来自读 PR 页面和权重仓库页面，
**没有跑过模型**。



但它**不卡主线**。阶段 8 删 Python 的前置条件是阶段 7 完成（成片能出、
对拍通过），配音这期间走 ComfyUI 可选后端。Qwen3-TTS 的 C++ 化作为
阶段 9 并行推进。

这意味着阶段 8 之后有一段时间，实际形态是"C++ 二进制 + 用户自己装的
ComfyUI"，纯二进制出不了声。这一点写在这里，不要在阶段表里假装它不存在。

### 风险二：统一 ggml 是一笔长期维护成本（中）

sd.cpp 和 llama.cpp 各自 vendor 了不同 commit 的 ggml。同时链接进一个
二进制会有符号冲突或 ABI 不兼容。而"llama.cpp 走子进程"这条退路已经被
严格单一二进制关掉了。

做法是两个库都关掉自带的 ggml，指向同一份。麻烦不在第一次接通，在之后：
两个上游各自前进时，那个"两边都能编"的 commit 要手工重新找。这是一笔
持续的维护成本，不是一次性的。

前置验证工程的第二项就是验它。找不到能同时编过的 commit，退路是 fork
其中一个自己维护——控制力最强，成本也最高。

#### 这笔账推迟到 llama.cpp 真进来的时候再付（2026-09-08）

阶段 5 开工时重新想了一遍这条：**统一 ggml 只在两个库同时链接时才需要**。

决策 4 之后大模型走远端（`[llm]` 配置段，`RemoteClient`），
llama.cpp 还没进程内化。所以现在 sd.cpp 可以带着自己那份 ggml 单独链，
`CMakeLists.txt` 里就是这么做的。

补丁集（`patches/`）留着不动。它已经在 CUDA 和 Metal 上都验证过了，
不是没做完的东西——只是现在用不上。提前统一等于**现在就开始付**
"两个上游各自前进、那个能同时编的 commit 要重新找"的维护成本，
而收益要等到 llama.cpp 进来才有。

重新用它的时机：把 llama.cpp 链进来做进程内大模型的那一天。
到时候按 `patches/README.md` 的步骤走，先重新生成一次补丁
（leejet/ggml 和上游都会前进）。

### 风险三：已验证解除，但换来一条硬约束（原为高）

前置验证的第三、四项在 RTX 2060 6GB 上跑完了，结论见
[cpp/verify/RESULTS.md](../cpp/verify/RESULTS.md)。

**`--offload-to-cpu` 不复现崩溃。** Issue #1483 在 sd.cpp `d8fb10c` 上没有出现。
11.3GB 权重（文本编码器 6.7GB + 扩散模型 3.3GB + VAE 1.3GB）显存常驻 0，
采样时峰值 68.64 MB。**方案第一条立项理由实测成立。** 原风险四关闭。

**VAE 分块存在且可用，不需要自己实现。** 但默认参数对 Wan 无效：默认 32x32
的块碰上 40x22 的潜变量，切出来只有 2 块、重叠率 0.75，显存只降 18%
（11747 → 9610 MB），仍然不够。改成 `--vae-tile-size 16x11 --vae-tile-overlap 0.25`
（6 块）后成功，VAE 解码 44.73s。

**换来的硬约束，要写进阶段 5**：

- `--offload-to-cpu`、`--vae-tiling` 是必备参数
- **`--vae-tile-size` 必须按潜变量尺寸算，不能用默认值**，而且要随分辨率
  自适应——写死一个值在换画质档位时会失效。这是编排层的责任，不是调一次
  就完事的配置
- `--temporal-tiling` 是独立开关，但低帧数下是空操作（9 帧只压成 3 个潜变量帧，
  分块粒度 4 帧比总数还大），且会引入额外开销让显存不降反升。**别默认打开**

一条纠正直觉的实测：**显存大头不是帧数，是空间维的解码展开。** 潜变量
`40x22x3x48` 只有 3 个时间帧却要 11.7GB，瓶颈在 40x22 展开成 640x352 的过程。
"少出几帧省显存"这个想法不成立。

### 风险四：树莓派跑不了 Wan 2.2（已验证，决策 4 已重定）

选型结论里成片档 5 秒片子在 5080 上要 392 秒。Pi 5 没有独立显存、没有
硬件 H.264 编码器，VideoCore VII 的 Vulkan 驱动成熟度未知。

**前置验证第六项已经跑完，结论是跑不了**，详见
[cpp/verify/RESULTS.md](../cpp/verify/RESULTS.md)。不是慢，是一步采样都没到：

```
MESA: error: Failed to allocate device memory for BO
vk::CommandBuffer::end: ErrorOutOfHostMemory
```

条件已经拉满——`--offload-to-cpu`、VAE 分块、文本编码器放 CPU、
额外加 8GB 磁盘交换、停掉 Docker 和整个桌面会话、换过电源
（全程 `throttled=0x0`），起跑时可用内存 7.4GB。

`total params memory size = 11285.94MB` 与 Windows 上完全一致，
所以这不是 ARM 的特殊行为，就是 11.3GB 的工作集塞不进 8GB 机器。

**交换救不了**：GPU 缓冲区要物理驻留的内存，换页出去的对 Vulkan 驱动
不可用。交换能延后 CPU 侧的 OOM，挡不住 GPU 侧的分配失败。

所以"能跑 > 画质 > 速度"的第一条就没满足，决策 4 要重定。三个方向：

1. **Pi 只做编排 + 界面，推理打到局域网里的 Windows 机器。**
   代价是 sd.cpp 不必链进同一个二进制，本方案第一条立项理由
   （逐层换入换出让大模型在小显存上跑）就只对 Windows 成立。
2. **换更小的模型跑 Pi。** 文本编码器占 11.3GB 里的 6.7GB，是最大一块。
   换更激进的量化可能压得下来，但那是另一条选型线，要重新验画质。
3. **等 16GB 的 Pi 5。** 装得下，但 V3D 没有矩阵核心这条不变，
   速度仍然是问题。

#### 决策 4（重定）：Pi 保留，Windows 做全流程验证，模型文件走配置

2026-09-07 定的。取的是方向 1 加方向 2 的组合，但把顺序倒过来：
**先不决定 Pi 上跑什么，先让"跑什么"变成可配置的。**

- **Pi 保留在方案里**，不删。它现在的角色是编排加界面，
  以及将来验证"小模型能不能凑合"的那台机器。
- **全流程验证在 Windows 上做。** 阶段 4 和阶段 5 的完成判据都以
  Windows 为准，Pi 不再是阻塞项。
- **模型文件改成配置项**，见下面那节。这是让前两条能同时成立的机制：
  同一个二进制，Windows 上指向全尺寸模型，Pi 上指向别的东西
  （或者干脆不配，走局域网推理）。

这样处理的理由是，方向 1 和 2 的分歧点在于"Pi 上到底能跑多小的模型"，
而那个问题现在答不了——要先有能跑起来的 C++ 流水线才谈得上换模型试。
把模型路径抽成配置之后，这个决定可以推迟到有数据的时候再做，
而且到时候不需要改代码。

对"严格单一二进制"那条立项理由的影响说清楚：**它在 Windows 上仍然成立**
（sd.cpp 链进同一个 exe，逐层换入换出让大模型在小显存上跑）；
在 Pi 上暂时不成立，Pi 现在是个只做编排的同款二进制。
这不是放弃那条理由，是承认它有硬件下限。

顺带记一条实测：本机开发机是 **RTX 2060 6GB**。Wan 2.2 TI2V-5B 的
工作集 11.3GB 在它上面同样装不下显存，Windows 上的全流程验证要靠
`--offload-to-cpu` 加分块，速度会比选型结论里那个 5080 的数字慢很多。
"能跑"没问题，"速度"要另算——阶段 5 的性能判据不能拿 5080 的数当基准。

另有两条实测顺带记下：**V3D 跑不了 T5 的嵌入表**，ggml 直接 abort 不回落，
文本编码器在 Pi 上只能走 CPU；**瓶颈是 GPU 不是 CPU**，扩散阶段只有一核
在自旋提交，V3D 满频但没有矩阵核心。

### 零运行时依赖在 MSVC 上要单独做（阶段 5 发现）

`CHANGJI_STATIC_RUNTIME` 那个开关原来只对 GNU/Clang 生效，
`if(CHANGJI_STATIC_RUNTIME AND NOT MSVC)`。链进 sd.cpp 之后
`dumpbin /dependents` 显示 exe 依赖：

```
MSVCP140.dll  VCRUNTIME140.dll  VCRUNTIME140_1.dll  VCOMP140.DLL
```

拷到没装 VC++ 运行库的机器上直接弹"缺少 DLL"。而"零运行时依赖"是这个
后端的立项理由之一，不能只在 MinGW 那条路上成立。

两处改动：

- `CMAKE_MSVC_RUNTIME_LIBRARY` 设成 `MultiThreaded`，而且**必须在
  FetchContent 之前设**——它要传染给所有子项目，一半 `/MT` 一半 `/MD`
  链接时报 RuntimeLibrary 不匹配，而那个错误指向的是某个 `.obj`，
  看不出是运行库选项的问题。
- `GGML_OPENMP=OFF`。**MSVC 的 OpenMP 运行时只有动态版**，`/MT` 也去不掉
  `VCOMP140.DLL`。关掉之后 ggml 用自带的线程池，CPU 推理慢一点，
  但这个项目的目标是 GPU 推理，"拷过去就能跑"比那点 CPU 性能重要。

改完只剩 `WS2_32` `MSWSOCK` `KERNEL32` `ADVAPI32` 四个 Windows 自带的，
二进制 49.6 MB。

顺带记一条操作上的坑：改运行库之后**要全量重编依赖**，只删
`build/CMakeCache.txt` 不够——而且删了它 CMake 会忘掉生成器，
下次配置默认成 Visual Studio，和 `_deps/*-subbuild` 里的 Ninja 缓存冲突，
报的错是"generator does not match"。正确做法是整个删掉 `build/`。

### 风险五：MSVC 切换会作废阶段 0 的一部分结论（中）

阶段 0 是 MinGW 编的，[cpp/README.md](../cpp/README.md) 里那套静态链接的
论证（`-static` 而不是 `-static-libgcc -static-libstdc++`）、中文路径 junction
的实测结论，都是 MinGW 语境下的。换 MSVC 之后 `/MT` 是另一套机制，
中文路径的表现也要重测。

放在阶段 1 之前换，是因为越晚换作废的东西越多。

标定值、各种边界情况的处理。这些以注释形式存在于 Python 源码里。

缓解：移植时**注释一并翻译过去**，不要只译代码。删除 Python 之前通读一遍
`stages/` 和 `hardware.py` 的注释，确认没有遗漏的隐性约束。

阶段 8 提前到 TTS 之前，让这一条的时间压力变大了——删的时候阶段 9 还没开始，
配音那部分注释（[audio.py](../src/changji/stages/audio.py) 685 行）还没有

## 七点五、实现期踩到的坑

这一节和阶段划分无关，是**做的过程中撞出来的、值得记住的几类问题**。
原来它们混在阶段 9 那一节里（只因为是同一段时间做的），但它们和配音没关系。

共同点是：**编译过、测试过、看起来一切正常，而错的地方要等真跑到那一步
才炸**——而"那一步"往往是用户第一次用的时候。

**`--init-config` 会写出一份让 Python 后端起不来的配置**（2026-09-08 修）。

模板里有 `[models]` 这一节，而 Python 的 `Settings` 是 `extra="forbid"`——
只要用户配置里出现它，**Python 整份加载失败、后端根本起不来**，
报的是 `Extra inputs are not permitted`。而迁移期间两个后端共用这一份文件。

这是踩出来的，不是想出来的：我拿 `--init-config` 当"看一眼配置在哪"的探针，
一敲就把模板写进了用户配置，然后对拍里 **152 条全变成"Python 侧：连不上"**
——而那看起来像是端口或网络的问题，离真正的原因很远。

两处改：
- 模板里 `[models]` 整节默认注释掉，并写明"取消注释之后 Python 就起不来了"。
  加了用例盯着（行首出现 `[models]` 就算失败）。
- **`--init-config` 不再覆盖已有配置**，要覆盖得显式加 `--force`。
  原来是无条件截断写的：一个已经配好模型路径和后端地址的用户，
  只是想看看模板长什么样，那些就全没了——而且没有任何提示，因为命令"成功"了。

**`/ws` 的服务端那一侧原来一条测试都没有**（2026-09-08 补上）。

`test_ws_client.cpp` 测的是我们自己写的客户端（连 ComfyUI 用的），
和广播中心是两码事。而 **Python 侧根本没有 WebSocket**（`server.py` 开头
写着"不用 WebSocket，因为轮询在这个场景够用"），所以这条路**没法对拍**，
只能自己测——它是全项目唯一一处既没有对拍、原来也没有单元测试的地方。

拿假指针测是安全的：`Hub` 里那个 `connection*` **纯粹当键用，从不解引用**，
唯一会解引用的是 `broadcast`，用例一次都不调它。

**第一次跑就抓到一个真 bug。** 用例里塞了一串畸形消息，
其中 `{"type":123,"job_id":456}` 让 handler 直接抛了出去：

```
[json.exception.type_error.302] type must be string, but is number
```

`msg.value("type", std::string{})` 只兜得住"键不存在"，兜不住"键在但类型
不对"。而这里是**客户端能直接喂进来的地方**，文件开头那句"客户端发来的
东西一律当不可信输入：解析失败就静默丢弃"因此并不成立。
改成先问类型再取。

**Windows 上"窄接口吃 UTF-8"这一类坑，已经踩到第四次**（2026-09-08）。
清单记在这儿，新写代码前扫一眼：

| 踩在哪 | 症状 |
|---|---|
| `stbi_write_png` 的 `fopen` | 中文项目名写不进图，报"写文件失败" |
| `_popen`（`proc::run`） | 中文/带空格的路径跑不起来，报"不是内部或外部命令" |
| `_putenv_s`（测试的 `ScopedEnv`） | PATH 被截断，**之后每条用例都在坏 PATH 上跑** |
| `std::fopen`（`llama_tts.cpp` 写 wav） | 同第一条。这处是我几天前新写的，**踩的是已经有注释警告过的同一个坑** |
| `fs::path(窄字符串字面量)` | 直接抛 "No mapping for the Unicode character" |

**规矩**：Windows 上凡是吃 `const char*` 路径或命令行的接口，一律换宽字符版
（`_wpopen`、`SetEnvironmentVariableW`），或者用 `ofstream(fs::path)`；
源码里的中文字面量转 `fs::path` 一律走 `paths::from_utf8`。

最后一条尤其顽固：**我写那条"中文路径跑得起来"的用例时，自己又踩了一次**
——用例测的就是这条规矩，写的时候还是忘了。大概这就是它值得有一条用例的原因。

**`proc::run` 不再经过 shell**（2026-09-08）：Windows 上 `CreateProcessW`，
别处 `fork + execv`。文件头那条 TODO 写的是"装配环节接进来之前必须换成
CreateProcess 加超时"——阶段 7 代码完成之后，这个期限到了。

换掉的直接原因是**上一条那个 bug 只是绕过去了，没有根治**：cmd 把
`,` `;` `=` 当分隔符是靠多加引号绕的，但绕不掉 cmd 在引号里照样展开
`%VAR%`，也绕不掉 popen 没有超时。不经过 shell 之后这一整类问题都不存在了。

引用规则也跟着换：从"迁就 cmd"改成 `CommandLineToArgvW` 那一套
（只有紧挨着引号的反斜杠要翻倍）。**判断"要不要引"仍然用宽的并集**，
因为 `which()` 可能返回一个 `.bat`（PATHEXT 里有，而 ffmpeg 的某些装法
正是 .bat 包装），而 Windows 跑 .bat 一定经过 cmd。

**新写的超时第一次就是错的，是新加的用例抓出来的。** 我先把管道读到 EOF
再等进程——而管道的 EOF 要等子进程退出才来，所以超时永远在"它已经结束了"
之后才开始计时。用例里 800 毫秒的超时实际等了 4123 毫秒。
改成读放在线程里、主线程只等进程，超时就 `TerminateProcess`。

测试靶子也换了：**必须是真的 `.exe`**（新增 `tests/tools/argecho.cpp`）。
原来拿 `.bat` 当靶子，而 Windows 跑 .bat 一定经过 cmd.exe——
测出来的是 cmd 的分隔规则，不是 `CreateProcessW` 的。
换成 CreateProcessW 之后那条用例照旧红，而那个红是测试工具带来的。

**一处两边共有的洞，记着但先不改**（2026-09-08）：
`-vf subtitles='<路径>'` 是用单引号括起来的，路径里再出现一个单引号就会
提前收尾，ffmpeg 报一句滤镜语法错误。

Python 的 `_escape_filter_path` 只做了 `\` → `/` 和 `:` → `\:`，
C++ 的 `escape_filter_path` 一模一样——**所以这不是移植漏了，是两边共有的**。
契约标准要求和 Python 一致，单方面改会让对拍多一条"不同"，
而那条不同其实是我们更对。

加了一条用例把现状钉住：**哪天有人只改一侧，它会立刻红**。真要修就两边
一起修——阶段 8 删掉 Python 之后就只剩一侧，那时候顺手改掉。
实际风险不高：项目名和集名基本是中文，中文里没有 ASCII 单引号。

**服务默认绑在 0.0.0.0 上**（2026-09-08 改掉）。

把 `--help` 当成用户看到的东西读了一遍，注意到 `--host` 的默认值是
`0.0.0.0`——**整个局域网都连得上**。而这套接口没有任何鉴权：
连上就能读项目、改分镜、起流水线。桌面用户不会想到自己起了个服务之后，
同一个 Wi-Fi 上的人都能操作它。

**Python 侧一直是 127.0.0.1**（`run_server` 的默认值和 `cli.py` 的 `--host`
都是），所以这也是一处**对拍看不见的差异**——对拍比的是响应内容，
比不到绑在哪个地址上。这类"不在响应里"的行为差异，对拍结构上就查不到，
只能靠一条条对着读。

容器里确实要 `0.0.0.0`，但那条路**本来就显式传了**
（Dockerfile 最后一行 `changji serve --host 0.0.0.0 --port 8080`），
不依赖这个默认值。所以改回环没有代价。

**装配层补上了和 Python 的命令行对比**（2026-09-08）。

上一条那个 bug 能活下来，是因为**装配层从来没有和 Python 比过**：
`test_assemble.cpp` 那 60 条断言钉的是我们自己的意图，
`golden/ffmpeg/parsers.json` 只覆盖**解析 ffmpeg 的输出**。
那条用例甚至**把截过位的值当成正确答案钉住了**（`loudnorm=I=-14:TP=-2`），
自己钉自己，钉错了照样绿。

新增 `cpp/tests/export_assemble_golden.py` → `golden/ffmpeg/commands.json`：
假一个 FFmpeg 塞进真的 `Assembler`，把 `run_ffmpeg` 收到的 argv 记下来，
七条命令（统一规格 ×2、拼接、混音、混音高精度、静音轨、烧字幕）。
C++ 侧七条用例逐个参数比。

放宽了两处，都写在语料的 `note` 里：**路径的拼写**（项目根换成 `<ROOT>`、
反斜杠换正斜杠）和**整数浮点的写法**（Python `-16.0` / 我们 `-16`）。
除此之外逐字节。

三件值得记的事：

一，**我的第一版语料带着它要抓的那个 bug**。只导了默认的 -16.0 / -1.5，
而 `%g` 把这两个渲染成 -16 / -1.5，抹掉 ".0" 之后和 Python 一样——
**默认值根本试不出截位**。补了一条 -16.123456 的用例才真的抓得到。
语料抓不住自己的立案理由，等于没有。

二，**路径归一化第一版是错的**：烧字幕那条命令里的路径已经被
`_escape_filter_path` 处理过（冒号变 `\:`），再无脑替换反斜杠会把
`C\:` 变成 `C/:`，转义毁了、根也认不出来。要先按转义后的拼法替根。
副作用是那条命令里的冒号转义就不再被走到了，所以另外单列了四条
真路径的 `escape_filter_path` 用例。

三，**顺带抓到一条空断言**。验语料牙齿时把 `concat_listing` 里的 `fwd(p)`
换成 `to_utf8(p)`，509 条**全绿**。原因是那条用例喂进去的路径本来就是
正斜杠字面量，"清单里没有反斜杠"这条断言**永远为真**，
那个转换一次都没被走到。改成用反斜杠拼路径，并先 `REQUIRE` 输入里
确实有反斜杠——**断言的前提要自己立住**，否则它只是看着在测。

**响度目标被 `%g` 截到 6 位有效数字**（2026-09-08 修）。

`mix_args` 里 loudnorm 的两个数用的是 `fmt("%g", ...)`。`%g` 默认 6 位
有效数字，而 `target_lufs` 是配置里一个**没有小数位限制**的浮点数。
填 `-16.123456`，C++ 写出去的是 `-16.1235`——**ffmpeg 就照这个值归一，
成片响度和 Python 的不一样**，而两边的命令行都"看着对"。

它是抄错了地方：`storyboard.cpp` 的 `format_g` 用 `%g` 是**对的**，
那边对的是 Python 的 `f"{x:g}"`，两边同一套 6 位规则。而 loudnorm 这边
Python 写的是 `f"{self.target_lufs}"`，也就是 `str(float)`，不截位。
两个看起来一样的格式化需求，Python 侧用的不是同一个东西。

改成 `%.12g`。

**另一处对不齐是有意留着的，也钉了用例**：整数值 Python 写 `-16.0`，
这里写 `-16`。ffmpeg 两个都当 `-16` 解析，成片一模一样；要逐字节一样
得照搬 Python 的 repr 规则（整数浮点补 `.0`），为一个解析结果相同的
字符串背那套算法不值。钉住是因为**下一个人看见这处不一致，得知道它是
被想过的**，而不是抄漏了。

顺带说清一件事：`test_assemble.cpp` 那 60 条断言**不读语料**——
它们钉的是 C++ 自己的行为，不是"和 Python 一样"。ffmpeg 那份语料
（`golden/ffmpeg/parsers.json`）只覆盖**解析 ffmpeg 的输出**，
不覆盖**拼 ffmpeg 的命令**。所以装配这一层目前是"按我们的意图测过"，
不是"和 Python 对过"——这条差别在删 Python 之前值得记着。

**HTTP 配音后端有两处比 Python 严，原来一个字都没记**（2026-09-08 补记）。

顺着上一条的思路查的：那个 bug 的形状是"**后端函数对象拿不到 Python 的
`self` 里有的东西**"，所以把七个后端逐个对了一遍。图像和视频那两个已经查完，
这次查配音。

没查到同类 bug，但查到两处**没记录的有意偏差**——C++ 的 `http_tts_backend`
比 Python 的 `HttpTTSBackend` 严：

| | Python（audio.py:161，2026-09-08 复核仍是这样） | C++ |
|---|---|---|
| 读时长 | `probe_wav_duration`，**只认 wav** | `probe_audio_duration`，wav 读不动退 ffprobe |
| 静音检查 | **没有**（只有它的 Comfy 后端有） | 有 |

两条都往严的方向偏，不会把 Python 能过的正常输入判失败。静音那条尤其
该有：独立 TTS 服务同样会在模型没载好时回一个合法的空 wav，
放行的代价是**一整集静音被当成配音成功**，混音、字幕、时长锁全部照跑。
读时长那条，Python 自己的两个后端就不一致（Comfy 用的正是
`probe_audio_duration`），更像是漏了而不是有意的。

**记下来的理由是阶段 8。** 删掉 Python 之后，后来的人看见 C++ 比 Python 严，
无从判断这是有意的还是抄漏了，很可能"对齐一下"改回去。
现在代码注释里写了，方案里也有这一条。

静音那条已经补了用例（把它去掉会挂 2 条）。**读时长那条钉不住**：
要证明差别得让一个 mp3 响应在这里成功，而那需要机器上真有 ffmpeg。
用例里写明了这一点，装上 ffmpeg 之后该补。

**首帧那条路的尺寸节点名单和 Python 不一样，没人记着为什么**（2026-09-08 记）。

给首帧后端补和 Python 的工作流对比时发现的（`frame_submit.json`）。
两边"尺寸节点候选名单"从来就不一样：

| | Python `ImageModelFrameBackend` | C++ `set_size` |
|---|---|---|
| 1 | `EmptySD3LatentImage` | `Wan22ImageToVideoLatent` |
| 2 | `EmptyLatentImage` | `EmptySD3LatentImage` |
| 3 | `EmptySD3LatentImage`（重复，多半是笔误） | `EmptyLatentImage` |
| 4 | `ModelSamplingSD3` | `EmptyHunyuanLatentVideo` |

第 4 项是要紧的。`ModelSamplingSD3` 只有 `model` 和 `shift`，
**根本没有 width / height**。而两边的 `set_by_class` 都只在**类名找不到**
时才抛，键不存在照样写进去。于是一个没有潜空间节点的工作流：
Python 会把 `width` / `height` 塞到 `ModelSamplingSD3` 上，
**看着成功了，实际什么也没设成**，还往工作流里多塞了两个无效输入。

两边都没真的调整尺寸，所以这不是画面出错的 bug；但它是一处**真实存在、
之前没有任何记录**的差异。C++ 不复刻那个无效写入。

记法用的是语料里的 `cpp_differs` 标注（和端点语料的 `cpp_note` 一个路子），
用例**两个方向都验**：Python 现在确实还那样写、C++ 确实没写，
**并且除了那一个节点其余必须逐字节一样**——偏差不许悄悄变宽。

另外五条（无参考图 / 两张 / 多于 LoadImage / 文件不在 / 没有 SaveImage）
和 Python 完全一致。这条路除此之外没有漂移。

**语料项目的七个空目录不在版本库里，新克隆跑测试就会挂**（2026-09-08 修）。

`test_project.cpp` 那条「子目录齐全」列的是语料项目根下的目录，
和 `project_expectations.json` 里 Python 导出的名单比。
但那七个目录（audio / frames / logs / output / refs / shots / subtitles）
**是空的，而 git 不跟踪空目录**——版本库里只有 `project.json` 和
`assets.json` 两个文件。它们一直只是"碰巧在盘上"。

后果有两个：**新克隆一份仓库跑测试就会挂**；任何清过一次工作区的操作
也会让它挂。是后者撞出来的——一次 `git stash -u` 把它们清掉了，
而 `stash pop` 带不回来，git 从来没跟踪过它们。
报错只说"子目录对不上"，指不到真正的原因。

先试的 `.gitkeep` 占位是**错的**：`refs/` 里多一个文件，而上传那四条
用例是逐个文件名比 `refs/` 内容的，立刻挂四条。

改成在临时目录里现建一个项目、比 `ensure()` 建出来的布局——
**本来要钉的就是这个**（"C++ 的 ensure() 和 Python 建出同一套目录"），
不是"语料目录里现在有什么"。验过：把那七个目录全删掉再跑，511 条全过。

**动漫线的视频提示词，两个后端都写死了写实线**（2026-09-08 修）。

`video_positive` 拼的是"画面描述 + 分隔符 + 运动描述"，分隔符跟着风格线走：
动漫线 `", "`，写实线 `"，"`。而两个视频后端——`comfy/renderers.cpp` 和
`infer/sd_video.cpp`——**都传的常量 `StyleLine::REALISTIC`**。

Python 那边走的是 `self.composer._sep`，composer 是从资产库建的，
天然知道风格线。C++ 把后端抽成了函数对象（那个抽象本身是对的，
换后端不用改流水线），代价是**函数对象拿不到资产库**，于是
"传哪个风格线"变成了调用方的责任，而两个调用方都传错了。

后果：动漫线的项目，C++ 拼出 `画面，运动`，Python 拼出 `画面, 运动`。
一个分隔符的差别，而**提示词是要逐字节对得上的**——
`export_prompt_golden.py` 的文档字符串里就是这么写的。

修法不是把两处常量改对，是**把 style_line 放进 `RenderPlan`**
（`make_plan` 从 composer 里取），`video_positive` 只收一个参数。
让它没法传错，比让两个调用方记得传对可靠。

**为什么之前没抓到，这一点比 bug 本身重要。** 语料里有动漫线的用例
（43 条里 3 条），`positive` 和 `motion` 两个字段也都逐字节比过——
**但没有任何一条比过"把这两个拼起来"的结果**。
两个零件各自合格，装配那一步没有图纸。

已经补进语料：每条用例多导一个 `video_positive`，由真的
`RenderStage._video_positive` 算出来，41 条 ok 用例全比。

**工作线程里的 `REQUIRE` 会把整轮跑截断，而汇总行看不出来**（2026-09-08 修）。

`test_jobs.cpp` 有一条竞态用例：poller 线程死循环读快照，主线程那边
工作线程狂写 3000 条事件。poller 里原来用的是 `REQUIRE`。

`REQUIRE` 失败靠**抛异常**中止用例。这是工作线程，异常出不去。实测：

    改成必失败的 REQUIRE →  test cases: 215 | 214 passed | 1 failed | 277 skipped
    改成必失败的 CHECK   →  test cases: 492 | 491 passed | 1 failed |   0 skipped

492 条只跑了 215 条，**剩下 277 条根本没执行**，而汇总行写的是"1 failed"。
看见这行的人会去修那一条然后重跑——不会想到另外 277 条压根没跑过。

改成 `CHECK`，并在后面补一句 `continue`：`CHECK` 不中止，
后面那行 `s.at("events")` 在字段缺失时会抛 nlohmann 的异常，
**那个才是真的会 terminate**。原来的 `REQUIRE` 顺带挡住了这一点，
换成 `CHECK` 就得自己挡。

顺带解释了一个一直没在意的现象：**断言总数每次都不一样**
（同一个二进制跑三次：10009 / 9577 / 22770，用例数都是 492）。
就是这条用例——poller 转多少圈看机器。所以 `verify_all` 的下限只能查
**用例数**，查断言数会一直误报（当初写对了，但那是碰巧）。

### 这一节的共同教训

**一、给一块没测过的代码补测试，往往不是"确认它是对的"，而是当场发现
它不对。** 上面几块里大半是这么来的：`/ws` 的 handler 能被任意客户端
一条消息抛出去、`proc::run` 跑不了中文路径、cmd 把 ffmpeg 的滤镜串切碎。

**二、新加的检查要验它有没有牙齿。** 故意把被测代码弄坏一次，看用例红不红。
有两次用例写完全绿、破坏之后**依然全绿**——说明它什么都没验到：
一次是用 `%*` 回显整条参数串（分不出参数被拆成了几个），
一次是靠 `where.exe` 的报错文字判断（它根本不回显搜的那个名字）。

**三、能观察到的才算数。** 推规则很容易推出一个"看起来对"的结论，
然后测试和实现一起错。cmd 的引用规则、`_popen` 的编码行为、
`launched` 的真实含义，都是真跑一遍才看清的。
