# C++ 后端重构方案

制定时间 2026-09-07，同日按十六项决策修订。

修订集中在三处：单一二进制的边界、推理接入的顺序、契约兼容的标准。
阶段表和风险表整个重排，并新增了一个必须在阶段 1 之前做完的前置验证工程。

## 目标

把现在的三层（Python 引擎 + ComfyUI + Node 界面）收敛成两层：

- **C++ 单一二进制**：编排 + 推理 + HTTP 服务
- **Node**：界面，以及平台投递这类天然属于 Node 生态的对接

产出物是一个 exe，零运行时依赖，Windows 和树莓派都能直接跑。

约束顺序：**能跑 > 画质 > 速度**。低配硬件上时间不是问题，显存才是。

### 单一二进制的边界

严格执行：**不允许随包分发任何 Python 侧车**。配音、口型、超分这些现在
只有 Python 实现的环节，要么自己 C++ 化，要么不做。

ComfyUI 不算侧车。它是用户机器上本来就装着的独立程序，作为**可选后端**
保留——有它就能用它那一整套生态，没有它二进制自己也要能跑。

但这个目标是**终局的，不是任何一个阶段的验收标准**。配音的 C++ 化
（见风险一）工期不可估，在它完成之前，纯二进制出不了声，配音要走
ComfyUI 后端过渡。阶段表里没有任何一格的完成标志包含"单一二进制已达成"。

## 为什么是 C++

不是为了快。编排层是纯 IO 胶水，语言对性能没有影响。

真正的理由只有两个：

1. **推理层必须是 C++**。sd.cpp 和 llama.cpp 都基于 ggml，链接进来才能拿到
   逐层权重换入换出的控制权，让 16GB 的模型在 6GB 卡上跑起来。这是整个
   项目的立项理由
2. **单一二进制**。低配设备上装 Python 环境和 Node 运行时本身就是负担

代价要认：编排层用 C++ 大约要 2.5 倍行数，且没有 pydantic 的等价物。
这是为上面两条付的学费，不是 C++ 在这一层更优。

## 一、工作量盘点

现有 Python 引擎 11,169 行。其中：

| 处理方式 | 模块 | 行数 |
|---|---|---|
| **直接删** | `web/page.py`（旧单页界面，Node 接管） | 1,563 |
| **暂缓** | `cli.py`（命令行入口，后期再补） | 366 |
| **需要移植** | 其余全部 | 9,240 |

`comfy/` 那 604 行和 `workflows_loader.py` 那 57 行原本列在"直接删"里。
ComfyUI 定为可选后端之后它们要移植，包括 `comfy/workflow.py` 里对付
界面版/接口版格式错位（`widgets_values` 那一坨）的 222 行。链接 sd.cpp
并不能让这个问题消失，只是让它不再是唯一路径。

移植目标约 9,240 行 Python，预计对应 **19,000 ~ 23,000 行 C++**。

这个数字不含两块：对拍程序（全 C++ 写，不复用 pytest，见第六节），
以及 Qwen3-TTS 的 codec 解码器（不可估，见风险一）。

Node 侧另有 `webapp/server/src/engine/` 5,385 行加 3,255 行测试，是早先
一次 JS 移植的残留，运行时无人 import——`index.js` 只用 `engine.js` 的
转发，只有测试文件在引它。已随本次修订删除。留着它的实际危害是让人
以为 Node 侧还有一份可用的引擎实现。

## 二、技术选型

| 用途 | 选型 | 理由 |
|---|---|---|
| HTTP + WebSocket 服务端 | **Crow** | 路由写法接近 Flask/FastAPI，接口能近乎一一对译；WebSocket 内置；header-only，交叉编译到 ARM 省事 |
| HTTP 客户端 | **cpp-httplib** | 只用来连可选的 ComfyUI 后端。LLM 和 TTS 都进程内，不再需要客户端 |
| JSON | **nlohmann/json** | 用普通 `json` 即可，不需要 `ordered_json`——契约标准是结构兼容而不是逐字节，见第三节 |
| 视频/图像推理 | **stable-diffusion.cpp** | 已支持 Wan 2.2 TI2V-5B，含 `--offload-to-cpu` 逐层卸载、`--vae-tiling`、`--diffusion-fa` |
| 文本推理 | **llama.cpp（进程内链接）** | 剧本/圣经/分镜三个阶段用。见下 |
| ggml | **统一 vendor 一份** | 两个库都关掉自带的，指向同一个 commit。见风险二 |
| 音视频 | **ffmpeg 子进程** | 保持现状。链接 libav 收益不足以抵消复杂度 |
| 配音 | **Qwen3-TTS 自行 C++ 化** | 见风险一 |
| 单元测试 | **doctest** | 单头文件、编译快、FetchContent 友好。Pi 上本机编译时 Catch2 的编译开销受不了 |
| 构建 | **CMake + FetchContent** | Windows 用 MSVC（CUDA 要过 nvcc，nvcc 不支持 MinGW）；ARM 用 Vulkan 后端 |

### 文本推理为什么走进程内

llama.cpp 起 server 也是 OpenAI 兼容的，保留现有的 HTTP 客户端本来是
零改动的省事做法。选进程内链接是为了守住单一二进制：一个要求用户
另外起一个服务进程的二进制，不叫单一二进制。

代价要认：`LLMConfig` 的 `base_url` / `api_key` 作废，`/api/llm/providers`
和 `/api/llm/models` 语义重定义为"列本地 gguf"，连远端云端大模型的能力
一并放弃——写剧本这一环云端大模型质量明显更好，这是真的损失。
这三项进第三节的破契约白名单。

### 不需要的东西

- **业务逻辑的异步化**。Crow 自带 asio 事件循环处理连接，但六个阶段的
  代码保持同步写法，跑在工作线程池上。Python 那边满屏的 `async` 是
  FastAPI 的框架要求，不是业务需求，不要照搬
- **ORM / 数据库**。项目数据是文件系统上的 JSON，保持原样

### pydantic 的替代

C++ 没有等价物，这是移植中最枯燥的一块。采用的模式：

```cpp
struct Shot {
    std::string shot_id;
    int duration_ms = 3000;
    // ... 字段
    NLOHMANN_DEFINE_TYPE_INTRUSIVE_WITH_DEFAULT(Shot, shot_id, duration_ms, ...)

    // 校验单独一个方法，返回错误列表而不是抛异常。
    // Python 那边 pydantic 的 field_validator 逐条翻译到这里。
    std::vector<std::string> validate() const;
};
```

约束：**校验逻辑必须和 Python 的 validator 一一对应**，对拍时才能发现漏移植。

### 核心策略：接口契约兼容

标准：**字段名、嵌套结构、取值、状态码一致；key 顺序不管**。

"逐字节兼容"这个说法在早先版本里出现过，收回。nlohmann::json 默认底层是
`std::map`，key 会被排序，而 Python 的 dict 是插入序，逐字节本来就做不到；
换 `ordered_json` 能做到，但为此把每个结构体的字段声明顺序对着 pydantic
模型排一遍，收益不值。

在这个标准下：

- Node 前端零改动（破契约白名单里那几项除外）
- 改地址加换配置文件就能在两个后端之间切（配置为什么要换，见第六节）
- 任何时刻两个后端都能同时跑，同样的请求打过去比对响应
- 出问题随时切回去

不允许借重构之机顺手改接口。要改接口，等 Python 删掉之后再说。

### 破契约白名单

这四项做不到兼容，前端要跟着改。改动排进阶段 4，不能拖——拖着的话
阶段 4 之后前端就同时对不上两个后端，两边都跑不顺。

| 项 | 原因 |
|---|---|
| `GET /` | 返回 `page.py` 的 HTML。page.py 删掉之后，C++ 只回一句纯文本指向 Node 界面 |
| `/api/llm/providers` | 探测远端 OpenAI 兼容服务。进程内推理之后语义重定义 |
| `/api/llm/models` | 同上，改成列本地 gguf 文件。设置页的模型下拉框跟着改 |
| `[llm]` 配置段 | `base_url` / `api_key` 换成模型文件路径。Python 的 `Settings` 是 `extra="forbid"`，多一个键整份配置就加载失败 |

### 校验错误的消息文字不算契约

状态码和 body 的**形状**要一致，但 `detail` 里那句话的**文字**不比。

Python 那边 pydantic 的报错长这样：

```
改动不合法：1 validation error for Shot
duration_s
  Input should be less than or equal to 30 [type=less_than_equal, input_value=99.0, ...]
    For further information visit https://errors.pydantic.dev/2.13/v/less_than_equal
```

里面嵌着 pydantic 的版本号和文档 URL。在 C++ 里复刻既荒唐又会随上游版本
腐烂，而前端只是把这个字符串显示出来、不解析它。C++ 侧给的是
`改动不合法：duration_s 要在 0 到 30 秒之间，当前 99`——更短也更能照着做。

对拍语料里这类用例标了 `"compare": "shape"`，只比状态码加"detail 是个非空
字符串"。**这是有意的偏离，不是没对齐。**

另有一条相反方向的发现：`extra="forbid"` 的违规，FastAPI 回的是 **422 而不是
400**，而且 detail 是结构化数组 `[{type, loc, msg, input}]` 不是一句话。
那个**要照做**——状态码和嵌套结构都在契约里。第一版我写成 400，对拍抓到了。

`/api/doctor` 的 `checks` 数组内容**不算**契约。前端是泛化渲染的，只认
`can_run` 和 `name/level/detail/fix` 四个键；检查项本身按各自后端的实际
情况写（Python 那边叫 "Python"、"ComfyUI"、"hardware"，C++ 叫"运行时"、
"推理服务"、GPU，这是对的，不要为了对拍改回去）。

`/api/voices` 在阶段 6 之前返回空列表加一条说明——它依赖 ComfyUI 的
节点清单，而 comfy/ 的移植排在阶段 6。这是暂时状态，不进白名单。

### WebSocket：增量，不是替换

**REST 接口原样保留，WebSocket 是加在旁边的第二条通道。**

这样契约兼容的策略才不会破：Node 前端可以先不动（继续轮询），等 C++
后端稳定后再改成订阅 WebSocket。两种方式并存，互为退路。

推送的理由是现有代码里已经论证过的——[comfy/client.py](../src/changji/comfy/client.py)
开头写着：*"用 WebSocket 监听进度而不是轮询历史接口，因为成片档一个镜头
要跑好几分钟，轮询既慢又容易漏掉中间状态。"* sd.cpp 的采样循环有逐步回调，
能推「第 12/30 步」这种真实时进度，轮询拿不到。

#### 消息格式

服务端下行，一律 JSON，带 `type` 和 `job_id`：

```json
{"type": "progress", "job_id": "...", "stage": "render",
 "shot_id": "S03", "step": 12, "total": 30}
{"type": "stage",    "job_id": "...", "stage": "audio", "status": "started"}
{"type": "log",      "job_id": "...", "level": "warn", "text": "..."}
{"type": "done",     "job_id": "...", "outputs": [...]}
{"type": "error",    "job_id": "...", "message": "..."}
```

客户端上行只有订阅控制：`{"type":"subscribe","job_id":"..."}` 和 `unsubscribe`。
**不通过 WebSocket 发业务指令**，那些走 REST。上行通道越窄越好。

#### 两条从 ComfyUI 那边学到的教训，必须带过来

1. **订阅按 job_id 记，不按连接记。** ComfyUI 按 clientId 记订阅，
   同一个 id 上并发跑两个任务，后连的会把先连的挤下线，先连的永远
   等不到完成消息。新设计里一个连接可订阅多个 job，一个 job 可被多个连接订阅，
   两者是多对多，不是一对一

2. **WebSocket 断线不是致命错误。** 服务端必须把每个 job 的最新状态
   留在内存里，REST 的 `GET /api/run` 仍然能查到完整状态。前端 WS 掉线
   就退回轮询，重连后先拉一次全量状态再续订阅。任务本身不受连接影响

#### 线程模型

```
Crow 事件循环线程   ──  HTTP 请求 + WebSocket 收发
工作线程池          ──  跑 job，同步写法
共享状态            ──  互斥量保护的 job 表 + 连接注册表
```

**不是一条工作线程。** [server.py](../src/changji/web/server.py) 现在有两个
独立的任务槽——`RunState` 跑流水线、`WriteState` 写整季，`WriteState` 的
注释明写着"跟跑流水线分开，两件事可以同时进行"。串行化会被对拍测出来。

用池加队列而不是两条固定线程：按 job 类型限流（流水线最多 1 个、写作
最多 1 个），以后想并发跑多集不用改架构。

**取消令牌按 job 挂，不按线程挂。** `/api/stop` 和 `/api/script/series/stop`
各自取消对应的 job。取消要能打断三个地方：sd.cpp 的采样回调、llama.cpp
的生成、ffmpeg 子进程。前两个的中止接口在前置验证工程里一并确认——
如果 sd.cpp 的逐步回调没有中止返回值，采样中途就停不下来，这会影响
`/api/stop` 的对拍结果。

工作线程产生进度 → 写进 job 表 → 通知广播器 → 广播器在事件循环线程上
向订阅了该 job 的连接发送。

需要小心的两处：

- **连接生命周期**。广播时连接可能已经关闭。连接注册表的增删和遍历
  必须在同一把锁下，或者用 Crow 提供的连接句柄有效性检查
- **推送频率**。逐步回调每秒可能触发几十次，直接透传会把前端淹掉。
  加节流，最多每 200ms 推一次，并且**完成消息不受节流影响**

## 四、前置验证工程

**阶段 1 之前必须做完。** 六项里任何一项不过，后面的阶段表都要重排。

它存在的理由：阶段 5 定了"直接上 sd.cpp"，没有阶段内退路。风险要在写下
两万行之前暴露，不是之后。

| 验证项 | 内容 | 不过的后果 |
|---|---|---|
| MSVC + CUDA | 阶段 0 是 MinGW 编的，但 sd.cpp/llama.cpp 的 CUDA 后端要过 nvcc，nvcc 在 Windows 上只支持 MSVC，整条工具链要换 | `-static` 那一套换成 `/MT`，README 里中文路径 junction 的结论要重测 |
| 统一 ggml 后双链 | 两个库都关掉自带 ggml 指向同一 commit，各跑一次推理 | 找不到两边都能编的 commit，就要 fork 其中一个长期自己维护 |
| ~~`--offload-to-cpu`~~ | **已验证：不复现崩溃。** 11.3GB 权重显存常驻 0，采样峰值 68.64 MB | — |
| ~~视频路径的 VAE 分块~~ | **已验证：接通可用**，但默认块大小对 Wan 无效，必须显式设 `--vae-tile-size` | — |
| Pi 上的 Vulkan 后端 | ggml 的 Vulkan 后端在 VideoCore VII 上能不能起来 | 退回 CPU/NEON，速度再降一档 |
| Pi 上的内存 | 8GB 能不能同时装下 Wan 2.2 TI2V-5B 的 Q4 权重、VAE 和系统 | 装不下的话"树莓派跑全流程"这个目标要重新讨论，见风险四 |

前四项在 Windows 上做，后两项在 Pi 上做，可以并行。

顺带在这个工程里确认 sd.cpp 的逐步回调和 llama.cpp 的生成有没有中止接口
——线程模型那一节的取消语义依赖它。

## 五、迁移顺序

原则：**每个阶段结束时系统都是可运行的**，不存在"写完才能跑"的中间态。

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| **0** | CMake 骨架、Crow 起 HTTP、配置读写、`/api/health` `/api/doctor`、WebSocket echo | Windows 上已完成。ARM 那部分并入前置验证工程 |
| **P** | 前置验证工程，见第四节 | 六项验证都有结论 |
| **1** | 工具链切到 MSVC；`models/` 三个数据结构 + 项目库读写 | 能读 Python 写的项目文件（含中文路径和中文内容），字段全部对得上 |
| **2** | 只读接口：`/api/project` `/api/shots` `/api/assets` `/api/settings` `/api/hardware` | Node 前端指向 C++ 后端，能正常显示项目 |
| **3** | 编辑接口：`/api/shot` `/api/character` `/api/style` `/api/location` 等；多段上传和 `/api/media` 的 Range 支持 | `test_web_editing.py` 的 1083 行全部对拍通过；参考图能传、成片能拖进度条 |
| **4** | LLM 三阶段接进程内 llama.cpp；线程池 + job 表 + WebSocket 广播；破契约那四项前端同步改 | 回放模式下生成结果与 Python 一致；WS 能实时看到阶段推进；设置页的模型选择改成本地 gguf |
| **5** | 链接 sd.cpp，frames + render；逐步进度接进 WS 广播 | 能出图能出视频，与 ComfyUI 输出做画质比对；前端能看到「第 12/30 步」 |
| **6** | 移植 `comfy/`，ComfyUI 作为可选后端接回来 | 配置里能在 sd.cpp 和 ComfyUI 之间切；`/api/voices` 恢复 |
| **7** | 配音编排 + 组装：`audio.py` 的编排逻辑、ffmpeg、字幕、成片 | 能产出完整一集（配音走 ComfyUI 后端） |
| **8** | 删 Python 引擎 | 只剩两层 |
| **9** | Qwen3-TTS 的 C++ 化 | 纯二进制能出声。并行推进，不卡前面任何阶段 |

### 阶段 5 的条件分支

前置验证的前四项全过，按上表顺序做。

`--offload-to-cpu` 或视频路径的 VAE 分块**不过**，阶段 5 和阶段 6 对调：
先把 ComfyUI 客户端移植出来，让 C++ 后端先具备完整的出片能力，再回头
啃 sd.cpp。这个分支现在写下来，不要等撞上了再临时决定。

### 为什么删 Python 排在阶段 8 而不是阶段 9

配音的 C++ 化工期不可估（风险一）。让它卡住 Python 的删除，等于让
"收敛成两层"这个目标挂在一个研发项上。阶段 7 结束时成片已经能出、
对拍已经通过，Python 引擎的回归基准作用就到头了。这期间配音走
ComfyUI 后端——TTS-Audio-Suite 那一套覆盖 19 个引擎、支持 SRT 对齐和
方括号切角色，质量比自己写的第一版只会更好。

## 六、对拍验证

Python 引擎保留的唯一目的：**当回归基准**。删除之前必须完成对拍。

### 对拍程序

纯 C++ 写，放在 `cpp/tests/compat/`。同时驱动两个后端，深比较响应。

pytest 那 5,781 行不直接复用，但里面积累的请求语料要留下来：写一个
用完即弃的 Python 脚本，把请求体和预期响应导出成 `cpp/tests/golden/` 下的
JSON，之后对拍程序纯 C++ 读这些文件。导出脚本是一次性的，不进仓库的
长期维护范围——这样"彻底去 Python"和"不丢掉三千多行测试里的边界情况"
两件事可以同时做到。

### 配置隔离

两个后端**不能**共用同一份用户全局配置。`[llm]` 段的字段在 C++ 侧要变，
而 Python 的 `Settings` 是 `extra="forbid"`，多一个键整份配置就加载失败；
`/api/settings` 又是可写接口，两边会互相覆盖。

对拍期两个后端各用 `--config` 指一份自己的配置，对拍程序负责把两份调成
等价。代价是"改一个地址就能切后端"变成"改地址加换配置文件"。

### 数据层对拍（阶段 1-3）

Python 和 C++ 读写同一批项目文件，逐字段比对。差异必须为零——字段顺序
无关的深比较、浮点数精度、空值处理。

**语料必须包含中文项目名、中文角色名、中文台词。** 项目目录现在就在
`E:\AI短剧\` 下，而 `std::filesystem` 在窄字符路径上的行为是这次移植
第一个会撞的坑（构建期的同类问题已经在 [cpp/README.md](../cpp/README.md)
里记过一次）。不专门造中文语料的话，会在阶段 1 的最后才发现。

### 接口层对拍（阶段 2-4）

两个后端同时启动在不同端口，同一组请求打过去比对响应体。破契约白名单里
那四项不参与对拍。

### LLM 阶段对拍（阶段 4）

LLM 输出不确定，不能直接对拍。做法：

1. 用 Python 跑一遍，把每次 LLM 的请求和响应录成 JSON 文件
2. C++ 侧接一个"回放模式"，读录制文件而不真的推理
3. 比对提示词拼接结果（必须逐字节相同）和后续解析结果

提示词拼接尤其要严：[render.py](../src/changji/stages/render.py) 里的分层顺序
（身份层 → 场景层 → 镜头层 → 风格层）不能变，顺序一改画面重心就变。

注意这里的"逐字节"是对**提示词字符串**说的，和第三节收回的那个"接口
逐字节兼容"是两回事。提示词是喂给模型的输入，差一个空格出图就不同。

### 推理层对拍（阶段 5）

不能要求逐像素相同——不同的实现、不同的量化格式必然有数值差异。
做法是固定种子生成同一个镜头，人工比对画质，重点看：

- 角色长相是否一致（这是整个项目的核心指标）
- 有无量化导致的色带、糊面、细节丢失
- 分块 VAE 解码有无可见接缝

## 七、风险

### 风险一：配音的 C++ 化没有先例（高）

现有 `models/TTS/` 里 17GB 权重是 CosyVoice、Qwen3-TTS、higgs_audio_v3，
全部是 Python 模型，没有 C++ 实现。[选型结论.md](选型结论.md) 里的主力是
Qwen3-TTS 1.7B（Apache 2.0，中文综合最强）。

要把它链进二进制，路径是：Qwen3 骨干转 GGUF 交给已经链在里面的 llama.cpp，
codec 解码器/声码器用 ggml 自己写。已知的未知有三个：llama.cpp 现在的 TTS
支持只覆盖 OuteTTS 那一档；Qwen3-TTS 用的是哪种 codec、声码器规模多大；
骨干能不能干净地转成 GGUF。这三个都要先查，查完才能估工期。

**决定：硬做，不接受退路。** sherpa-onnx 那一档的中文质量会丢掉选型结论里
TTS 那一节的筛选成果，不接受；Python 侧车违背单一二进制，不接受。

但它**不卡主线**。阶段 8 删 Python 的前置条件是阶段 7 完成（成片能出、
对拍通过），配音这期间走 ComfyUI 可选后端。Qwen3-TTS 的 C++ 化作为
阶段 9 并行推进。

这意味着阶段 8 之后有一段时间，实际形态是"C++ 二进制 + 用户自己装的
ComfyUI"，纯二进制出不了声。这一点写在这里，不要在阶段表里假装它不存在。

### 风险二：统一 ggml 是一笔长期维护成本（中）

sd.cpp 和 llama.cpp 各自 vendor 了不同 commit 的 ggml。同时链接进一个
二进制会有符号冲突或 ABI 不兼容。而"llama.cpp 走子进程"这条退路已经被
严格单一二进制关掉了。

做法是两个库都关掉自带的 ggml，指向同一份。麻烦不在第一次接通，在之后：
两个上游各自前进时，那个"两边都能编"的 commit 要手工重新找。这是一笔
持续的维护成本，不是一次性的。

前置验证工程的第二项就是验它。找不到能同时编过的 commit，退路是 fork
其中一个自己维护——控制力最强，成本也最高。

### 风险三：已验证解除，但换来一条硬约束（原为高）

前置验证的第三、四项在 RTX 2060 6GB 上跑完了，结论见
[cpp/verify/RESULTS.md](../cpp/verify/RESULTS.md)。

**`--offload-to-cpu` 不复现崩溃。** Issue #1483 在 sd.cpp `d8fb10c` 上没有出现。
11.3GB 权重（文本编码器 6.7GB + 扩散模型 3.3GB + VAE 1.3GB）显存常驻 0，
采样时峰值 68.64 MB。**方案第一条立项理由实测成立。** 原风险四关闭。

**VAE 分块存在且可用，不需要自己实现。** 但默认参数对 Wan 无效：默认 32x32
的块碰上 40x22 的潜变量，切出来只有 2 块、重叠率 0.75，显存只降 18%
（11747 → 9610 MB），仍然不够。改成 `--vae-tile-size 16x11 --vae-tile-overlap 0.25`
（6 块）后成功，VAE 解码 44.73s。

**换来的硬约束，要写进阶段 5**：

- `--offload-to-cpu`、`--vae-tiling` 是必备参数
- **`--vae-tile-size` 必须按潜变量尺寸算，不能用默认值**，而且要随分辨率
  自适应——写死一个值在换画质档位时会失效。这是编排层的责任，不是调一次
  就完事的配置
- `--temporal-tiling` 是独立开关，但低帧数下是空操作（9 帧只压成 3 个潜变量帧，
  分块粒度 4 帧比总数还大），且会引入额外开销让显存不降反升。**别默认打开**

一条纠正直觉的实测：**显存大头不是帧数，是空间维的解码展开。** 潜变量
`40x22x3x48` 只有 3 个时间帧却要 11.7GB，瓶颈在 40x22 展开成 640x352 的过程。
"少出几帧省显存"这个想法不成立。

### 风险四：树莓派跑全流程可能撞内存墙（高）

选型结论里成片档 5 秒片子在 5080 上要 392 秒。Pi 5 没有独立显存、没有
硬件 H.264 编码器，VideoCore VII 的 Vulkan 驱动成熟度未知。

决定是"跑全流程，慢也认"，符合"能跑 > 画质 > 速度"的约束顺序。速度不是
问题，**内存才是**：8GB 要同时装下 Q4 权重、VAE 和系统。这一项归入前置
验证工程。

装不下的话这个目标要重新讨论。退路是 Pi 只做编排和界面、推理打到局域网里
的 Windows 机器——但那样 sd.cpp 就不必链进同一个二进制，整个方案的第一条
立项理由（逐层权重换入换出）就只对 Windows 成立。这个连锁反应要提前知道。

### 风险五：MSVC 切换会作废阶段 0 的一部分结论（中）

阶段 0 是 MinGW 编的，[cpp/README.md](../cpp/README.md) 里那套静态链接的
论证（`-static` 而不是 `-static-libgcc -static-libstdc++`）、中文路径 junction
的实测结论，都是 MinGW 语境下的。换 MSVC 之后 `/MT` 是另一套机制，
中文路径的表现也要重测。

放在阶段 1 之前换，是因为越晚换作废的东西越多。

### 风险六：业务知识随 Python 删除而流失（中）

`stages/` 里积累的不只是代码：提示词分层顺序及其理由、画质档位的实测
标定值、各种边界情况的处理。这些以注释形式存在于 Python 源码里。

缓解：移植时**注释一并翻译过去**，不要只译代码。删除 Python 之前通读一遍
`stages/` 和 `hardware.py` 的注释，确认没有遗漏的隐性约束。

阶段 8 提前到 TTS 之前，让这一条的时间压力变大了——删的时候阶段 9 还没开始，
配音那部分注释（[audio.py](../src/changji/stages/audio.py) 685 行）还没有
对应的 C++ 落点。删之前要专门把它们抄进阶段 9 的工作笔记。
